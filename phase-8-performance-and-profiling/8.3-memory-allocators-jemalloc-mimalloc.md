## Concept

In multi-threaded Rust backend servers processing $100,000\text{ requests/sec}$, allocating and freeing heap memory (e.g. `String`, `Vec<u8>`, `Box<T>`, JSON DTOs) is often the **single largest CPU and memory bottleneck**.

By default, Rust uses the operating system's standard C library allocator (e.g., `glibc ptmalloc` on Linux). Under heavy multi-threaded load, default allocators suffer from:
1. **Global Allocator Lock Contention**: Threads block waiting to acquire central heap locks.
2. **Memory Fragmentation**: Inability to return unused memory pages back to the OS.
3. **Allocator Metadata False Sharing**.

```
                           Default System Allocator Bottleneck
┌────────────────────────────────────────────────────────────────────────┐
│  Worker 1 (Alloc 64B) ──┐                                              │
│  Worker 2 (Alloc 128B) ─┼──► [ Global Allocator Lock ] ──► System Heap │
│  Worker 3 (Free 32B) ───┘    (Threads STALL on Lock Contention!)       │
└────────────────────────────────────────────────────────────────────────┘

                   jemalloc / mimalloc (Thread-Local Arenas)
┌────────────────────────────────────────────────────────────────────────┐
│  Worker 1 ──► [ Thread Cache 1 (tcache) ] (ZERO LOCKS! 5ns Alloc)     │
│  Worker 2 ──► [ Thread Cache 2 (tcache) ] (ZERO LOCKS! 5ns Alloc)     │
│  Worker 3 ──► [ Thread Cache 3 (tcache) ] (ZERO LOCKS! 5ns Alloc)     │
└────────────────────────────────────────────────────────────────────────┘
```

---

### 1. High-Performance Modern Allocators

1. **`jemalloc` (`tikv-jemallocator`)**:
   - Developed for FreeBSD and Facebook's high-concurrency servers.
   - Employs **Thread Caches (`tcache`)** and **Per-Core Arenas** to eliminate lock contention.
   - Uses size classes (e.g., 8B, 16B, 32B, 48B, 64B) to prevent memory fragmentation.
   - Includes live heap profiling and decay-based page purging.

2. **`mimalloc` (`mimalloc`)**:
   - Developed by Microsoft Research.
   - Uses **Free-List Sharding** and **Compact Page Segments**.
   - Extremely fast micro-benchmark allocation speeds with low memory footprint.

---

### 2. Switching the Global Allocator in Rust

Switching your entire application's allocator requires **one single line of code**:

```rust
// Using jemalloc:
#[global_allocator]
static GLOBAL: tikv_jemallocator::Jemalloc = tikv_jemallocator::Jemalloc;

// OR using mimalloc:
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
```

---

### 3. Per-Request Bump Allocation (`bumpalo`)

For web handlers that allocate dozens of temporary objects during request processing, even `jemalloc` has some overhead.

A **Bump Allocator (Arena)** pre-allocates a contiguous slice of memory (e.g., 64KB) and increments a raw pointer on every allocation ($O(1)$). At the end of the HTTP request, the entire arena is reset in a single operation, **making deallocation completely free ($0\text{ns}$)**.

```
                    Bump Arena (Request Lifetime)
┌────────────────────────────────────────────────────────────────────────┐
│ [ JSON DTO 1 (128B) ] │ [ SQL Result (512B) ] │ [ Unused 63KB... ]     │
└───────────────────────────────────────────────▲────────────────────────┘
                                                │ Bump Pointer
```

---

## Why It Matters in Systems Programming

1. **Up to 30% Throughput Boost**: Switching to `jemalloc` or `mimalloc` on multi-core servers often provides an immediate 15–30% increase in request throughput with zero architectural changes.
2. **Eliminate Memory Leaks / Bloat**: jemalloc's aggressive decay policies prevent long-running microservices from slowly ballooning to gigabytes of RSS memory.
3. **Sub-Microsecond Latencies**: Thread caches provide constant $5 - 10\text{ns}$ allocations directly from L1/L2 cache.

## Real-World Analogy

- **System Allocator (`glibc`)** is like a single supply closet at an office: all 100 employees must line up at the same door to ask the clerk for a pencil, and line up again to return it.
- **jemalloc** is giving each employee their own desk drawer filled with pens, pencils, and paper clips: they grab and return supplies instantly without ever leaving their desk.
- **Bump Allocator (`bumpalo`)** is an append-only roll of butcher paper on the desk: you tear off pieces as needed, and at the end of the day you throw the whole roll into the recycle bin in one motion.

## Complete, Compilable Code Example

Below is a complete implementation of a **Per-Thread Bump Arena Allocator** in pure Rust demonstrating zero-cost bulk deallocations:

```rust
use std::cell::RefCell;
use std::time::Instant;

// ============================================================================
// 1. Fixed-Size Bump Arena Allocator
// ============================================================================

pub struct BumpArena {
    buffer: Vec<u8>,
    offset: usize,
}

impl BumpArena {
    pub fn with_capacity(capacity: usize) -> Self {
        Self {
            buffer: vec![0u8; capacity],
            offset: 0,
        }
    }

    /// Allocate `size` bytes with specified byte alignment
    pub fn alloc(&mut self, size: usize, align: usize) -> Option<*mut u8> {
        // Calculate aligned starting offset
        let current_ptr = self.buffer.as_ptr() as usize + self.offset;
        let aligned_ptr = (current_ptr + align - 1) & !(align - 1);
        let padding = aligned_ptr - current_ptr;

        if self.offset + padding + size > self.buffer.len() {
            return None; // Arena capacity exhausted
        }

        self.offset += padding;
        let result_ptr = unsafe { self.buffer.as_mut_ptr().add(self.offset) };
        self.offset += size;

        Some(result_ptr)
    }

    /// Instant zero-cost reset: deallocates all objects simultaneously
    pub fn reset(&mut self) {
        self.offset = 0;
    }

    pub fn allocated_bytes(&self) -> usize {
        self.offset
    }
}

// ============================================================================
// 2. Thread-Local Arena Pool
// ============================================================================

thread_local! {
    static REQUEST_ARENA: RefCell<BumpArena> = RefCell::new(BumpArena::with_capacity(64 * 1024)); // 64KB per thread
}

// ============================================================================
// 3. Benchmarking Standard Heap vs Bump Arena
// ============================================================================

fn benchmark_standard_heap(iterations: usize) -> (u128, usize) {
    let start = Instant::now();
    let mut total_bytes = 0;

    for _ in 0..iterations {
        // Simulate allocating 5 objects per HTTP request
        let v1: Vec<u8> = vec![0xAA; 128];
        let v2: Vec<u8> = vec![0xBB; 256];
        let v3: Vec<u8> = vec![0xCC; 512];
        total_bytes += v1.len() + v2.len() + v3.len();
        // Dropped individually -> 3 heap dealloc calls!
    }

    (start.elapsed().as_millis(), total_bytes)
}

fn benchmark_bump_arena(iterations: usize) -> (u128, usize) {
    let start = Instant::now();
    let mut total_bytes = 0;

    for _ in 0..iterations {
        REQUEST_ARENA.with(|arena_cell| {
            let mut arena = arena_cell.borrow_mut();
            
            // Allocate 3 objects inside arena
            let _p1 = arena.alloc(128, 8).unwrap();
            let _p2 = arena.alloc(256, 8).unwrap();
            let _p3 = arena.alloc(512, 8).unwrap();
            
            total_bytes += arena.allocated_bytes();
            
            // End of HTTP request -> Instant O(1) reset!
            arena.reset();
        });
    }

    (start.elapsed().as_millis(), total_bytes)
}

fn main() {
    println!("=== 1. Testing Bump Arena Allocation Mechanics ===");
    let mut arena = BumpArena::with_capacity(1024);
    let p1 = arena.alloc(64, 8).unwrap();
    let p2 = arena.alloc(128, 16).unwrap();

    println!("Allocated Pointer 1 (64B, align 8):  {:p}", p1);
    println!("Allocated Pointer 2 (128B, align 16): {:p}", p2);
    println!("Total Arena Memory Allocated: {} bytes", arena.allocated_bytes());

    arena.reset();
    println!("Arena Reset! Allocated bytes: {}\n", arena.allocated_bytes());

    println!("=== 2. Benchmarking Standard Heap vs Bump Arena (1,000,000 Requests) ===");
    let iters = 1_000_000;

    let (heap_ms, _) = benchmark_standard_heap(iters);
    println!("Standard Heap Allocation: {:>5} ms (Repeated malloc & free calls)", heap_ms);

    let (arena_ms, _) = benchmark_bump_arena(iters);
    println!("Thread Bump Arena:        {:>5} ms (Zero-Cost Bulk Reset)", arena_ms);

    if heap_ms > 0 && arena_ms > 0 {
        let speedup = heap_ms as f64 / arena_ms as f64;
        println!("\nSpeedup from Bump Allocation: {:.2}x faster!", speedup);
    }
}
```

## Common Pitfalls & Compiler Errors

### 1. Lifetime Violations with Bump Allocations
Memory allocated inside an arena is only valid until the arena is reset. If you attempt to return a reference to arena data outside the request scope, Rust's borrow checker prevents compilation:
```rust
// Compiler Error: `arena` does not live long enough
```

### 2. Cross-Thread Deallocations
If Thread A allocates memory and passes the pointer to Thread B to free, default allocators require cross-thread synchronization. `jemalloc` handles this via remote free lists, but excessive cross-thread frees reduce thread cache efficiency.

impl BumpArena {
    pub fn alloc_val<T>(&mut self, value: T) -> Option<&mut T> {
        let size = std::mem::size_of::<T>();
        let align = std::mem::align_of::<T>();
        let raw_ptr = self.alloc(size, align)? as *mut T;
        unsafe {
            raw_ptr.write(value);
            Some(&mut *raw_ptr)
        }
    }
