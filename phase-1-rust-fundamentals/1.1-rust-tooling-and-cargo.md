# Lesson 1.1: Rust Tooling: rustc, cargo, and the Build Workflow

## Prerequisites
- Lesson 0.1: Compiling vs Running (understanding source code, the compiler, and binary execution).

---

## Concept

When developing real-world software in Rust, you rarely compile files by invoking the raw compiler (`rustc`) directly. Instead, you interact with Rust's unified toolchain through **Cargo**.

---

### 1. The Compiler (`rustc`) vs. The Build Manager (`cargo`)

- **`rustc`**: The low-level Rust compiler. It takes `.rs` files and translates them into machine code binaries. While you can run `rustc main.rs`, it becomes cumbersome when managing multiple source files, automated tests, and third-party libraries.
- **`Cargo`**: Rust's official **build system and package manager**. Cargo automates downloading dependencies, configuring the compiler, running tests, and assembling your final binary.

```
                  ┌──────────────────────────────────────────────┐
                  │                 Cargo CLI                    │
                  │   (cargo check / cargo build / cargo run)    │
                  └──────────────────────┬───────────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
     ┌───────────────────────┐                       ┌───────────────────────┐
     │  Dependency Resolver  │                       │      rustc (LLVM)     │
     │ Downloads & Caches    │ ────────────────────> │ Compiles native code  │
     │ crates from crates.io │                       │ into machine binary   │
     └───────────────────────┘                       └───────────────────────┘
```

---

### 2. Standard Cargo Project Layout

When you create a new project using Cargo:
```bash
cargo new http_server
```
Cargo generates a standardized folder structure:

```text
http_server/
├── Cargo.toml      # The Project Manifest (metadata & dependencies)
├── Cargo.lock      # Auto-generated exact dependency snapshot
└── src/
    └── main.rs     # The entry point of your binary application
```

#### Understanding `Cargo.toml`:
Written in TOML (*Tom's Obvious Minimal Language*), this file contains your project configuration:

```toml
[package]
name = "http_server"
version = "0.1.0"
edition = "2021"

[dependencies]
# External libraries (crates) are listed here
```

---

### 3. Essential Cargo Commands

| Command | What it does | When to use it |
| :--- | :--- | :--- |
| `cargo new <name>` | Scaffolds a new binary Rust project directory. | Starting a new project. |
| `cargo check` | Validates syntax and types **without** generating a binary. | During active coding (runs 5-10x faster than building). |
| `cargo build` | Compiles source code into a **Debug binary** in `target/debug/`. | When you need a local executable for testing/debugging. |
| `cargo run` | Compiles (if modified) and immediately executes the binary. | Running and testing your code in one step. |
| `cargo build --release` | Compiles with aggressive optimizations in `target/release/`. | Production builds and performance benchmarking. |

---

### 4. Debug vs. Release Builds

Cargo provides two distinct build profiles:

1. **Debug Mode (`cargo build` / `cargo run`)**:
   - Compiles very quickly.
   - Leaves in extra runtime safety checks (like overflow checks).
   - Generates large binary files containing debugging symbols.
2. **Release Mode (`cargo build --release` / `cargo run --release`)**:
   - Takes longer to compile.
   - LLVM optimization engine reorganizes loops, inlines functions, and removes dead code.
   - Produces a compact, ultra-fast native binary suitable for production servers.

---

## Why it matters

Systems programming requires absolute predictability and maximum performance. Developing in debug mode gives you rapid compiler feedback and panic stack traces during development. Then, compiling with `--release` enables the compiler's optimization passes, often speeding up systems code (such as HTTP request parsers or matrix multiplications) by **10x to 100x**.

---

## Analogy

- `rustc` is a single hand saw. It works fine for cutting a single piece of wood.
- `cargo` is a complete automated woodworking workshop: it orders the lumber, sets the alignment jigs, measures the cuts, runs safety inspections, and packages the finished furniture for delivery.

## Code Example

Below is a complete `src/main.rs` that inspects its own compile-time environment to determine whether it is running as a Debug build or an Optimized Release build.

```rust
fn main() {
    let service_name = "AuthWorker";
    let version = "1.0.0";

    println!("========================================");
    println!("  Starting Service: {} (v{})", service_name, version);
    println!("========================================");

    // "cfg!(debug_assertions)" is a built-in macro that evaluates to `true`
    // when compiled in debug mode, and `false` when compiled with `--release`.
    if cfg!(debug_assertions) {
        println!("Build Profile : DEBUG");
        println!("Optimizations : Disabled (Fast compilation, debug symbols present)");
        println!("Warning       : Do not benchmark performance in this mode!");
    } else {
        println!("Build Profile : RELEASE");
        println!("Optimizations : Maximum (High-performance production binary)");
    }

    println!("----------------------------------------");
    println!("System ready to accept network requests.");
}
```

### How to Run This Code:
1. Run in debug mode:
   ```bash
   cargo run
   ```
2. Run in optimized release mode:
   ```bash
   cargo run --release
   ```

## Common Mistakes

### 1. Benchmarking Performance in Debug Mode
A beginner writes a complex algorithm, runs it with `cargo run`, and assumes Rust is slow. 

*Why it happens*: In debug mode, compiler optimizations are turned off so compilation is fast. You must always use `cargo run --release` when measuring execution speed.

---

### 2. Forgetting to Use `cargo check` During Development
Constantly waiting for `cargo build` to link a full binary file after every minor code edit.

*Why it happens*: Beginners don't know about `cargo check`. `cargo check` skips code generation and only does type/syntax verification, saving thousands of seconds of development time.

---

### 3. Manually Editing `Cargo.lock`
Modifying `Cargo.lock` directly in a text editor.

*Why it happens*: `Cargo.toml` is meant for humans (where you specify dependency requirements like `serde = "1.0"`). `Cargo.lock` is an exact record generated automatically by Cargo to ensure reproducible builds across different machines. Never edit `Cargo.lock` by hand.

## Solutions

### Solution to Exercise 1
1. `cargo check`
2. `cargo run`
3. `cargo build --release`
4. `cargo new network_sniffer`

---

### Solution to Exercise 2
- **`Cargo.toml`**: The high-level configuration file written and edited by the developer. It specifies package metadata, compiler settings, and required dependencies.
- **`Cargo.lock`**: An exact snapshot generated and maintained automatically by Cargo that records the precise versions of all dependencies and sub-dependencies used during the build.
- **Only `Cargo.toml` should be edited manually.**

---

### Solution to Exercise 3
**Output:**
```text
Build Profile : RELEASE
```
**Explanation**: When the `--release` flag is provided, Cargo disables debug assertions, causing `cfg!(debug_assertions)` to evaluate to `false` and triggering the `else` branch.
