## Concept

In professional systems software, relying on manual `println!` statements to verify code is slow, incomplete, and unsustainable. 

Rust includes a first-class, industrial-grade **Automated Testing Framework** built directly into the language and `cargo`.

---

### 1. Unit Tests (Internal Component Testing)

**Unit tests** verify small, isolated pieces of logic (individual functions or structs). In Rust, unit tests live in the **exact same file as the production code**, inside a dedicated test module.

```
src/parser.rs
┌────────────────────────────────────────────────────────┐
│ pub fn parse_header(...) { ... }                       │
│ fn sanitize_line(...) { ... } // Private helper        │
│                                                        │
│ #[cfg(test)]                                           │
│ mod tests {                                            │
│     use super::*; // Brings outer items into scope    │
│                                                        │
│     #[test]                                            │
│     fn test_parse_valid_header() {                     │
│         assert_eq!(...);                               │
│     }                                                  │
│ }                                                      │
└────────────────────────────────────────────────────────┘
```

#### Key Annotations and Macros:
1. **`#[cfg(test)]`**: Tells the compiler to compile and run this module **only when running `cargo test`**. In production release builds (`cargo build --release`), this code is completely excluded with zero binary bloat.
2. **`#[test]`**: Marks a function as a runnable test case.
3. **`use super::*;`**: Imports all functions and structs from the outer module (including **private** functions!).
4. **Assertion Macros**:
   - `assert!(condition)`: Verifies that a boolean expression is `true`.
   - `assert_eq!(left, right)`: Verifies that `left == right`.
   - `assert_ne!(left, right)`: Verifies that `left != right`.
5. **`#[should_panic]`**: Verifies that the code intentionally crashes/panics under invalid conditions.

#### Tests Returning `Result`:
You can write test functions that return `Result<(), E>`, allowing you to use the `?` operator inside tests:

```rust
#[test]
fn test_with_question_mark() -> Result<(), String> {
    let port = "8080".parse::<u16>().map_err(|e| e.to_string())?;
    assert_eq!(port, 8080);
    Ok(())
}
```

### 2. Integration Tests (Black-Box Testing)

**Integration tests** live outside the `src/` directory in a dedicated **`tests/`** directory at your project root (e.g., `tests/server_integration.rs`).

- They treat your library crate as an external client.
- They can **only access public (`pub`) APIs**.
- They verify that multiple subsystems (routing, parsing, state) work together correctly.

---

### 3. Test-Driven Development (TDD) Workflow

TDD follows the three-step **Red $\rightarrow$ Green $\rightarrow$ Refactor** loop:
1. **Red**: Write an automated test for a feature before writing the implementation. Run `cargo test` and watch it fail.
2. **Green**: Write the minimal amount of code necessary to make the test pass.
3. **Refactor**: Clean up and optimize the implementation while running `cargo test` to ensure no regressions.

---

### 4. Running Tests with Cargo

```bash
cargo test                    # Run all unit and integration tests in parallel
cargo test test_parse_port    # Run only tests matching a name filter
cargo test -- --nocapture     # Show println! output even for passing tests
```

## Why it matters

In Phase 2 (building custom Data Structures from scratch) and Phase 4 (hand-rolling an HTTP/1.1 server from raw TCP bytes), manual testing cannot reliably catch subtle memory layout bugs, off-by-one pointer errors, or boundary conditions. 

Automated unit testing allows you to verify hundreds of edge cases (empty buffers, corrupted header bytes, buffer overflows) in milliseconds on every code save.

## Analogy

Think of an **Automotive Proving Ground**:
- **Unit Tests (`#[cfg(test)]`)**: The bench test in the laboratory where an engineer puts a single fuel injector into a clamp, runs electrical pulses through it, and measures the droplet spray volume in isolation.
- **Integration Tests (`tests/`)**: Driving the fully assembled car onto the outdoor track to verify that pressing the brake pedal activates the hydraulic fluid and stops the wheels.
- **`cargo test`**: The master automated factory inspection checklist that executes every single bench test and track test before shipping the car to the customer.

## Code Example

```rust
// --- PRODUCTION CODE ---

#[derive(Debug, PartialEq)]
pub struct HttpResponse {
    pub status_code: u16,
    pub body: String,
}

pub fn create_response(status_code: u16, body: &str) -> Result<HttpResponse, String> {
    if status_code < 100 || status_code > 599 {
        return Err(format!("Invalid HTTP status code: {}", status_code));
    }

    Ok(HttpResponse {
        status_code,
        body: body.to_string(),
    })
}

// Private helper function
fn sanitize_body(raw: &str) -> String {
    raw.trim().replace('\r', "")
}

// --- UNIT TEST MODULE ---
#[cfg(test)]
mod tests {
    use super::*; // Bring production items (including private `sanitize_body`) into scope

    #[test]
    fn test_valid_response_creation() {
        let result = create_response(200, "OK");
        assert!(result.is_ok());

        let response = result.unwrap();
        assert_eq!(response.status_code, 200);
        assert_eq!(response.body, "OK");
    }

    #[test]
    fn test_invalid_status_code_returns_err() {
        let result = create_response(999, "Error");
        assert!(result.is_err());
        assert_eq!(
            result.unwrap_err(),
            "Invalid HTTP status code: 999"
        );
    }

    #[test]
    fn test_private_sanitizer_helper() {
        let dirty = "  payload with carriage return \r  ";
        let clean = sanitize_body(dirty);
        assert_eq!(clean, "payload with carriage return");
    }

    #[test]
    fn test_using_result_and_question_mark() -> Result<(), String> {
        let res = create_response(404, "Not Found")?;
        assert_ne!(res.status_code, 200);
        Ok(())
    }
}

fn main() {
    println!("Run `cargo test` to execute the automated test suite!");
}
```

## Common Mistakes

### 1. Forgetting `use super::*;` in the Test Module
Because `mod tests` is an inner module, it does not automatically inherit items from its parent.

**Broken Code:**
```rust
#[cfg(test)]
mod tests {
    #[test]
    fn test_something() {
        let res = create_response(200, "OK"); // Error: cannot find function `create_response`
    }
}
```
*How to fix*: Add `use super::*;` at the top of the test module.

---

### 2. Forgetting `#[cfg(test)]`
Declaring `mod tests` without `#[cfg(test)]`. 

*Why it's bad*: The test code, test fixtures, and assertion strings will be compiled into your production release binary, increasing binary size and memory footprint.

---

### 3. Using `println!` Instead of Assertions
Printing text and looking at it manually rather than writing `assert_eq!`. If a test doesn't panic or return `Err`, Cargo considers it passed—even if the output printed to the screen is wrong.

## Exercises

### Exercise 1 (Testing a Content-Length Calculator)
1. Write a function `calculate_content_length(body: &str) -> usize` that returns `body.len()`.
2. Write a unit test module with:
   - A test verifying that an empty string returns `0`.
   - A test verifying that `"Hello, World!"` returns `13`.
   - A test verifying that the 4-byte emoji `"🦀"` returns `4`.

---

### Exercise 2 (Testing for Expected Panics)
Write a function `validate_port(port: u16)` that panics with `"Port cannot be 0"` if `port == 0`.
Write a test with `#[should_panic(expected = "Port cannot be 0")]` that verifies the panic occurs.

---

### Exercise 3 (TDD for an IP Sanitizer)
Using Test-Driven Development:
1. First write a test `test_strip_http_prefix` that asserts `strip_http_prefix("http://127.0.0.1")` returns `"127.0.0.1"`, and `strip_http_prefix("127.0.0.1")` returns `"127.0.0.1"`.
2. Implement the function `strip_http_prefix(url: &str) -> &str` using `.strip_prefix("http://").unwrap_or(url)` to make the test turn green.

## Solutions

### Solution to Exercise 1
```rust
pub fn calculate_content_length(body: &str) -> usize {
    body.len()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_empty_string() {
        assert_eq!(calculate_content_length(""), 0);
    }

    #[test]
    fn test_ascii_string() {
        assert_eq!(calculate_content_length("Hello, World!"), 13);
    }

    #[test]
    fn test_unicode_emoji_bytes() {
        assert_eq!(calculate_content_length("🦀"), 4);
    }
}
```

---

### Solution to Exercise 2
```rust
pub fn validate_port(port: u16) {
    if port == 0 {
        panic!("Port cannot be 0");
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    #[should_panic(expected = "Port cannot be 0")]
    fn test_port_zero_panics() {
        validate_port(0);
    }

    #[test]
    fn test_valid_port_does_not_panic() {
        validate_port(8080); // Should pass cleanly
    }
}
```

---

### Solution to Exercise 3
```rust
pub fn strip_http_prefix(url: &str) -> &str {
    url.strip_prefix("http://").unwrap_or(url)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_strip_http_prefix() {
        assert_eq!(strip_http_prefix("http://127.0.0.1"), "127.0.0.1");
        assert_eq!(strip_http_prefix("127.0.0.1"), "127.0.0.1");
    }
}
```
