# Lesson 1.5: Borrowing and References: Shared vs. Mutable

## Prerequisites
- Lesson 0.5: Memory Architecture (Pointers, addresses, and heap allocations).
- Lesson 1.4: Ownership (The 3 rules of ownership, move semantics, and dropping values).

## Concept

In Lesson 1.4, we saw that passing a heap-allocated `String` into a function transfers (moves) ownership. If the caller wants to use the data again, the function has to return the string back in a tuple. This pattern quickly becomes tedious and impractical.

To allow code to access data without taking ownership, Rust provides **References**. The act of creating a reference is called **Borrowing**.

```
Original Owner (Stack)                  Heap Data
┌───────────────────────┐              ┌───────────────────────────┐
│ request_body          │ ───────────> │ "POST /api/v1/auth"       │
│ ptr: 0x7FFF00         │              │ [0x7FFF00]                │
└───────────────────────┘              └───────────────────────────┘
           ▲
           │ Pointer to Owner
┌───────────────────────┐
│ &request_body         │ (Shared Reference: Borrows read access)
└───────────────────────┘
```

---

### 1. Shared References (`&T`)

A **shared reference** (indicated by an ampersand `&`) gives you **read-only** access to the data.

- You do not own the data.
- When the reference goes out of scope, the underlying data is **not** dropped.
- You can create **as many shared references as you want** at the same time.

```rust
fn calculate_length(text: &String) -> usize {
    text.len() // Read-only access
} // `text` goes out of scope, but the String is NOT dropped because `text` only borrowed it!
```

---

### 2. Mutable References (`&mut T`)

If you need a function to modify data in-place without taking ownership, you use a **mutable reference** (`&mut`):

1. The original variable **must** be declared with `let mut`.
2. You pass it with `&mut variable_name`.
3. The function accepts it with `param: &mut Type`.

```rust
fn append_status(log: &mut String) {
    log.push_str(" [200 OK]");
}
```

---

### 3. The Two Inviolable Rules of Borrowing (Aliasing XOR Mutability)

To guarantee that data can never be corrupted by concurrent reads and writes, the Rust compiler enforces two rules:

1. **At any given time, you can have either:**
   - **Any number of shared references (`&T`)**, OR
   - **Exactly one mutable reference (`&mut T`)**.
2. **References must always be valid** (Rust prevents dangling references at compile time).

```
┌────────────────────────────────────────────────────────┐
│             THE BORROW CHECKER FORMULA                 │
│                                                        │
│   (Many Readers)  XOR  (One Writer)                    │
│                                                        │
│   You can NEVER have a writer while readers exist!     │
└────────────────────────────────────────────────────────┘
```

#### Why this rule exists:
If one part of your code is modifying a buffer (`&mut`) while another part is reading it (`&`), the reader could see partially written, corrupt data (a **Data Race**). Rust eliminates this entire category of bugs at compile time.

---

### 4. Non-Lexical Lifetimes (NLL)

A reference's lifespan does not necessarily extend to the end of the enclosing `{}` block. A borrow ends at the **last line of code where that reference is actively used**. 

Once all shared references have been used for the last time, you are free to create a mutable reference.

---

## Why it matters

In high-performance networking, request routers inspect incoming URLs hundreds of thousands of times per second. If routing required copying the URL string every time, memory allocation would grind the server to a halt. 

By passing shared references (`&String` or `&str`), the router inspects the exact same memory buffer instantly. Simultaneously, Rust's borrow checker guarantees that no background thread can mutate that buffer while the router is reading it.

---

## Analogy

- **Shared Borrow (`&T`)**: A book in a public library reference room. Twenty people can sit around the table and read the exact same book simultaneously. Nobody is allowed to bring a pen and alter the text while others are reading.
- **Mutable Borrow (`&mut T`)**: An author checking out the master manuscript into a private editing room. Only **one** author can hold the red pen at a time. While the author is editing, no public readers are permitted in the room.

## Code Example

```rust
// 1. Function borrowing a shared reference (Read-Only)
fn print_request_summary(path: &String, port: u16) {
    println!("Incoming Request -> Path: '{}', Target Port: {}", path, port);
    // path.push_str("/extra"); // COMPILE ERROR: Cannot mutate through a shared reference!
}

// 2. Function borrowing a mutable reference (Read & Write)
fn append_trace_id(header_buffer: &mut String, trace_id: u64) {
    header_buffer.push_str("\nTrace-ID: ");
    header_buffer.push_str(&trace_id.to_string());
}

fn main() {
    println!("--- 1. Shared References (Multiple Readers) ---");
    let endpoint = String::from("/api/v2/users");
    let server_port: u16 = 443;

    // Creating two simultaneous shared borrows
    let ref1 = &endpoint;
    let ref2 = &endpoint;
    println!("Reader 1 sees: {}", ref1);
    println!("Reader 2 sees: {}", ref2);

    // Passing shared reference to a function
    print_request_summary(&endpoint, server_port);

    // `endpoint` was only borrowed, so it is still 100% valid here!
    println!("Original endpoint is still alive: {}", endpoint);

    println!("\n--- 2. Mutable Reference (Single Writer) ---");
    let mut http_headers = String::from("Host: example.internal\nContent-Type: application/json");

    // Pass a mutable reference to modify the buffer in-place
    append_trace_id(&mut http_headers, 984019283);

    println!("Updated Headers:\n{}", http_headers);
}
```

## Common Mistakes

### 1. Mixing Shared and Mutable References Simultaneously
Attempting to modify a variable while an active shared reference still exists.

**Broken Code:**
```rust
fn main() {
    let mut message = String::from("Hello");
    let read_ref = &message; // Shared borrow begins
    message.push_str(", World!"); // Error: Mutation occurs while read_ref exists!
    println!("Message: {}", read_ref);
}
```

**Compiler Output:**
```text
error[E0502]: cannot borrow `message` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let read_ref = &message;
  |                    -------- immutable borrow occurs here
4 |     message.push_str(", World!");
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("Message: {}", read_ref);
  |                            --------- immutable borrow later used here
```

---

### 2. Creating a Dangling Reference
Returning a reference to a local variable that will be destroyed when the function exits.

**Broken Code:**
```rust
fn create_dangling_reference() -> &String {
    let local_data = String::from("temporary");
    &local_data // Error: `local_data` is dropped at end of function!
}
```

**Compiler Output:**
```text
error[E0515]: cannot return reference to local variable `local_data`
 --> src/main.rs:3:5
  |
3 |     &local_data
  |     ^^^^^^^^^^^ returns a reference to data owned by the current function
```
*How to fix*: Return the `String` directly (moving ownership) instead of returning a reference.

---

### 3. Forgetting `mut` on the Original Variable
You cannot create a mutable reference (`&mut`) to an immutable variable.

```rust
// Snippet A
let mut buffer = String::from("Data");
let r1 = &buffer;
let r2 = &buffer;
println!("{} and {}", r1, r2);

let r1 = &buffer;
let r2 = &mut buffer;

```

### Exercise 2 (Refactoring Away From Moves)
The following code unnecessarily moves ownership into `verify_token`, requiring the caller to pass it back. Refactor `verify_token` to use a **shared reference** (`&String`) so `auth_token` remains accessible in `main()`.

```rust
fn verify_token(token: String) -> bool {
    token.starts_with("Bearer_")
}

fn main() {
    let auth_token = String::from("Bearer_secret99");
    let is_valid = verify_token(auth_token);
    // Goal: print auth_token here without compile error
}
```

---

### Exercise 3 (In-Place Header Injector)
Write a complete Rust program with a function `inject_content_length`:
1. It takes a mutable reference to a `headers: &mut String` and a `length: usize`.
2. It appends `"\nContent-Length: <length>"` to the headers.
3. In `main()`, initialize a mutable header string, call the function, and print the updated string.

---

## Solutions

### Solution to Exercise 1
- **Snippet A**: **Compiles**. Any number of immutable/shared references (`r1`, `r2`) can coexist.
- **Snippet B**: **Fails to compile**. You cannot have a mutable reference (`r2`) while a shared reference (`r1`) is active and used.

---

### Solution to Exercise 2
```rust
fn verify_token(token: &String) -> bool {
    token.starts_with("Bearer_")
}

fn main() {
    let auth_token = String::from("Bearer_secret99");
    let is_valid = verify_token(&auth_token);

    println!("Token: '{}' is valid: {}", auth_token, is_valid);
}
```

---

### Solution to Exercise 3
```rust
fn inject_content_length(headers: &mut String, length: usize) {
    headers.push_str("\nContent-Length: ");
    headers.push_str(&length.to_string());
}

fn main() {
    let mut request_headers = String::from("POST /submit HTTP/1.1\nHost: api.local");

    inject_content_length(&mut request_headers, 2048);

    println!("Final Request Headers:\n{}", request_headers);
}
```
