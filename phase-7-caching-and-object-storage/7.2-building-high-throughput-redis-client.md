## Concept

In relational databases (like PostgreSQL), each query takes over a TCP connection until it finishes, requiring a pool of 20–50 connections.

In Redis, because operations execute in microseconds, high-throughput Rust drivers (like `redis-rs` or `fred`) use **Connection Multiplexing** and **Pipelining**.

```
                Multiplexed Connection (1 Single TCP Socket)
  Async Task 1: GET k1 ────┐
  Async Task 2: SET k2 v2 ─┼──► [ Tokio Multiplexing Engine ] ──► Redis Server (1 TCP Socket)
  Async Task 3: INCR cnt ──┘
```

---

### 1. Connection Multiplexing vs Pipelining

1. **Multiplexing (`MultiplexedConnection`)**: Multiple concurrent Tokio tasks clone the same `MultiplexedConnection` handle. The driver pipelines requests onto a single TCP stream and matches incoming RESP responses to the appropriate awaiting task using unique request IDs.
2. **Pipelining (`redis::pipe()`)**: Sends a batch of 100 commands in a single network frame, cutting 100 Round-Trip Times (RTTs) down to **1 single RTT**:

```rust
let mut pipe = redis::pipe();
for i in 0..100 {
    pipe.set(format!("key:{}", i), i).ignore();
}
// 100 commands sent in 1 single TCP write!
pipe.query_async(&mut conn).await?;
```

---

### 2. High-Performance Redis Data Structures

| Data Structure | Rust Command | Real-World Use Case |
| :--- | :--- | :--- |
| **String / Bytes** | `GET`, `SETEX` | Cached JSON payloads, session tokens |
| **Hash (`HSET`, `HGET`)** | `hset`, `hgetall` | User profile objects without full JSON re-serialization |
| **Sorted Set (`ZSET`)** | `zadd`, `zrange` | Real-time gaming leaderboards, sliding-window rate limiters |
| **Streams (`XADD`, `XREAD`)** | `xadd`, `xreadgroup`| Distributed event logs, Kafka-like consumer groups |

---

### 3. Async Pub/Sub Mechanics

Pub/Sub allows Redis to act as an instant message bus:
- **Publishing (`PUBLISH channel msg`)**: Can be performed on any standard multiplexed connection.
- **Subscribing (`SUBSCRIBE channel`)**: **Consumes the entire TCP connection**. Once subscribed, a connection can only listen for incoming channel events or issue `SUBSCRIBE`/`UNSUBSCRIBE` commands.

---

## Why It Matters in Systems Programming

1. **Zero TCP Socket Exhaustion**: Using a single multiplexed connection to handle $100,000$ queries/sec prevents OS ephemeral port exhaustion (`TIME_WAIT`).
2. **Sub-Millisecond Sliding Window Rate Limiting**: Implementing a rate limiter using Sorted Sets (`ZREMRANGEBYSCORE` + `ZADD` + `ZCARD`) allows atomic, distributed rate limiting across 50 API nodes.
3. **Pipelining Cuts Network Overhead**: On a network with 2ms latency, running 500 individual queries sequentially takes $1,000\text{ms}$ (1 second). With pipelining, all 500 queries finish in **$2\text{ms}$**.

---

## Real-World Analogy

- **Sequential Queries** are like sending 50 individual postcards to a friend in another city: each postcard takes 3 days to travel and 3 days for a reply (300 days total).
- **Pipelining** is putting all 50 letters into a single envelope and mailing them together: your friend reads all 50 at once and replies in a single return envelope (3 days total).

## Complete, Compilable Code Example

Below is a complete, production-ready Rust client demonstrating Redis connection multiplexing, pipelined batch operations, and sliding-window rate limiting:

```rust
use std::collections::BTreeMap;
use std::sync::{Arc, Mutex};
use std::time::{Duration, Instant, SystemTime, UNIX_EPOCH};

// ============================================================================
// 1. In-Memory Mock of High-Throughput Redis Engine
// ============================================================================

pub struct MockRedisServer {
    strings: Mutex<BTreeMap<String, (Vec<u8>, Option<Instant>)>>, // Key -> (Val, TTL)
    sorted_sets: Mutex<BTreeMap<String, BTreeMap<i64, String>>>,   // Key -> (Score -> Member)
}

impl MockRedisServer {
    pub fn new() -> Self {
        Self {
            strings: Mutex::new(BTreeMap::new()),
            sorted_sets: Mutex::new(BTreeMap::new()),
        }
    }

    /// SET with Expiration (SETEX)
    pub fn setex(&self, key: &str, val: &[u8], ttl: Duration) {
        let mut map = self.strings.lock().unwrap();
        let expiry = Instant::now() + ttl;
        map.insert(key.to_string(), (val.to_vec(), Some(expiry)));
    }

    /// GET with TTL Eviction check
    pub fn get(&self, key: &str) -> Option<Vec<u8>> {
        let mut map = self.strings.lock().unwrap();
        if let Some((val, expiry_opt)) = map.get(key) {
            if let Some(expiry) = expiry_opt {
                if Instant::now() > *expiry {
                    map.remove(key); // Lazy expiration
                    return None;
                }
            }
            return Some(val.clone());
        }
        None
    }

    /// Atomic Sliding-Window Rate Limiter using Sorted Sets
    pub fn check_rate_limit(
        &self,
        user_id: &str,
        max_requests: usize,
        window: Duration,
    ) -> Result<bool, &'static str> {
        let now_ms = SystemTime::now()
            .duration_since(UNIX_EPOCH)
            .unwrap()
            .as_millis() as i64;
        let window_start = now_ms - window.as_millis() as i64;
        let zset_key = format!("ratelimit:{}", user_id);

        let mut zsets = self.sorted_sets.lock().unwrap();
        let set = zsets.entry(zset_key).or_default();

        // 1. Evict timestamps older than current window (ZREMRANGEBYSCORE)
        set.retain(|&score, _| score >= window_start);

        // 2. Check current request count (ZCARD)
        if set.len() >= max_requests {
            return Ok(false); // Rate limited!
        }

        // 3. Add current timestamp (ZADD)
        set.insert(now_ms, format!("req_{}", now_ms));
        Ok(true) // Allowed!
    }
}

// ============================================================================
// 2. High-Level Redis Client & Pipeline Simulator
// ============================================================================

#[derive(Clone)]
pub struct HighThroughputRedisClient {
    server: Arc<MockRedisServer>,
}

impl HighThroughputRedisClient {
    pub fn new(server: Arc<MockRedisServer>) -> Self {
        Self { server }
    }

    /// Pipelined batch set execution (simulates single network round trip)
    pub async fn execute_batch_set(&self, items: Vec<(String, String, Duration)>) {
        println!("  [PIPELINE] Dispatching batch of {} commands in 1 network frame...", items.len());
        let start = Instant::now();

        for (k, v, ttl) in items {
            self.server.setex(&k, v.as_bytes(), ttl);
        }

        println!("  [PIPELINE] Batch completed in {:?}", start.elapsed());
    }
}

// ============================================================================
// 3. Verification & Concurrency Test
// ============================================================================

#[tokio::main]
async fn main() {
    println!("=== 1. Testing Multiplexed Redis Pipelining ===");
    let server = Arc::new(MockRedisServer::new());
    let client = HighThroughputRedisClient::new(server.clone());

    // Generate 1000 cache items
    let mut batch = Vec::new();
    for i in 1..=1000 {
        batch.push((
            format!("user:session:{}", i),
            format!("token_abc123_{}", i),
            Duration::from_secs(3600),
        ));
    }

    client.execute_batch_set(batch).await;

    // Verify key exists
    let val = server.get("user:session:42").unwrap();
    println!("Extracted user:session:42 -> {}\n", String::from_utf8_lossy(&val));

    println!("=== 2. Testing Distributed Sliding-Window Rate Limiter ===");
    println!("Rate Limit Rule: Max 5 requests per 500ms window");

    let user = "usr_client_88";
    for req_num in 1..=8 {
        let allowed = server.check_rate_limit(user, 5, Duration::from_millis(500)).unwrap();
        println!(
            "  Request #{:<2} -> {}",
            req_num,
            if allowed { "✅ ALLOWED (200 OK)" } else { "❌ BLOCKED (429 Too Many Requests)" }
        );
        tokio::time::sleep(Duration::from_millis(50)).await;
    }

    println!("\nSleeping 550ms for window to slide...");
    tokio::time::sleep(Duration::from_millis(550)).await;

    let allowed_after_slide = server.check_rate_limit(user, 5, Duration::from_millis(500)).unwrap();
    println!("  Request after reset -> {}", if allowed_after_slide { "✅ ALLOWED (200 OK)" } else { "❌ BLOCKED" });
}
```

## Common Pitfalls & Compiler Errors

### 1. Executing Regular Commands on a Subscribed PubSub Connection
Once a Redis connection issues `SUBSCRIBE`, the server switches the connection into subscriber mode. Attempting to run `GET` or `SET` on that connection produces an error:
```
ERR only (P)SUBSCRIBE / (P)UNSUBSCRIBE / PING / QUIT allowed in this context
```
**Fix**: Always dedicate a separate connection for Pub/Sub listeners.

### 2. Unbounded Memory Growth from Missing TTLs
Inserting millions of cache keys without setting an expiration (`EXPIRE` or `SETEX`) will eventually consume all available RAM on the Redis instance, triggering `OOM command not allowed when used memory > 'maxmemory'`.

## Complete Solutions to Exercises

### Solution 1: Hash DTO Caching

```rust
// Using redis-rs:
pub async fn cache_user_profile(
    conn: &mut redis::aio::MultiplexedConnection,
    user_id: u64,
    fields: &[(&str, &str)],
) -> redis::RedisResult<()> {
    let key = format!("user:profile:{}", user_id);
    let mut pipe = redis::pipe();
    
    for &(field, val) in fields {
        pipe.hset(&key, field, val).ignore();
    }
    pipe.expire(&key, 3600).ignore();

    pipe.query_async(conn).await
}
```

### Solution 2: Sliding Window vs Fixed Window
In a fixed window (e.g. 100 requests per minute resetting at :00), a client could send 100 requests at 11:59:59 and another 100 requests at 12:00:01 (200 requests within 2 seconds), causing traffic spikes. A **sliding window** continuously checks the last 60 seconds rolling window, preventing burst boundary bypasses.
