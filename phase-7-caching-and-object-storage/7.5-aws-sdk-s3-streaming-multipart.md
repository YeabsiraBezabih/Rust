## Concept

When uploading multi-gigabyte datasets, video files, or database backups to S3, sending the file in a single standard HTTP `PUT` request is risky and inefficient:
1. If the network connection drops at 99%, the entire upload is lost and must restart from byte 0.
2. Single-stream uploads cannot saturate 10Gbps/100Gbps network interfaces.

The **S3 Multipart Upload Protocol** splits large files into independent 5MB–50MB chunks uploaded concurrently in parallel worker threads, with automatic individual part retries.

```
                  Parallel Multipart Upload Pipeline (1GB Video File)
┌────────────────────────────────────────────────────────────────────────┐
│  Local Disk File (1GB) ──► Split into 20 x 50MB Chunks                 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
       ┌────────────────────────────┼────────────────────────────┐
       ▼ (Tokio Task 1)             ▼ (Tokio Task 2)             ▼ (Tokio Task 20)
┌──────────────┐             ┌──────────────┐             ┌──────────────┐
│ UploadPart 1 │             │ UploadPart 2 │             │ UploadPart 20│
│ (50MB) ──► S3│             │ (50MB) ──► S3│             │ (50MB) ──► S3│
└──────┬───────┘             └──────┬───────┘             └──────┬───────┘
       │ ETag 1                     │ ETag 2                     │ ETag 20
       └────────────────────────────┼────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  CompleteMultipartUpload: Submits sorted list of 20 (PartNumber, ETag) │
│  S3 assembles final 1GB object atomically!                             │
└────────────────────────────────────────────────────────────────────────┘
```

### 1. Presigned URLs: Offloading Backend Bandwidth

In traditional architectures, clients upload large files to your backend API server, and your backend uploads them to S3. This wastes $2\times$ backend CPU and bandwidth!

With **Presigned URLs**:
1. Client asks backend: `"I want to upload avatar.png"`.
2. Backend generates a cryptographically signed S3 `PUT` URL valid for 15 minutes.
3. Browser/Mobile app uploads the file **directly to S3**.
4. Your backend server CPU and network usage remain at **0%**.

```rust
use aws_sdk_s3::presigning::PresigningConfig;
use std::time::Duration;

// Generate presigned PUT URL for direct client upload
let presigned_req = client
    .put_object()
    .bucket("user-uploads")
    .key("avatars/user_101.png")
    .presigned(PresigningConfig::expires_in(Duration::from_secs(900))?)
    .await?;

println!("Direct Upload URL: {}", presigned_req.uri());
```

### 2. The Multipart Upload State Machine

1. **`create_multipart_upload`**: Initiates the session and returns an `upload_id`.
2. **`upload_part`**: Concurrently uploads slices. Minimum part size is **5MB** (except the final part).
3. **`complete_multipart_upload`**: Submits the completed parts array. Parts **MUST be sorted in ascending order by `part_number`**.
4. **`abort_multipart_upload`**: If any part fails unrecoverably, abort to avoid being billed for dangling abandoned parts on AWS.

---

## Why It Matters in Systems Programming

1. **Max Throughput via Parallel Streams**: Uploading 10 parts simultaneously over 10 parallel TCP connections achieves full line-rate saturation (up to $10\text{Gbps}$).
2. **Resilience to Network Drops**: If part #14 of 100 fails due to a packet drop, you retry only that single 10MB chunk instead of restarting the entire 1GB upload.
3. **Zero Backend Bottlenecks**: Presigned URLs allow a single tiny $5/mo VPS to handle millions of user media uploads without spending any backend network bandwidth.

---

## Real-World Analogy

- **Single PUT Upload** is like transporting a 100-ton bridge across the country in one single giant truck: if one tire blows out on the highway, the entire shipment is stuck.
- **Multipart Upload** is disassembling the bridge into 20 numbered shipping crates, putting each crate onto a separate delivery van traveling simultaneously, and re-bolting the bridge together at the destination.
- **Presigned URL** is giving the customer a temporary VIP security badge directly to the warehouse loading dock so you don't have to carry their boxes for them.

## Complete, Compilable Code Example

Below is a complete, working async **Multipart Upload Coordinator Engine** in pure Rust demonstrating chunk slicing, concurrent task scheduling, and atomic assembly:

```rust
use std::collections::BTreeMap;
use std::sync::{Arc, Mutex};
use std::time::Duration;
use tokio::task::JoinSet;

// ============================================================================
// 1. Mock S3 Multipart Backend
// ============================================================================

#[derive(Debug, Clone)]
pub struct UploadedPart {
    pub part_number: i32,
    pub etag: String,
    pub data_len: usize,
}

pub struct MockS3MultipartServer {
    active_uploads: Mutex<BTreeMap<String, Vec<UploadedPart>>>, // UploadId -> Parts
}

impl MockS3MultipartServer {
    pub fn new() -> Self {
        Self {
            active_uploads: Mutex::new(BTreeMap::new()),
        }
    }

    pub fn create_multipart_upload(&self, key: &str) -> String {
        let upload_id = format!("upload_{}_{}", key.replace('/', "_"), 1001);
        self.active_uploads
            .lock()
            .unwrap()
            .insert(upload_id.clone(), Vec::new());
        upload_id
    }

    pub fn upload_part(&self, upload_id: &str, part_number: i32, data: &[u8]) -> Result<String, &'static str> {
        let mut map = self.active_uploads.lock().unwrap();
        let parts = map.get_mut(upload_id).ok_or("NoSuchUpload")?;

        let etag = format!("\"etag_part_{}_{:x}\"", part_number, data.len());
        parts.push(UploadedPart {
            part_number,
            etag: etag.clone(),
            data_len: data.len(),
        });

        Ok(etag)
    }

    pub fn complete_multipart_upload(
        &self,
        upload_id: &str,
        mut completed_parts: Vec<UploadedPart>,
    ) -> Result<String, &'static str> {
        let mut map = self.active_uploads.lock().unwrap();
        let _server_parts = map.remove(upload_id).ok_or("NoSuchUpload")?;

        // S3 RULE: Completed parts must be sorted strictly in ascending part_number order!
        completed_parts.sort_by_key(|p| p.part_number);

        let total_bytes: usize = completed_parts.iter().map(|p| p.data_len).sum();
        let final_etag = format!("\"{}-{}\"", "3858f62230ac3c915f300c664312c63f", completed_parts.len());

        println!(
            "  [S3 BACKEND] Multipart Upload Completed! Assembled {} parts (Total: {} bytes)",
            completed_parts.len(),
            total_bytes
        );

        Ok(final_etag)
    }
}

// ============================================================================
// 2. High-Performance Parallel Multipart Uploader
// ============================================================================

pub struct ParallelUploader {
    server: Arc<MockS3MultipartServer>,
}

impl ParallelUploader {
    pub fn new(server: Arc<MockS3MultipartServer>) -> Self {
        Self { server }
    }

    /// Slices raw bytes into 5MB chunks and uploads concurrently across Tokio tasks
    pub async fn upload_large_blob(
        &self,
        key: &str,
        payload: &[u8],
        chunk_size: usize,
    ) -> Result<String, &'static str> {
        let upload_id = self.server.create_multipart_upload(key);
        println!("Initiated Multipart Upload for '{}' -> UploadId: {}", key, upload_id);

        let chunks: Vec<Vec<u8>> = payload.chunks(chunk_size).map(|c| c.to_vec()).collect();
        let total_chunks = chunks.len();
        println!("Split payload into {} chunks (Chunk Size: {} bytes)", total_chunks, chunk_size);

        let mut join_set = JoinSet::new();

        for (idx, chunk) in chunks.into_iter().enumerate() {
            let part_number = (idx + 1) as i32;
            let srv = Arc::clone(&self.server);
            let uid = upload_id.clone();

            join_set.spawn(async move {
                // Simulate network transfer latency per part
                tokio::time::sleep(Duration::from_millis(30)).await;
                let etag = srv.upload_part(&uid, part_number, &chunk)?;
                println!("    Finished uploading Part #{} -> ETag: {}", part_number, etag);
                Ok::<UploadedPart, &'static str>(UploadedPart {
                    part_number,
                    etag,
                    data_len: chunk.len(),
                })
            });
        }

        let mut completed_parts = Vec::with_capacity(total_chunks);
        while let Some(res) = join_set.join_next().await {
            match res {
                Ok(Ok(part)) => completed_parts.push(part),
                _ => return Err("One or more part uploads failed"),
            }
        }

        // Finalize assembly
        let final_etag = self.server.complete_multipart_upload(&upload_id, completed_parts)?;
        Ok(final_etag)
    }
}

// ============================================================================
// 3. Verification & Execution
// ============================================================================

#[tokio::main]
async fn main() {
    println!("=== Testing Parallel S3 Multipart Upload Engine ===");
    let server = Arc::new(MockS3MultipartServer::new());
    let uploader = ParallelUploader::new(server.clone());

    // Generate 25MB simulated dataset (25 * 1024 * 1024 bytes)
    let payload = vec![0xFE; 25 * 1024 * 1024];
    let chunk_size = 5 * 1024 * 1024; // 5MB chunks (Standard S3 minimum part size)

    let final_etag = uploader
        .upload_large_blob("backups/2026/database_dump.tar.gz", &payload, chunk_size)
        .await
        .unwrap();

    println!("\nSuccess! Final Object ETag: {}", final_etag);
}
```

## Common Pitfalls & Compiler Errors

### 1. Uploading Chunks Smaller than 5MB
AWS S3 returns an `EntityTooSmall` error if any part (except the very last part) is less than $5\text{MB}$ ($5,242,880\text{ bytes}$). Always ensure chunk buffers are at least 5MB.

### 2. Unsorted Part Numbers in `CompleteMultipartUpload`
If you submit completed parts in arbitrary order (e.g. `[Part 2, Part 1, Part 3]`), S3 rejects the completion request with `InvalidPartOrder`. Always sort completed parts by `part_number` ascending before submitting.
