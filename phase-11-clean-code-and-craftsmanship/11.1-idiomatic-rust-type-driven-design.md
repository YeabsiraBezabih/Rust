## Concept

In object-oriented languages (like Java, Python, or C#), "Clean Code" is often associated with inheritance hierarchies, deep abstraction layers, getter/setter boilerplate, and runtime validation checks scattered across every function.

In Rust, **Clean Code** means **Type-Driven Design**:
1. **Make Illegal States Unrepresentable**: Leverage algebraic data types (`enum` and `struct`) so the compiler physically prevents invalid states from compiling.
2. **Parse, Don't Validate**: Instead of checking boolean flags repeatedly throughout your codebase (`if user.is_verified()`), parse raw, untrusted data at the system boundary into a strongly-typed domain struct that guarantees validity by construction.
3. **The Newtype Pattern**: Wrap primitive types (e.g. `u64`, `String`) into zero-cost domain types (e.g. `UserId`, `EmailAddress`, `Dollars`) to completely eliminate **Primitive Obsession**.

```
                        The "Parse, Don't Validate" Pipeline
┌──────────────────────────────────────┐
│  Untrusted Input: raw string         │
│  "alice@company.com"                 │
└──────────────────┬───────────────────┘
                   │
                   │ 1. Parse at system boundary: `EmailAddress::parse(raw_str)`
                   │    - Checks format, domain, '@' symbol ONCE.
                   ▼
┌──────────────────────────────────────┐
│  Domain Representation: EmailAddress │ ◄── 100% Guaranteed Valid!
└──────────────────┬───────────────────┘     (Cannot be instantiated with invalid email)
                   │
                   ▼
┌──────────────────────────────────────┐
│  Internal Business Functions         │
│  fn send_invoice(email: EmailAddress)│ ◄── Zero runtime validation checks needed!
└──────────────────────────────────────┘     Zero `if is_valid` boilerplate!
```

---

### 1. Primitive Obsession vs The Newtype Pattern

#### The Anti-Pattern (Primitive Obsession):
```rust
// Bug waiting to happen: easily pass account_id to user_id parameter!
fn transfer_funds(source_user_id: u64, target_user_id: u64, amount: f64) { ... }

// Accidentally swapped arguments! Compiler cannot help:
transfer_funds(target_id, source_id, amount); 
```

#### The Clean Code Solution (Newtypes):
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct UserId(pub u64);

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub struct MoneyCents(pub i64);

fn transfer_funds(source: UserId, target: UserId, amount: MoneyCents) { ... }

// If you accidentally pass an AccountId or integer, the Rust compiler fails immediately!
```

Because Newtypes are single-field tuple structs, **the Rust compiler completely optimizes them away into raw primitive machine integers at runtime (Zero Cost)**.

---

### 2. Making Illegal States Unrepresentable

#### The Anti-Pattern (Field Explosion & Invalid Combinations):
```rust
// A user might have is_verified = true but verification_token = None, or vice-versa!
struct UserBad {
    id: u64,
    email: String,
    is_verified: bool,
    verification_token: Option<String>,
    verified_at: Option<chrono::DateTime<chrono::Utc>>,
}
```

#### The Clean Code Solution (Algebraic Data Types):
```rust
pub enum VerificationStatus {
    Unverified { token: String, expires_at: chrono::DateTime<chrono::Utc> },
    Verified { verified_at: chrono::DateTime<chrono::Utc> },
}

pub struct User {
    pub id: UserId,
    pub email: EmailAddress,
    pub status: VerificationStatus, // Invalid combinations are physically impossible!
}
```

---

## Why It Matters in Systems Programming

1. **Eliminates Entire Classes of Runtime Bugs**: By replacing runtime `if` conditions with type-system constraints, invalid states are caught at compile time.
2. **Self-Documenting Code**: Function signatures like `fn ship(order: PaidOrder)` clearly state their exact preconditions without requiring hundreds of lines of docstrings or defensive assertions.
3. **Zero Performance Penalty**: Unlike dynamic language validations that burn CPU cycles on every method call, Rust's type-level abstractions disappear during monomorphization.

---

## Real-World Analogy

- **Validation (OOP style)** is like a passport officer standing at every single doorway inside an airport, asking to see your passport, boarding pass, and luggage receipt at the duty-free shop, the restroom, and the gate.
- **Type-Driven Parsing (Rust style)** is scanning your passport once at the security gate to enter the "International Departures Terminal" (**Type Transformation**): once inside that terminal, you are physically guaranteed to be an authenticated international traveler.

## Complete, Compilable Code Example

Below is a complete, self-contained implementation demonstrating **Type-Driven Design, the Newtype Pattern, and Non-Empty Collections** in pure Rust:

```rust
use std::fmt;

// ============================================================================
// 1. Zero-Cost Newtypes (Preventing Primitive Obsession)
// ============================================================================

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct AccountId(pub u64);

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub struct Cents(pub i64);

impl Cents {
    pub fn from_dollars(dollars: f64) -> Result<Self, &'static str> {
        if dollars < 0.0 {
            return Err("Amount cannot be negative");
        }
        Ok(Self((dollars * 100.0).round() as i64))
    }

    pub fn to_dollars(&self) -> f64 {
        self.0 as f64 / 100.0
    }
}

// ============================================================================
// 2. Parse, Don't Validate: Validated Domain Value Objects
// ============================================================================

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct EmailAddress(String);

impl EmailAddress {
    /// The ONLY way to create an EmailAddress is via parsing at the boundary!
    pub fn parse(raw: &str) -> Result<Self, &'static str> {
        let trimmed = raw.trim();
        if trimmed.is_empty() {
            return Err("Email cannot be empty");
        }

        let parts: Vec<&str> = trimmed.split('@').collect();
        if parts.len() != 2 || parts[0].is_empty() || parts[1].is_empty() {
            return Err("Email must contain exactly one '@' with local and domain parts");
        }

        if !parts[1].contains('.') {
            return Err("Email domain must contain a '.' TLD");
        }

        Ok(Self(trimmed.to_lowercase()))
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl fmt::Display for EmailAddress {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}", self.0)
    }
}

// ============================================================================
// 3. Making Illegal States Unrepresentable (NonEmptyList)
// ============================================================================

/// A list guaranteed by the type system to have at least ONE element!
#[derive(Debug, Clone)]
pub struct NonEmptyVec<T> {
    head: T,
    tail: Vec<T>,
}

impl<T> NonEmptyVec<T> {
    pub fn new(head: T, tail: Vec<T>) -> Self {
        Self { head, tail }
    }

    pub fn from_vec(mut vec: Vec<T>) -> Option<Self> {
        if vec.is_empty() {
            None
        } else {
            let head = vec.remove(0);
            Some(Self { head, tail: vec })
        }
    }

    /// Guaranteed to never panic because head always exists!
    pub fn first(&self) -> &T {
        &self.head
    }

    pub fn len(&self) -> usize {
        1 + self.tail.len()
    }
}

// ============================================================================
// 4. Domain Service (Zero Runtime Validation Boilerplate!)
// ============================================================================

pub struct Invoice {
    pub id: u64,
    pub recipient: EmailAddress, // Guaranteed valid email
    pub total: Cents,            // Guaranteed valid monetary value
    pub line_items: NonEmptyVec<String>, // Guaranteed to have at least 1 item!
}

pub fn generate_invoice(
    id: u64,
    recipient: EmailAddress,
    total: Cents,
    line_items: NonEmptyVec<String>,
) -> Invoice {
    // Look at this function: ZERO `if total < 0`, ZERO `if email.is_valid()`, ZERO `if items.is_empty()`!
    // The type system already enforced all invariants before execution arrived here!
    Invoice {
        id,
        recipient,
        total,
        line_items,
    }
}

// ============================================================================
// 5. Verification & Execution
// ============================================================================

fn main() {
    println!("=== 1. Testing 'Parse, Don't Validate' Email Parsing ===");
    let valid_email = EmailAddress::parse("  Satoshi@Bitcoin.ORG  ").unwrap();
    println!("Parsed Email: {}", valid_email);

    let invalid_email_res = EmailAddress::parse("invalid-email-address");
    println!("Invalid Email Parse Result: {:?}\n", invalid_email_res);
    assert!(invalid_email_res.is_err());

    println!("=== 2. Testing NonEmptyVec Guarantee ===");
    let items_raw = vec!["Server Hosting (1 Month)".to_string(), "Dedicated IP".to_string()];
    let non_empty_items = NonEmptyVec::from_vec(items_raw).expect("Must have items");

    println!("Non-Empty Items Count: {}", non_empty_items.len());
    println!("First Item (Guaranteed Safe): {}\n", non_empty_items.first());

    println!("=== 3. Clean Domain Invoice Generation ===");
    let invoice = generate_invoice(
        1001,
        valid_email,
        Cents::from_dollars(149.99).unwrap(),
        non_empty_items,
    );

    println!("Successfully generated Invoice #{}", invoice.id);
    println!("  Recipient: {}", invoice.recipient);
    println!("  Total:     ${:.2}", invoice.total.to_dollars());
    println!("  Items:     {} line items", invoice.line_items.len());
}
```

## Common Pitfalls & Compiler Errors

### 1. Leaking Raw Value Constructors
If you provide a `pub struct EmailAddress(pub String);` with a public inner field, external callers can bypass your `parse()` constructor and write `EmailAddress("garbage".to_string())`.
**Fix**: Keep the inner field private (`pub struct EmailAddress(String);`) and provide only public constructor functions that enforce validation invariants.

### 2. Overusing `Option` and `bool` Flags
Adding multiple `Option` fields to a single struct to represent different states leads to exponential invalid combinations.
**Fix**: Consolidate mutually exclusive states into an `enum`.

## Complete Solutions to Exercises

### Solution 1: Percentage Value Object

```rust
#[derive(Debug, Clone, Copy, PartialEq, PartialOrd)]
pub struct Percentage(f64);

impl Percentage {
    pub fn from_f64(val: f64) -> Result<Self, &'static str> {
        if (0.0..=100.0).contains(&val) {
            Ok(Self(val))
        } else {
            Err("Percentage must be strictly between 0.0 and 100.0")
        }
    }

    pub fn value(&self) -> f64 {
        self.0
    }
}
```

### Solution 2: TaskState Enum

```rust
pub enum TaskState {
    Pending,
    Running { started_at: std::time::Instant },
    Failed { error: String, retry_count: u32 },
    Completed { duration: std::time::Duration },
}
```
