## Concept

Many classic GoF design patterns (like Abstract Factory, Decorator, or Visitor) require heavy inheritance and dynamic pointer indirection in OOP languages.

In Rust, design patterns leverage **Ownership**, **Zero-Sized Marker Types (ZST)**, and **RAII (Resource Acquisition Is Initialization)**:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        The Type-State Pattern State Machine            │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   [ Order<Draft> ] ─── .pay(card) ───► [ Order<Paid> ]                 │
│         │                                    │                         │
│         │ (Invalid transition!)              │ .ship(tracking_number)  │
│         X .ship() FAILS COMPILATION!         ▼                         │
│                                        [ Order<Shipped> ]              │
│                                                                        │
│   ◄── State transitions consume `self` by value! Old state destroyed! ──►
└────────────────────────────────────────────────────────────────────────┘
```

---

### 1. The Type-State Pattern

In traditional code, an order might have methods like `ship()` that check `if !self.is_paid { return Err("Not paid"); }`. If a developer forgets the check, the bug triggers at runtime in production.

In the **Type-State Pattern**:
1. Different states are represented as zero-sized types (e.g. `Draft`, `Paid`, `Shipped`).
2. The core struct is generic over its state: `struct Order<State> { ... }`.
3. Methods are implemented **only for specific states**:
   - `Order<Draft>::pay(self) -> Order<Paid>`
   - `Order<Paid>::ship(self, tracking: &str) -> Order<Shipped>`
4. **Attempting to call `ship()` on an `Order<Draft>` fails at compile time!**

Because marker types are zero-sized, the compiled machine code is identical to a raw struct with **$0\text{ bytes}$ of memory overhead**.

---

### 2. Type-Safe Compile-Time Builder Pattern

Standard builders check that all mandatory fields are present at runtime when `.build()` is called, returning `Result<T, Error>`.

A **Type-State Builder** ensures that `.build()` **only exists in the type system once all required fields have been set**, converting runtime errors into compile-time proofs!

---

### 3. The RAII Custom Guard Pattern

In Rust, the **RAII Guard Pattern** ties cleanup logic to variable scope via the `Drop` and `Deref` traits:
- When the guard is created, it acquires a resource or switches state.
- When the guard goes out of scope (even during early returns or panics), its `drop()` method executes automatically.

---

## Why It Matters in Systems Programming

1. **Compile-Time Protocol Verification**: Ensure network sockets or transaction sessions follow strict RFC sequences (e.g. `Handshake` ➔ `Authenticated` ➔ `Streaming`) without runtime branch checks.
2. **Move Semantics Prevent Use-After-Transition**: Because transition methods take `self` by value, the previous state is moved and destroyed—preventing double-execution bugs.
3. **Zero Runtime Overhead**: All state validation happens inside the compiler's type checker; zero CPU cycles are spent checking state flags at runtime.

---

## Real-World Analogy

- **Runtime State Checking** is a train conductor walking down the aisle checking every passenger's ticket every 10 minutes.
- **The Type-State Pattern** is a physical turnstile gate: you cannot step onto the departure platform without a scanned ticket; once you board the train, your presence in the seat is physical proof that you have a valid ticket.

## Complete, Compilable Code Example

Below is a complete, self-contained implementation demonstrating the **Type-State Pattern**, a **Type-Safe Builder**, and an **RAII Scope Timer Guard** in pure Rust:

```rust
use std::marker::PhantomData;
use std::time::Instant;

// ============================================================================
// 1. Zero-Sized Type-State Markers
// ============================================================================

pub struct Draft;
pub struct Paid {
    pub transaction_id: String,
}
pub struct Shipped {
    pub tracking_number: String,
}

// ============================================================================
// 2. Type-State FSM Entity
// ============================================================================

pub struct Order<State> {
    pub id: u64,
    pub customer_email: String,
    pub amount_cents: i64,
    pub state: State,
}

impl Order<Draft> {
    /// Create new Draft order
    pub fn new(id: u64, customer_email: &str, amount_cents: i64) -> Self {
        Self {
            id,
            customer_email: customer_email.to_string(),
            amount_cents,
            state: Draft,
        }
    }

    /// Transition from Draft -> Paid (Consumes self by value!)
    pub fn pay(self, transaction_id: &str) -> Order<Paid> {
        println!("  [TypeState] Order #{} transitioned: Draft -> Paid (Tx: {})", self.id, transaction_id);
        Order {
            id: self.id,
            customer_email: self.customer_email,
            amount_cents: self.amount_cents,
            state: Paid {
                transaction_id: transaction_id.to_string(),
            },
        }
    }
}

impl Order<Paid> {
    /// Transition from Paid -> Shipped (Consumes self by value!)
    pub fn ship(self, tracking_number: &str) -> Order<Shipped> {
        println!("  [TypeState] Order #{} transitioned: Paid -> Shipped (Tracking: {})", self.id, tracking_number);
        Order {
            id: self.id,
            customer_email: self.customer_email,
            amount_cents: self.amount_cents,
            state: Shipped {
                tracking_number: tracking_number.to_string(),
            },
        }
    }
}

// Notice: `ship()` is NOT implemented for `Order<Draft>`!
// Calling `draft_order.ship()` will not even compile!

// ============================================================================
// 3. Type-Safe Compile-Time Builder Pattern
// ============================================================================

pub struct NoHost;
pub struct Host(String);

pub struct NoPort;
pub struct Port(u16);

pub struct ServerConfig {
    pub host: String,
    pub port: u16,
    pub max_connections: usize,
}

pub struct ServerConfigBuilder<H, P> {
    host: H,
    port: P,
    max_connections: usize,
}

impl ServerConfigBuilder<NoHost, NoPort> {
    pub fn new() -> Self {
        Self {
            host: NoHost,
            port: NoPort,
            max_connections: 100, // Default optional value
        }
    }
}

impl<P> ServerConfigBuilder<NoHost, P> {
    pub fn host(self, host: &str) -> ServerConfigBuilder<Host, P> {
        ServerConfigBuilder {
            host: Host(host.to_string()),
            port: self.port,
            max_connections: self.max_connections,
        }
    }
}

impl<H> ServerConfigBuilder<H, NoPort> {
    pub fn port(self, port: u16) -> ServerConfigBuilder<H, Port> {
        ServerConfigBuilder {
            host: self.host,
            port: Port(port),
            max_connections: self.max_connections,
        }
    }
}

// `.build()` is ONLY available when BOTH Host and Port are provided!
impl ServerConfigBuilder<Host, Port> {
    pub fn max_connections(mut self, max: usize) -> Self {
        self.max_connections = max;
        self
    }

    pub fn build(self) -> ServerConfig {
        ServerConfig {
            host: self.host.0,
            port: self.port.0,
            max_connections: self.max_connections,
        }
    }
}

// ============================================================================
// 4. RAII Scope Execution Timer Guard
// ============================================================================

pub struct ScopeTimer {
    name: &'static str,
    start: Instant,
}

impl ScopeTimer {
    pub fn new(name: &'static str) -> Self {
        Self {
            name,
            start: Instant::now(),
        }
    }
}

impl Drop for ScopeTimer {
    fn drop(&mut self) {
        println!("  [RAII Timer] Block '{}' completed in {:?}", self.name, self.start.elapsed());
    }
}

// ============================================================================
// 5. Verification & Execution
// ============================================================================

fn main() {
    println!("=== 1. Testing Type-State FSM Lifecycle ===");
    let _timer = ScopeTimer::new("Full Lifecycle Demo");

    let draft_order = Order::new(101, "alice@company.com", 25_000);
    println!("Created Draft Order #{}", draft_order.id);

    // Pay order (Draft -> Paid)
    let paid_order = draft_order.pay("tx_stripe_98412");

    // Ship order (Paid -> Shipped)
    let shipped_order = paid_order.ship("DHL-TRACK-9941");
    println!("Final Order Tracking: {}", shipped_order.state.tracking_number);

    println!("\n=== 2. Testing Type-Safe Compile-Time Builder ===");
    let config = ServerConfigBuilder::new()
        .host("127.0.0.1")
        .port(8080)
        .max_connections(500)
        .build(); // Guaranteed to never fail at runtime!

    println!("Built Server Config: {}:{} (Max Conn: {})", config.host, config.port, config.max_connections);
}
```

## Common Pitfalls & Compiler Errors

### 1. Attempting to Reuse Old State Variables
Because Type-State transition methods consume `self` by value, the original variable is moved:
```rust
let paid = draft.pay("tx_123");
draft.pay("tx_456"); // error[E0382]: use of moved value: `draft`
```
This compiler error is a **feature**: it physically prevents double-spending or processing the same draft twice.

### 2. Generics Explosion
If a struct has 10 independent state dimensions, using type-states for all 10 can create overly complex generic signatures.
**Fix**: Use Type-States for the core sequential lifecycle, and standard builder pattern for independent attributes.

## Complete Solutions to Exercises

### Solution 2: Cancelled State Transition

```rust
pub struct Cancelled {
    pub reason: String,
}

impl Order<Draft> {
    pub fn cancel(self, reason: &str) -> Order<Cancelled> {
        Order {
            id: self.id,
            customer_email: self.customer_email,
            amount_cents: self.amount_cents,
            state: Cancelled { reason: reason.to_string() },
        }
    }
}

impl Order<Paid> {
    pub fn cancel(self, reason: &str) -> Order<Cancelled> {
        Order {
            id: self.id,
            customer_email: self.customer_email,
            amount_cents: self.amount_cents,
            state: Cancelled { reason: reason.to_string() },
        }
    }
}
```
