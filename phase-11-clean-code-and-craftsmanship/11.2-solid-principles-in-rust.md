## Concept

The **SOLID principles** were originally formulated by Robert C. Martin ("Uncle Bob") for classical Object-Oriented Programming (OOP) with class inheritance.

In Rust—a language with **no classes, no inheritance, and no null pointers**—SOLID principles are re-imagined around **Traits**, **Generics**, and **Composition**.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SOLID in Rust: Trait Matrix                     │
├───────────────────────────────┬────────────────────────────────────────┤
│ OOP Principle                 │ Idiomatic Rust Translation             │
├───────────────────────────────┼────────────────────────────────────────┤
│ **S**ingle Responsibility (SRP)│ Small structs + cohesive modules      │
│ **O**pen/Closed (OCP)         │ Extension traits & generic trait bounds│
│ **L**iskov Substitution (LSP) │ Trait contract invariants              │
│ **I**nterface Segregation (ISP)│ Micro-traits (`Read`, `Write`, `AsRef`)│
│ **D**ependency Inversion (DIP)│ Domain traits (Ports) & Infras (Adapters)│
└───────────────────────────────┴────────────────────────────────────────┘
```

---

### 1. Single Responsibility Principle (SRP)
A struct or module should have **one reason to change**.
- **Anti-Pattern**: A `User` struct that parses JSON, validates passwords, writes SQL to Postgres, and sends welcome emails.
- **Clean Rust**: Separate data (`struct User`), repository access (`trait UserRepository`), and notification delivery (`trait NotificationService`).

---

### 2. Open/Closed Principle (OCP) via Extension Traits
Code should be **open for extension, but closed for modification**.

In Rust, you can extend any type (even standard library types like `u64` or `&str`) with new methods without modifying their original source code using **Extension Traits**:

```rust
// Extend primitive numbers with financial currency formatting
pub trait CurrencyFormattingExt {
    fn to_usd_string(&self) -> String;
}

impl CurrencyFormattingExt for i64 {
    fn to_usd_string(&self) -> String {
        format!("${:.2}", *self as f64 / 100.0)
    }
}

// 5000.to_usd_string() -> "$50.00"
```

---

### 3. Interface Segregation Principle (ISP) via Micro-Traits
Clients should not be forced to depend on methods they do not use.

In Java/C#, developers often build monolithic interfaces with 25 methods (`interface Repository { get, save, delete, list, count, export_csv, ... }`).
In Rust, the standard library embodies ISP through tiny, single-method **Micro-Traits**:
- `std::io::Read` (1 required method: `read`)
- `std::io::Write` (2 required methods: `write`, `flush`)
- `std::convert::AsRef` (1 method: `as_ref`)
- `std::ops::Deref` (1 method: `deref`)

---

### 4. Dependency Inversion Principle (DIP): Ports & Adapters
High-level policy modules should not depend on low-level infrastructure modules. Both should depend on **abstract traits**.

```
  ┌────────────────────────────────────────────────────────┐
  │  Domain / Application Layer (High-Level Policy)        │
  │  struct OrderService<R: OrderRepository, P: PaymentPort>│
  │  - Depends strictly on abstract Rust Traits (Ports)    │
  └───────────────────────────┬────────────────────────────┘
                              │
               ┌──────────────┴──────────────┐
               ▼ (Implements Port)           ▼ (Implements Port)
  ┌──────────────────────────────┐ ┌──────────────────────────────┐
  │  PostgresRepository (Adapter)│ │  StripePaymentGateway (Adapter)
  │  Low-level SQLx database     │ │  Low-level HTTP client       │
  └──────────────────────────────┘ └──────────────────────────────┘
```

---

## Why It Matters in Systems Programming

1. **Effortless Unit Testing & Fakes**: By depending on traits (`trait PaymentGateway`), you can swap a real Stripe HTTP client for an in-memory `MockPaymentGateway` during tests with **zero network latency and 100% determinism**.
2. **Zero-Cost Abstractions**: Using generic static dispatch (`fn process<P: PaymentPort>(port: P)`) generates monomorphized machine code with **zero virtual method table (vtable) overhead**.
3. **Decoupled Architecture**: Upgrading your database driver or switching cloud providers requires editing only the infrastructure adapter, leaving core business logic 100% untouched.

---

## Real-World Analogy

- **Monolithic OOP Interfaces (Violating ISP & DIP)** are like buying an all-in-one printer/scanner/fax/toaster where if the toaster breaks, the printer stops working.
- **Rust Traits & DIP** are like standard USB-C wall plugs: the laptop charger only depends on the USB-C standard port (**Trait**); it doesn't care whether electricity comes from solar panels, a wall outlet, or a battery bank (**Adapters**).

## Complete, Compilable Code Example

Below is a complete, self-contained implementation demonstrating **all 5 SOLID principles in pure Rust** with Dependency Inversion, Micro-Traits, and Test Fakes:

```rust
use std::collections::HashMap;
use std::sync::Mutex;

// ============================================================================
// 1. Domain Entities & Value Objects (Single Responsibility)
// ============================================================================

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct OrderId(pub u64);

#[derive(Debug, Clone)]
pub struct Order {
    pub id: OrderId,
    pub customer_email: String,
    pub amount_cents: i64,
    pub is_paid: bool,
}

// ============================================================================
// 2. Abstract Ports / Interfaces (Dependency Inversion & Interface Segregation)
// ============================================================================

/// Micro-Trait 1: Only deals with storing and retrieving orders
pub trait OrderRepository: Send + Sync {
    fn get(&self, id: OrderId) -> Option<Order>;
    fn save(&self, order: Order) -> Result<(), &'static str>;
}

/// Micro-Trait 2: Only deals with charging payment cards
pub trait PaymentGateway: Send + Sync {
    fn charge(&self, email: &str, amount_cents: i64) -> Result<String, &'static str>;
}

// ============================================================================
// 3. High-Level Domain Service (Depends ONLY on Abstract Traits)
// ============================================================================

pub struct OrderFulfillmentService<R: OrderRepository, P: PaymentGateway> {
    repository: R,
    payment_gateway: P,
}

impl<R: OrderRepository, P: PaymentGateway> OrderFulfillmentService<R, P> {
    pub fn new(repository: R, payment_gateway: P) -> Self {
        Self {
            repository,
            payment_gateway,
        }
    }

    /// Pure business logic: Charges customer and updates order status
    pub fn process_order_payment(&self, order_id: OrderId) -> Result<Order, &'static str> {
        let mut order = self
            .repository
            .get(order_id)
            .ok_or("OrderNotFound: Order does not exist")?;

        if order.is_paid {
            return Err("OrderAlreadyPaid: Cannot double-charge order");
        }

        // Delegate to abstract payment gateway port
        let _tx_ref = self
            .payment_gateway
            .charge(&order.customer_email, order.amount_cents)?;

        order.is_paid = true;
        self.repository.save(order.clone())?;

        Ok(order)
    }
}

// ============================================================================
// 4. Infrastructure Adapters (In-Memory Test Fakes for 100% Deterministic Testing)
// ============================================================================

pub struct InMemoryOrderRepository {
    storage: Mutex<HashMap<OrderId, Order>>,
}

impl InMemoryOrderRepository {
    pub fn new() -> Self {
        Self {
            storage: Mutex::new(HashMap::new()),
        }
    }
}

impl OrderRepository for InMemoryOrderRepository {
    fn get(&self, id: OrderId) -> Option<Order> {
        let map = self.storage.lock().unwrap();
        map.get(&id).cloned()
    }

    fn save(&self, order: Order) -> Result<(), &'static str> {
        let mut map = self.storage.lock().unwrap();
        map.insert(order.id, order);
        Ok(())
    }
}

pub struct MockPaymentGateway {
    pub should_succeed: bool,
}

impl PaymentGateway for MockPaymentGateway {
    fn charge(&self, _email: &str, _amount_cents: i64) -> Result<String, &'static str> {
        if self.should_succeed {
            Ok("ch_mock_success_tx_9841".to_string())
        } else {
            Err("CardDeclined: Insufficient funds")
        }
    }
}

// ============================================================================
// 5. Open/Closed Principle via Extension Traits
// ============================================================================

pub trait OrderAnalyticsExt {
    fn is_high_value(&self) -> bool;
}

impl OrderAnalyticsExt for Order {
    fn is_high_value(&self) -> bool {
        self.amount_cents >= 100_000 // $1,000.00+
    }
}

// ============================================================================
// 6. Verification & Test Suite
// ============================================================================

fn main() {
    println!("=== 1. Setting Up Clean Architecture Ports & Adapters ===");
    let repo = InMemoryOrderRepository::new();
    let payment = MockPaymentGateway { should_succeed: true };

    let order = Order {
        id: OrderId(101),
        customer_email: "satoshi@bitcoin.org".to_string(),
        amount_cents: 150_000, // $1,500.00
        is_paid: false,
    };
    repo.save(order.clone()).unwrap();

    let service = OrderFulfillmentService::new(repo, payment);

    println!("Initial Order #101: Paid = {}", order.is_paid);
    println!("High Value Order (Extension Trait): {}\n", order.is_high_value());

    println!("=== 2. Processing Order Payment via Domain Service ===");
    let updated_order = service.process_order_payment(OrderId(101)).unwrap();
    println!("Processed Order #101: Paid = {}", updated_order.is_paid);
    assert!(updated_order.is_paid);

    println!("\n=== 3. Testing Business Rule: Double Charge Protection ===");
    let duplicate_charge_res = service.process_order_payment(OrderId(101));
    println!("Duplicate Charge Result: {:?}", duplicate_charge_res);
    assert!(duplicate_charge_res.is_err());
    println!("✅ Business invariant protected by clean domain service!");
}
```

## Common Pitfalls & Compiler Errors

### 1. Premature Traitification (Over-Abstraction)
Creating a `trait User` for a struct that will only ever have one implementation in the entire lifetime of your application adds unnecessary noise.
**Clean Rule**: Make structs concrete by default. Extract traits only when you have **multiple implementations** (e.g. Postgres vs In-Memory test fake) or need external plugin extension points.

### 2. Leaking Infrastructure Types into Domain Traits
If `trait OrderRepository` returns `Result<Order, sqlx::Error>`, your domain layer is now tightly coupled to SQLx!
**Fix**: Define domain error types (`enum RepositoryError { NotFound, ConnectionFailed }`) and map infrastructure errors at the adapter boundary.

## Complete Solutions to Exercises

### Solution 1: Logger Port

```rust
pub trait LoggerPort: Send + Sync {
    fn log(&self, msg: &str);
}

pub struct ConsoleLogger;

impl LoggerPort for ConsoleLogger {
    fn log(&self, msg: &str) {
        println!("[LOG] {}", msg);
    }
}
```
