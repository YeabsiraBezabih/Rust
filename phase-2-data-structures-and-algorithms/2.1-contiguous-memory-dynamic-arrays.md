## Concept

The **Dynamic Array** (represented by `Vec<T>` in Rust) is the single most important and frequently used data structure in systems programming. To understand why, we must examine how computer hardware interacts with memory.

---

### 1. Contiguous Memory and CPU Cache Locality

A memory structure is **contiguous** when all its elements are stored side-by-side in one unbroken block of RAM.

```
Contiguous Buffer in RAM:
┌──────────┬──────────┬──────────┬──────────┐
│ Item 0   │ Item 1   │ Item 2   │ Item 3   │
│ [0x1000] │ [0x1008] │ [0x1010] │ [0x1018] │
└──────────┴──────────┴──────────┴──────────┘
Address calculation for index `i`: Address = BaseAddress + (i * ElementSizeBytes)
```

Because elements are contiguous:
1. **Instant $O(1)$ Indexing**: The CPU calculates the exact memory address of `array[i]` in a single clock cycle using basic multiplication.
2. **CPU Cache Prefetching (Spatial Locality)**: When the CPU reads `Item 0`, the hardware automatically loads the adjacent bytes (`Item 1`, `Item 2`, `Item 3`) into ultra-fast L1/L2 CPU cache lines. This makes iterating through contiguous arrays up to **100x faster** than following scattered pointers across the heap.

---

### 2. How Dynamic Arrays Grow: The Doubling Strategy

A dynamic array maintains three fields:
- **`ptr`**: Pointer to the heap-allocated contiguous block.
- **`len`**: Number of valid elements currently stored.
- **`cap`**: Total number of element slots allocated in the heap buffer.

When you push an element and `len == cap`, the buffer is full. The dynamic array executes a **Reallocation**:
1. Allocates a new heap buffer with **$2 \times \text{capacity}$** (doubling the capacity).
2. Copies/moves all existing $N$ elements from the old buffer to the new buffer.
3. Frees the old buffer.
4. Appends the new element and updates `cap`.

```
Step 1 (Full):       [A, B, C, D] (len: 4, cap: 4)
Step 2 (Allocate):   [ _, _, _, _, _, _, _, _ ] (cap: 8)
Step 3 (Copy Old):   [ A, B, C, D, _, _, _, _ ]
Step 4 (Insert New): [ A, B, C, D, E, _, _, _ ] (len: 5, cap: 8)
```

---

### 3. Amortized Analysis: Why `push()` is $O(1)$ on Average

A single resize operation requires copying $N$ items, which takes **$O(N)$ linear time**. How can we claim that `push()` is an **$O(1)$** operation?

We use **Amortized Analysis**, which calculates the average cost per operation over a long sequence of operations:

Consider inserting 16 elements starting with capacity 1:
- Reallocations happen at sizes: $1, 2, 4, 8, 16$.
- Element copies: $1 + 2 + 4 + 8 = 15$ copies.
- Normal insertions: $16$ insertions.
- **Total operations**: $15 + 16 = 31$ operations for $16$ pushes.
- **Average cost per push**: $31 / 16 \approx 1.93$ operations $\approx O(1)$ **Amortized Constant Time**.

> **Crucial Rule**: Doubling capacity ($\times 2$) guarantees $O(1)$ amortized insertion. If you instead grow capacity by a fixed constant (e.g., $+1$ or $+10$), the total time degrades to **$O(N^2)$** (catastrophic quadratic slowdown).

---

### 4. Big-O Complexity Table

| Operation | Time Complexity | Reason |
| :--- | :--- | :--- |
| **Lookup by Index (`v[i]`)** | **$O(1)$** | Direct mathematical offset calculation. |
| **Append to End (`push`)** | **$O(1)$ amortized** | Instant when space exists; occasional doubling cost is spread out. |
| **Remove from End (`pop`)** | **$O(1)$** | Simply decrement `len` by 1. |
| **Insert at Index (`insert`)** | **$O(N)$** | Must shift all subsequent elements to the right. |
| **Remove at Index (`remove`)** | **$O(N)$** | Must shift all subsequent elements to the left. |

---

## Why it matters

In high-throughput HTTP servers and network proxies, TCP packets arrive as byte streams. Buffering those bytes in contiguous dynamic arrays maximizes hardware CPU cache utilization. 

Understanding amortized growth is why production network engines use `Vec::with_capacity(expected_size)`: by pre-allocating the buffer upfront, you eliminate the $O(N)$ resizing pauses entirely, ensuring flat, predictable sub-millisecond response latency.

---

## Analogy

Think of **Reserving Hotel Rooms for a Growing Team**:
- You reserve a contiguous block of 4 adjacent rooms in a hotel hallway.
- When employee #5 arrives, the next room is occupied by a stranger. You cannot split your team across hallways.
- The hotel moves your entire team to a new wing with **8 contiguous rooms** ($O(N)$ moving effort).
- The next 3 employees (6, 7, 8) check in instantly with zero moving effort ($O(1)$).
- The rare, expensive moves are paid for by the long streaks of effortless check-ins.

## Code Example

Below is a complete, educational implementation of a custom dynamic array (`CustomDynamicBuffer<T>`) built on top of standard heap allocations to demonstrate capacity doubling, element shifting, and amortized growth.

```rust
#[derive(Debug)]
pub struct CustomDynamicBuffer<T> {
    storage: Vec<T>, // Backing storage simulating raw contiguous heap buffer
}

impl<T: Clone> CustomDynamicBuffer<T> {
    // 1. Constructor: Creates an empty buffer with zero initial capacity
    pub fn new() -> Self {
        CustomDynamicBuffer {
            storage: Vec::new(),
        }
    }

    // 2. Pre-allocated Constructor
    pub fn with_capacity(capacity: usize) -> Self {
        CustomDynamicBuffer {
            storage: Vec::with_capacity(capacity),
        }
    }

    pub fn len(&self) -> usize {
        self.storage.len()
    }

    pub fn capacity(&self) -> usize {
        self.storage.capacity()
    }

    pub fn is_empty(&self) -> bool {
        self.storage.is_empty()
    }

    // 3. Amortized O(1) Push with Geometric Doubling
    pub fn push(&mut self, item: T) {
        if self.len() == self.capacity() {
            let new_cap = if self.capacity() == 0 { 2 } else { self.capacity() * 2 };
            println!("  [REALLOCATION] Growing capacity from {} -> {} slots", self.capacity(), new_cap);
            self.storage.reserve(new_cap - self.len());
        }
        self.storage.push(item);
    }

    // 4. O(1) Pop from end
    pub fn pop(&mut self) -> Option<T> {
        self.storage.pop()
    }

    // 5. O(1) Direct Index Access
    pub fn get(&self, index: usize) -> Option<&T> {
        self.storage.get(index)
    }

    // 6. O(N) Insertion at specific index (Requires shifting elements right)
    pub fn insert_at(&mut self, index: usize, item: T) -> Result<(), &'static str> {
        if index > self.len() {
            return Err("Index out of bounds");
        }
        self.storage.insert(index, item);
        Ok(())
    }

    // 7. O(N) Removal from specific index (Requires shifting elements left)
    pub fn remove_at(&mut self, index: usize) -> Option<T> {
        if index >= self.len() {
            None
        } else {
            Some(self.storage.remove(index))
        }
    }
}

fn main() {
    println!("--- 1. Demonstrating Geometric Capacity Growth ---");
    let mut buffer = CustomDynamicBuffer::new();

    for packet_id in 1..=10 {
        println!("Pushing packet {}:", packet_id);
        buffer.push(packet_id);
        println!("  Current len: {}, capacity: {}", buffer.len(), buffer.capacity());
    }

    println!("\n--- 2. O(1) Element Access ---");
    println!("Element at index 4: {:?}", buffer.get(4));

    println!("\n--- 3. O(N) Shifting Operations ---");
    // Insert at index 0 requires shifting all 10 elements right
    buffer.insert_at(0, 999).unwrap();
    println!("After inserting 999 at index 0: {:?}", buffer);

    // Remove from index 0 requires shifting all elements left
    let removed = buffer.remove_at(0);
    println!("Removed item: {:?}, New First Item: {:?}", removed, buffer.get(0));
}
```

## Common Mistakes

### 1. Growing Capacity Linearly (+1) Instead of Multiplicatively ($\times 2$)
Allocating space for only 1 additional item on each push forces an $O(N)$ copy on *every single push*, turning an $O(N)$ loop of $N$ insertions into an **$O(N^2)$ disaster**.

---

### 2. Inserting or Removing from the Front of a Vector in a Loop
Using `v.insert(0, item)` or `v.remove(0)` inside a loop of size $N$. Because every call shifts all $N$ elements in memory, the entire routine runs in **$O(N^2)$ quadratic time**. 

*How to fix*: If you need fast front insertions/removals, use `VecDeque` (a Ring Buffer / Double-Ended Queue, covered in Lesson 2.3).

---

### 3. Confusing `len` with `capacity`
- `len` is the number of initialized items you can safely access.
- `capacity` is the total allocated memory pool.
- Accessing `buffer[capacity - 1]` when `len < capacity` causes an out-of-bounds panic.

## Solutions

### Solution to Exercise 1
1. **Doubling Strategy**:
   - Resizes occur at: $1 \to 2$ (1 copy), $2 \to 4$ (2 copies), $4 \to 8$ (4 copies), $8 \to 16$ (8 copies), $16 \to 32$ (16 copies).
   - Total copies = $1 + 2 + 4 + 8 + 16 = \mathbf{31}$ **copies**.
2. **Fixed $+1$ Strategy**:
   - Resizes occur on every step: $1 + 2 + 3 + \dots + 31 = \frac{31 \times 32}{2} = \mathbf{496}$ **copies**.
3. **Comparison**: The doubling strategy requires only 31 copies vs 496 copies (a **$16\times$ reduction in work** for just 32 elements; at $1,000,000$ elements, doubling takes $\approx 10^6$ copies while $+1$ takes $\approx 5 \times 10^{11}$ operations!).

---

### Solution to Exercise 2
```rust
impl<T: Clone> CustomDynamicBuffer<T> {
    pub fn swap_remove(&mut self, index: usize) -> Option<T> {
        if index >= self.len() {
            return None;
        }
        Some(self.storage.swap_remove(index))
    }
}

fn main() {
    let mut buffer = CustomDynamicBuffer::new();
    buffer.push(10);
    buffer.push(20);
    buffer.push(30);
    buffer.push(40);

    let removed = buffer.swap_remove(1); // Removes 20, replaces with 40
    println!("Removed: {:?}", removed);   // Some(20)
    println!("Buffer state: {:?}", buffer); // [10, 40, 30]
}
```

### Solution to Exercise 3
```rust
fn simulate_packet_ingest(count: usize, preallocate: bool) -> usize {
    let mut buffer = if preallocate {
        Vec::with_capacity(count)
    } else {
        Vec::new()
    };

    for i in 0..count {
        buffer.push(i);
    }

    buffer.capacity()
}

fn main() {
    let unallocated_cap = simulate_packet_ingest(1000, false);
    let preallocated_cap = simulate_packet_ingest(1000, true);

    println!("Unallocated Final Capacity : {}", unallocated_cap); // Usually 1024 (grew 0->4->8...->1024)
    println!("Preallocated Final Capacity: {}", preallocated_cap); // Exactly 1000 (0 reallocations!)
}
```
