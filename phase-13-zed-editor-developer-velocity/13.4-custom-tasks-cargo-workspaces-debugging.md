## Concept

A high-velocity systems engineer should never waste time repeatedly retyping long terminal commands like `cargo test --package my-crate --test integration_tests -- --nocapture` or manually setting up profilers.

Zed includes an integrated **Task Runner System** configured via `.zed/tasks.json` and support for the **Debug Adapter Protocol (DAP)** using **LLDB** or **GDB**.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    Zed Automated Task & Debugger Pipeline                    │
├──────────────────────────────────────────────────────────────────────────────┤
│  ZED TASK RUNNER (.zed/tasks.json)                                           │
│  ┌────────────────────────────────────────────────────────────────────────┐  │
│  │ Context Variable Expansion: $ZED_FILE, $ZED_ROW, $ZED_WORKTREE_ROOT    │  │
│  │   • Run single test under cursor                                       │  │
│  │   • Generate SVG Flamegraph on current binary                          │  │
│  │   • Live test runner (cargo nextest / cargo watch)                     │  │
│  └───────────────────┬────────────────────────────────┬───────────────────┘  │
│                      │ Spawns Task Modal              │ Spawns LLDB DAP      │
│                      ▼                                ▼                      │
│  ┌────────────────────────────────────────┐ ┌─────────────────────────────┐  │
│  │ Integrated Terminal / Output Buffer    │ │ Native LLDB Debugger        │  │
│  │ (Direct GPU-rendered ANSI Stream)      │ │   • Hardware Breakpoints    │  │
```

### 1. The Production `.zed/tasks.json` Configuration

Create a `.zed/tasks.json` file in your workspace root to define one-keystroke development actions:

```json
[
  {
    "label": "Cargo: Run Test Under Cursor",
    "command": "cargo test -- --nocapture $ZED_SYMBOL",
    "use_new_terminal": false,
    "allow_concurrent_runs": false,
    "reveal": "always"
  },
  {
    "label": "Cargo: Nextest (Fast Parallel Test Runner)",
    "command": "cargo nextest run",
    "use_new_terminal": false,
    "allow_concurrent_runs": false,
    "reveal": "always"
  },
  {
    "label": "Cargo: Watch & Check Workspace",
    "command": "cargo watch -x 'check --all-targets --all-features'",
    "use_new_terminal": true,
    "allow_concurrent_runs": false,
    "reveal": "always"
  },
  {
    "label": "Cargo: Generate CPU Flamegraph",
    "command": "cargo flamegraph --root --bench $ZED_STEM -- --bench",
    "use_new_terminal": true,
    "allow_concurrent_runs": false,
    "reveal": "always"
  },
  {
    "label": "Clippy: Strict Pedantic Workspace Audit",
    "command": "cargo clippy --all-targets --all-features -- -D warnings -W clippy::pedantic",
    "use_new_terminal": false,
    "allow_concurrent_runs": false,
    "reveal": "always"
  }
]
```

### 2. Built-In Zed Task Variables

| Variable | Description |
| :--- | :--- |
| `$ZED_FILE` | Absolute path to the active file. |
| `$ZED_FILENAME` | Basename of the active file (e.g. `main.rs`). |
| `$ZED_STEM` | File name without extension (e.g. `main`). |
| `$ZED_ROW` | Current line number of the cursor (1-indexed). |
| `$ZED_COLUMN` | Current column number of the cursor. |
| `$ZED_SYMBOL` | Current symbol (function name, test name, struct) under cursor. |
| `$ZED_WORKTREE_ROOT` | Root directory of the opened project/workspace. |

### 3. Native Debugging with LLDB & DAP

For stepping through systems code, inspecting raw pointers, and catching segmentation faults or panics:

1. **Install LLDB DAP**: On Linux (`sudo apt install lldb`) or macOS (bundled with Xcode Command Line Tools).
2. **Launch Configuration (`.zed/launch.json` or debug task)**:
```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "lldb",
      "request": "launch",
      "name": "Debug Executable",
      "cargo": {
        "args": ["build", "--bin=my_engine"]
      },
      "args": ["--port", "8080"],
      "cwd": "${workspaceFolder}"
    }
  ]
]
```
3. **Interactive Debug Controls**:
   - `F9`: Toggle Breakpoint on current line.
   - `F5`: Start / Continue Debugging.
   - `F10`: Step Over next instruction.
   - `F11`: Step Into function call.
   - `Shift-F11`: Step Out of current stack frame.

## Why It Matters in Systems Programming

1. **Micro-Feedback Loops in TDD**: Spawning `cargo nextest` or running the test under your cursor with a single keystroke (`alt-t` or task launcher) cuts testing latency from 15 seconds to under 500 milliseconds.
2. **Inspecting Memory & Cache Traps**: When debugging unsafe Rust, FFI bindings, or lock contention, LLDB lets you view the exact memory addresses, register contents, and thread deadlock states.
3. **Automated Profiling Execution**: Triggering `cargo flamegraph` directly from the active file allows you to continuously profile algorithms during active development.

## Complete, Compilable Code Example

Here is a robust Rust concurrent calculation engine featuring unit tests and an intentional edge-case condition perfect for testing with Zed Tasks and the LLDB debugger:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::thread;

/// A thread-safe counter engine designed for step-through debugging
pub struct SharedCounter {
    value: Arc<AtomicU64>,
}

impl SharedCounter {
    pub fn new(initial: u64) -> Self {
        Self {
            value: Arc::new(AtomicU64::new(initial)),
        }
    }

    pub fn increment_by(&self, amount: u64) -> u64 {
        self.value.fetch_add(amount, Ordering::SeqCst)
    }

    pub fn get(&self) -> u64 {
        self.value.load(Ordering::SeqCst)
    }

    /// Parallel accumulator across N threads
    pub fn parallel_accumulate(&self, num_threads: usize, increments_per_thread: u64) -> u64 {
        let mut handles = Vec::with_capacity(num_threads);

        for _ in 0..num_threads {
            let counter_clone = Arc::clone(&self.value);
            let handle = thread::spawn(move || {
                for _ in 0..increments_per_thread {
                    counter_clone.fetch_add(1, Ordering::SeqCst);
                }
            });
            handles.push(handle);
        }

        for handle in handles {
            handle.join().expect("Thread panicked");
        }

        self.get()
    }
}

fn main() {
    println!("=== Zed Tasks & Debugger Execution Target ===");

    let counter = SharedCounter::new(100);
    println!("Initial count: {}", counter.get());

    let final_count = counter.parallel_accumulate(8, 10_000);
    println!("Final count after 80,000 increments: {}", final_count);
    assert_eq!(final_count, 80_100);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_single_increment() {
        let counter = SharedCounter::new(0);
        counter.increment_by(42);
        assert_eq!(counter.get(), 42);
    }

    #[test]
    fn test_parallel_concurrency() {
        let counter = SharedCounter::new(0);
        let result = counter.parallel_accumulate(4, 5_000);
        assert_eq!(result, 20_000);
    }
}
```

## Common Pitfalls & Configuration Errors

### 1. `cargo flamegraph` Permission Errors on Linux
- **Cause**: Linux kernel restricting unprivileged users from accessing hardware performance counters (`perf_event_open`).
- **Fix**: Run `sudo sysctl -w kernel.perf_event_paranoid=1` or configure your task with `sudo`.

### 2. Broken Path Resolution in Task Commands
- **Cause**: Using relative paths without accounting for whether Zed opened a single sub-crate or an entire Cargo workspace.
- **Fix**: Always prefix workspace commands with `$ZED_WORKTREE_ROOT` or run from project root.
