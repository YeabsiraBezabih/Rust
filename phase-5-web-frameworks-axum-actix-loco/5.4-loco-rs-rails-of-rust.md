## Concept

In traditional Rust web development, setting up an enterprise backend requires stitching together 15+ independent crates: Axum for routing, SeaORM for databases, Argon2 for hashing, JSON Web Tokens for auth, Tower for middleware, and custom background worker loops.

**Loco.rs** is the official "Ruby on Rails for Rust" — an opinionated, batteries-included framework built on **Axum** and **SeaORM** that emphasizes **Convention over Configuration**.

```
                           ┌──────────────────────────────────────────────┐
                           │          Loco.rs MVC Architecture            │
                           ├──────────────────────────────────────────────┤
HTTP Client ──────────────►│ Controllers (`src/controllers/`)             │
                           │     │ (Extracts params, validates input)     │
                           │     ▼                                        │
                           │ Models / Entities (`src/models/`)            │
                           │     │ (SeaORM ActiveModels & Business Logic) │
                           │     ▼                                        │
Database Storage ◄─────────│ PostgreSQL / SQLite / MySQL Engine           │
                           │                                              │
Background Jobs ◄──────────│ Workers (`src/workers/`)                     │
                           │     └── Async task queuing & email delivery  │
                           └──────────────────────────────────────────────┘
```

---

### 1. The Loco CLI & Scaffolding Engine

Loco provides an automated command-line interface that generates production code instantly:

```bash
# 1. Create a new full-stack SaaS backend
cargo install loco-cli
loco new

# 2. Generate a complete database-backed resource (Model, Controller, Migration, Tests)
loco generate scaffold user_article title:string content:text published:bool

# 3. Apply schema migrations
cargo loco db migrate

# 4. Start the development server with live reload
cargo loco start
```

---

### 2. The `Hooks` Trait: Lifecycle Management

In Loco, the master application configuration lives in `src/app.rs` by implementing the `Hooks` trait:
- **`routes`**: Registers controller endpoints.
- **`initializers`**: Attaches custom services (Redis pools, Prometheus metrics).
- **`connect_workers`**: Registers background queue tasks.
- **`seed`**: Populates default database records for development.

```rust
#[async_trait]
impl Hooks for App {
    fn app_name() -> &'static str { "Antigravity SaaS" }

    fn routes(ctx: &AppContext) -> AppRoutes {
        AppRoutes::with_default_routes()
            .add_route(controllers::article::routes())
            .add_route(controllers::auth::routes())
    }
}
```

### 3. Built-In Authentication and Background Tasks

Loco includes ready-to-use authentication endpoints (`/api/auth/register`, `/api/auth/login`, `/api/auth/verify`) and background worker queues (`BackgroundWorker<T>`).

## Why it matters

- **Unmatched Developer Velocity**: Teams can scaffold and deploy secure, database-backed REST APIs in minutes rather than weeks.
- **Zero Performance Penalty**: Because Loco compiles down to native **Axum and Tokio**, it retains the full microsecond-level latency and high concurrency of Rust.

## Code Example

A representative Loco controller (`src/controllers/article.rs`):

```rust
use axum::debug_handler;
use loco_rs::prelude::*;
use serde::{Deserialize, Serialize};

// 1. DTO Request & Response Structures
#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct CreateArticleParams {
    pub title: String,
    pub content: String,
}

#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct ArticleResponse {
    pub id: i32,
    pub title: String,
    pub content: String,
    pub views: u32,
}

// 2. Controller Handlers
#[debug_handler]
pub async fn list_articles(
    State(_ctx): State<AppContext>,
) -> Result<Response> {
    let articles = vec![
        ArticleResponse {
            id: 1,
            title: "Systems Programming in Rust".into(),
            content: "Deep dive into memory safety...".into(),
            views: 450,
        }
    ];

    // Loco format helper: serializes JSON and sets status 200 OK
    format::json(articles)
}

#[debug_handler]
pub async fn create_article(
    auth: auth::JWT, // Automatically verified by Loco JWT middleware!
    State(_ctx): State<AppContext>,
    Json(params): Json<CreateArticleParams>,
) -> Result<Response> {
    println!("[Loco] Article created by authenticated user ID: {}", auth.claims.pid);

    let created = ArticleResponse {
        id: 102,
        title: params.title,
        content: params.content,
        views: 0,
    };

    // Return status 201 Created with JSON
    format::render().status(StatusCode::CREATED).json(created)
}

// 3. Registering Controller Routes
pub fn routes() -> Routes {
    Routes::new()
        .prefix("/api/v1/articles")
        .add("/", get(list_articles))
        .add("/", post(create_article))
}

fn main() {
    println!("Loco.rs controller routes initialized.");
    let r = routes();
    println!("Mounted prefix: {}", r.prefix);
}
```

## Common Mistakes

### 1. Manually Editing Auto-Generated Database Migrations
Modifying an already-applied migration script directly instead of generating a new sequential migration using `loco generate migration <name>`. This causes database checksum mismatches in production.

---

### 2. Bypassing the `AppContext`
Attempting to connect to the database directly within a handler using raw `PgPool` instead of accessing `ctx.db` provided by the shared `AppContext`.

---

### 3. Hardcoding Environment Secrets
Placing JWT secrets or database passwords in `config/development.yaml` instead of referencing environment variables (`{{ get_env(name="DATABASE_URL") }}`).

## Solutions

### Solution to Exercise 1
```rust
use loco_rs::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
pub struct PaginationParams {
    pub page: Option<u64>,
    pub per_page: Option<u64>,
}

#[derive(Serialize)]
pub struct PagedResponse<T> {
    pub page: u64,
    pub per_page: u64,
    pub total: u64,
    pub data: Vec<T>,
}

pub async fn get_paged_items(
    Query(params): Query<PaginationParams>,
    State(_ctx): State<AppContext>,
) -> Result<Response> {
    let page = params.page.unwrap_or(1);
    let per_page = params.per_page.unwrap_or(20);

    let res = PagedResponse {
        page,
        per_page,
        total: 100,
        data: vec!["Item Alpha", "Item Bravo"],
    };

    format::json(res)
}
```

### Solution to Exercise 2
```rust
use loco_rs::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Deserialize, Serialize, Debug)]
pub struct EmailPayload {
    pub user_email: String,
    pub username: String,
}

pub struct WelcomeEmailWorker;

#[async_trait]
impl BackgroundWorker<EmailPayload> for WelcomeEmailWorker {
    fn build(_ctx: &AppContext) -> Self {
        WelcomeEmailWorker
    }

    async fn perform(&self, args: EmailPayload) -> Result<()> {
        println!("[Worker] Sending welcome email to: {} ({})", args.username, args.user_email);
        Ok(())
    }
}
```

### Solution to Exercise 3
**Explanation**:
1. **Migration File** (`migration/src/m..._projects.sql`): Creates table `projects` with columns `id`, `name`, `budget`, `created_at`, `updated_at`.
2. **SeaORM Entity Model** (`src/models/_entities/projects.rs` & `src/models/projects.rs`): Defines the `Model`, `ActiveModel`, and validation hooks.
3. **Axum Controller** (`src/controllers/projects.rs`): Generates CRUD endpoints (`list`, `get_one`, `add`, `update`, `delete`).
4. **Integration Test** (`tests/requests/projects.rs`): Tests API routes with mocked DB fixtures.
