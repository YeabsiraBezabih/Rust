## Concept

When writing software, there are often multiple ways to solve the same problem. How do we determine which solution is "better" or "more efficient"?

Measuring speed with a stopwatch (in milliseconds) is unreliable because runtime depends on hardware specs, background CPU load, operating system scheduling, and compiler optimizations. 

Instead, computer scientists use **Big-O Notation** to measure how an algorithm's resource requirements (**execution time** or **memory space**) scale as the **input size ($N$)** grows.

```
Operations (Time)
  ▲
  │                                    O(N²) [Quadratic - Dangerous]
  │                                  /
  │                                 /
  │                                /    O(N) [Linear - Acceptable]
  │                               /   /
  │                              /  /
  │                             / /
  │                            //       O(log N) [Logarithmic - Excellent]
  │                           // ────── O(1) [Constant - Ideal]
  └───────────────────────────┴────────────────────────► Input Size (N)
```

---

### 1. The Core Big-O Complexity Classes

Big-O focuses on the **worst-case scenario** as the input size $N$ becomes very large.

| Big-O | Name | Intuition | Operations for $N = 1,000,000$ |
| :--- | :--- | :--- | :--- |
| **$O(1)$** | **Constant Time** | Takes the exact same time regardless of whether $N$ is 1 or 1,000,000. | $\approx 1$ step |
| **$O(\log N)$** | **Logarithmic Time** | Cuts the problem size in half at every step (e.g., binary search). | $\approx 20$ steps |
| **$O(N)$** | **Linear Time** | Inspects every element once. Time scales directly 1-to-1 with $N$. | $1,000,000$ steps |
| **$O(N \log N)$** | **Linearithmic Time** | The standard speed for efficient general-purpose sorting algorithms. | $\approx 20,000,000$ steps |
| **$O(N^2)$** | **Quadratic Time** | Every item is compared with every other item (nested loops). | $1,000,000,000,000$ steps |

---

### 2. Time Complexity vs. Space Complexity

- **Time Complexity**: How many CPU operations are required as $N$ grows.
- **Space Complexity**: How much extra memory (RAM) is allocated on the Stack or Heap as $N$ grows.
  - If a function creates a single counter variable regardless of input size, its auxiliary space complexity is **$O(1)$**.
  - If a function creates a brand-new copy of an array with $N$ items on the heap, its space complexity is **$O(N)$**.

---

### 3. Rules for Simplifying Big-O

1. **Drop Constants**: $O(2N)$ and $O(500N)$ are both simplified to **$O(N)$**. Big-O measures the *growth rate curve*, not the constant multiplier.
2. **Drop Non-Dominant Terms**: In an algorithm taking $N^2 + N$ operations, as $N$ reaches one million, $N^2$ ($10^{12}$) completely dwarfs $N$ ($10^6$). Thus, $O(N^2 + N)$ simplifies to **$O(N^2)$**.

---

## Why it matters

In high-performance networking and backend architectures, algorithmic complexity makes the difference between a server handling 100,000 requests per second and a server crashing under light load:
- Looking up an active connection by its socket ID in a Hash Table is **$O(1)$** (instant).
- Looking up an active connection by looping through an unsorted list of 100,000 items is **$O(N)$** (slow).
- Checking every connection against every other connection with nested loops is **$O(N^2)$** (catastrophic: 10 billion operations).

---

## Analogy

Imagine searching for a specific name in a physical phone book containing 1,000,000 names:
- **$O(N)$ (Linear Search)**: You start on page 1 and read every single name one by one until you find it. If the name is at the end, you inspect 1,000,000 names.
- **$O(\log N)$ (Binary Search)**: You open the book to the exact middle (page 500,000). The name starts with "M", so you discard the first half. You open to the middle of the remaining half (page 750,000) and repeat. You will find any name in at most **20 page turns**.
- **$O(1)$ (Direct Index)**: Someone gives you the exact page and line number beforehand. You flip directly to that exact spot in 1 step.

## Code Example

```rust
// 1. O(1) - Constant Time
// Looks up an element directly at a known position. Takes 1 step regardless of array size.
fn get_first_packet_id(packets: &[u32]) -> u32 {
    packets[0]
}

// 2. O(N) - Linear Time
// A single loop that inspects every element once to find if a target exists.
fn contains_packet_id(packets: &[u32], target_id: u32) -> bool {
    for &id in packets {
        if id == target_id {
            return true;
        }
    }
    false
}

// 3. O(N^2) - Quadratic Time
// Nested loops comparing every packet against every other packet to detect duplicates.
fn has_duplicate_packets(packets: &[u32]) -> bool {
    let length = packets.len();
    for i in 0..length {
        for j in (i + 1)..length {
            if packets[i] == packets[j] {
                return true; // Duplicate detected
            }
        }
    }
    false
}

fn main() {
    let packet_batch = [101, 102, 103, 104, 105];

    // O(1) execution
    let first = get_first_packet_id(&packet_batch);
    println!("First packet: {}", first);

    // O(N) execution
    let found = contains_packet_id(&packet_batch, 104);
    println!("Contains packet 104: {}", found);

    // O(N^2) execution
    let duplicates = has_duplicate_packets(&packet_batch);
    println!("Contains duplicates: {}", duplicates);
}
```

## Common Mistakes

### 1. Equating Lines of Code to Big-O Efficiency
A beginner might assume that a function with 20 lines of simple math is "slower" than a function with 3 lines containing nested loops. Big-O measures how the number of **iterations/operations** scales with input size, not the physical length of the source code text.

---

### 2. Confusing Best-Case with Worst-Case
In `contains_packet_id`, if the target happens to be the very first item, the function exits in 1 step ($O(1)$ best-case). However, Big-O standard notation measures the **worst-case** (when the target is at the very end or not present at all, requiring $N$ steps).

---

### 3. Ignoring Space Complexity
Optimizing time complexity by allocating massive auxiliary tables on the heap can lead to out-of-memory (OOM) crashes. Systems engineers always evaluate both time and space trade-offs.

## Exercises

### Exercise 1 (Classifying Big-O Time Complexity)
State the Big-O time complexity ($O(1)$, $O(N)$, or $O(N^2)$) for each of the following functions:

```rust
// Function A
fn print_first_item(items: &[u32]) {
    if !items.is_empty() {
        println!("{}", items[0]);
    }
}

// Function B
fn calculate_sum(items: &[u32]) -> u32 {
    let mut total = 0;
    for &num in items {
        total += num;
    }
    total
}

// Function C
fn print_all_pairs(items: &[u32]) {
    for &a in items {
        for &b in items {
            println!("Pair: ({}, {})", a, b);
        }
    }
}
```

### Exercise 2 (Comparing Scaling in Systems)
You are building an authentication gateway that must verify incoming API tokens against a database of $N = 1,000,000$ active session tokens.
1. If you use a linear search algorithm ($O(N)$), what is the maximum number of token comparisons required for a single request?
2. If you use a binary search algorithm on a sorted list ($O(\log_2 N)$), approximately how many comparisons are required?
3. Which approach allows the gateway to sustain high request throughput without CPU starvation?

---

### Exercise 3 (Identifying Space Complexity)
Determine the auxiliary space complexity ($O(1)$ or $O(N)$) for this function:

```rust
fn count_positive_numbers(numbers: &[i32]) -> u32 {
    let mut count = 0;
    for &val in numbers {
        if val > 0 {
            count += 1;
        }
    }
    count
}
```

---

## Solutions

### Solution to Exercise 1
- **Function A**: **$O(1)$** (Constant Time) — Performs a single check and index lookup regardless of the slice size.
- **Function B**: **$O(N)$** (Linear Time) — Loops through all $N$ elements once.
- **Function C**: **$O(N^2)$** (Quadratic Time) — Nested loops iterate $N \times N$ times.

---

### Solution to Exercise 2
1. **$1,000,000$ comparisons** (in the worst-case where the token is invalid or at the end of the list).
2. **$\approx 20$ comparisons** ($\log_2(1,000,000) \approx 19.93$).
3. **Binary Search ($O(\log N)$)** (or an $O(1)$ hash map lookup), because 20 operations per request will not saturate the CPU, whereas 1,000,000 operations per request will immediately overload the server.

---

### Solution to Exercise 3
**Space Complexity**: **$O(1)$** (Constant Space).
**Explanation**: The function only allocates a single stack variable (`let mut count = 0;`). No matter how large `numbers` is (10 items or 10,000,000 items), the function uses the exact same fixed amount of memory.
