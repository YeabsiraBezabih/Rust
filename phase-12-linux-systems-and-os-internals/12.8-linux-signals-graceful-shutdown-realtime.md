## Concept

A **signal** is an asynchronous kernel notification delivered to a process to inform it of an event (e.g. user pressed `Ctrl-C` $\rightarrow$ `SIGINT`, system rebooting $\rightarrow$ `SIGTERM`, segmentation fault $\rightarrow$ `SIGSEGV`, or broken socket write $\rightarrow$ `SIGPIPE`).

When the kernel delivers a signal:
1. The CPU **pauses the currently executing user instruction stream**.
2. Saves CPU register state onto the process stack.
3. Jumps to the registered **Signal Handler** in user space.
4. Once the handler returns, restores registers and resumes normal execution.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                  Signal Delivery & Asynchronous Signal Safety                │
├──────────────────────────────────────────────────────────────────────────────┤
│  Normal Application Thread                                                   │
│  ┌────────────────────────────────────────────────────────────────────────┐  │
│  │ Acquires `let guard = MUTEX.lock();` ──► Interrupted mid-execution!    │  │
│  └───────────────────────────────────┬────────────────────────────────────┘  │
│                                      │ Kernel intercepts & interrupts thread │
│                                      ▼                                       │
│  ┌────────────────────────────────────────────────────────────────────────┐  │
│  │ Signal Handler (`sigaction` handler)                                   │  │
│  │   • ❌ DANGEROUS: If handler calls `MUTEX.lock()` ➔ INSTANT DEADLOCK!   │  │
│  │   • ❌ DANGEROUS: If handler calls `malloc()` / `println!` ➔ CRASH!     │  │
│  │   • ✓ SAFE: Set `AtomicBool` or write single byte to `signalfd` / Pipe │  │
│  └───────────────────────────────────┬────────────────────────────────────┘  │
│                                      │ Handler finishes (sys_rt_sigreturn)   │
│                                      ▼                                       │
│  Normal Thread Resumes Execution                                             │
└──────────────────────────────────────────────────────────────────────────────┘
```

---

### 1. The Trap of Asynchronous Signal Safety

Because a signal handler can interrupt **any thread at any instruction** (even inside `malloc()` or while holding a lock):
- You **cannot** allocate heap memory (`Vec::new()`, `String::from()`).
- You **cannot** acquire standard mutexes (`std::sync::Mutex`).
- You **cannot** use buffered standard I/O (`println!`).

Only a small list of POSIX **Async-Signal-Safe functions** (such as `write()`, `sigaction()`, and atomic operations) are permitted.

---

### 2. Bridging Signals to Event Loops: `signalfd` & The Self-Pipe Trick

To avoid writing unsafe code in signal handlers, modern systems engineers bridge signals into standard file descriptors:

1. **The Self-Pipe Trick (Portable POSIX)**: A signal handler does only one thing: writes `[1u8]` into an anonymous non-blocking pipe. The main event loop reads from the pipe using `epoll`.
2. **`signalfd` (Linux Native)**: Creates a dedicated file descriptor that directly emits `struct signalfd_siginfo` structs when signals arrive, allowing signals to be handled directly inside `epoll` or Tokio event loops without installing traditional signal handlers!

---

### 3. POSIX Real-Time Signals

Standard signals (`1..31`) do not queue: if 5 `SIGUSR1` signals arrive in quick succession, only 1 signal may be delivered (4 are dropped).

**POSIX Real-Time Signals (`SIGRTMIN` to `SIGRTMAX`, signals 34..64)**:
- Signals are **strictly queued** in order (no dropped notifications).
- Support transmitting an accompanying 64-bit payload (`sigval`) via `sigqueue()`.

---

## Why It Matters in Systems & Backend Engineering

1. **Graceful Zero-Downtime Teardown**: When Kubernetes or Systemd stops a pod/service, it sends `SIGTERM`. The backend must stop accepting new HTTP requests, finish in-flight database transactions, flush WAL buffers, and cleanly exit before `SIGKILL` is issued.
2. **Configuration Hot-Reloading (`SIGHUP`)**: Nginx and PostgreSQL reload configuration files without dropping connections upon receiving `SIGHUP`.
3. **Preventing Silent Process Death on `SIGPIPE`**: Writing to a closed TCP socket generates `SIGPIPE`, which kills the process by default. Production network daemons must explicitly ignore `SIGPIPE`.

---

## Real-World Analogy

- **A Normal Function Call** is like a colleague knocking on your office door and waiting for you to finish your sentence before speaking.
- **A Linux Signal** is like a fire alarm klaxon sounding: it interrupts whatever you are doing immediately, regardless of whether you were in the middle of writing down an important number (**Interrupting `malloc`**).

## Complete, Compilable Code Example

The following program demonstrates a **Safe Signal Coordinator** using atomic flags and event channels to achieve clean, graceful shutdown in multi-threaded Rust:

```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::Duration;

/// Thread-safe signal coordinator for server lifecycle management
pub struct ServerSignalCoordinator {
    shutdown_flag: Arc<AtomicBool>,
    reload_flag: Arc<AtomicBool>,
}

impl ServerSignalCoordinator {
    pub fn new() -> Self {
        Self {
            shutdown_flag: Arc::new(AtomicBool::new(false)),
            reload_flag: Arc::new(AtomicBool::new(false)),
        }
    }

    pub fn shutdown_handle(&self) -> Arc<AtomicBool> {
        Arc::clone(&self.shutdown_flag)
    }

    pub fn trigger_shutdown(&self) {
        self.shutdown_flag.store(true, Ordering::SeqCst);
    }

    pub fn trigger_reload(&self) {
        self.reload_flag.store(true, Ordering::SeqCst);
    }

    pub fn should_shutdown(&self) -> bool {
        self.shutdown_flag.load(Ordering::SeqCst)
    }

    pub fn should_reload(&self) -> bool {
        self.reload_flag.swap(false, Ordering::SeqCst) // Consumes reload event
    }
}

fn main() {
    println!("=== Linux Signal Handling & Graceful Teardown Engine ===");

    let coordinator = ServerSignalCoordinator::new();
    let shutdown_signal = coordinator.shutdown_handle();

    // 1. Simulate Background Worker Thread
    let worker_handle = thread::spawn(move || {
        let mut job_counter = 0;
        println!("[WORKER] Background task processing started.");

        while !shutdown_signal.load(Ordering::SeqCst) {
            job_counter += 1;
            println!("  -> [WORKER] Executing batch job #{}", job_counter);
            thread::sleep(Duration::from_millis(200));
        }

        println!("[WORKER] Shutdown signal received. Flushing pending database writes...");
        thread::sleep(Duration::from_millis(300)); // Simulate clean flush
        println!("[WORKER] All buffers safely committed. Worker cleanly stopped.");
    });

    // 2. Simulate Server Running for 800ms
    thread::sleep(Duration::from_millis(700));

    // 3. Simulate arrival of SIGTERM from Systemd / Kubernetes
    println!("\n[KERNEL] Delivering SIGTERM to Process PID: {}", std::process::id());
    coordinator.trigger_shutdown();

    // 4. Wait for graceful teardown
    worker_handle.join().expect("Worker thread failed");
    println!("[MAIN] Server shutdown completed with 0 errors. Goodbye!");
}
```

## Common Pitfalls & Server Mistakes

### 1. Calling Allocations or Mutexes in `sigaction` Handlers
- **Cause**: Trying to log with `println!` or write to a `Mutex<T>` inside a custom raw C signal handler.
- **Fix**: Never put complex logic in signal handlers. Set an `AtomicBool` or write a single byte to a channel / pipe.

### 2. Failing to Ignore `SIGPIPE` on Network Daemons
- **Cause**: When a client abruptly disconnects, subsequent writes to the socket trigger `SIGPIPE`. By default, Linux terminates the server instantly!
- **Fix**: Set `SIGPIPE` to `SIG_IGN` on server startup.

## Complete Solutions to Exercises

### Solution 1: Config Hot-Reload Coordinator
```rust
pub struct HotReloadEngine {
    config_version: u32,
    reload_requested: bool,
}

impl HotReloadEngine {
    pub fn new() -> Self {
        Self { config_version: 1, reload_requested: false }
    }

    pub fn handle_sighup(&mut self) {
        self.reload_requested = true;
    }

    pub fn poll_and_reload(&mut self) -> bool {
        if self.reload_requested {
            self.config_version += 1;
            self.reload_requested = false;
            true
        } else {
            false
        }
    }
}

#[test]
fn test_hot_reload() {
    let mut engine = HotReloadEngine::new();
    assert_eq!(engine.poll_and_reload(), false);
    engine.handle_sighup();
    assert_eq!(engine.poll_and_reload(), true);
    assert_eq!(engine.config_version, 2);
}
```

### Solution 2: Signal Classification Enum
```rust
pub fn classify_signal(signo: i32) -> &'static str {
    match signo {
        1 => "SIGHUP: Hangup / Reload Configuration",
        2 => "SIGINT: Terminal Interrupt (Ctrl-C)",
        9 => "SIGKILL: Uncatchable Immediate Termination",
        11 => "SIGSEGV: Invalid Memory Access / Segmentation Fault",
        13 => "SIGPIPE: Broken Pipe (Write to closed socket)",
        15 => "SIGTERM: Graceful Termination Request",
        17 => "SIGCHLD: Child Process Status Changed",
        _ => "OTHER: Unknown or Real-Time Signal",
    }
}

#[test]
fn test_classify_signal() {
    assert_eq!(classify_signal(15), "SIGTERM: Graceful Termination Request");
    assert_eq!(classify_signal(11), "SIGSEGV: Invalid Memory Access / Segmentation Fault");
}
```
