## Concept

Many developers believe a "Docker Container" is a lightweight virtual machine. 

In reality, **a container is just a normal Linux process bounded by kernel flags**. There is no hypervisor, no guest OS kernel, and no virtual hardware.

A container process is created using **Linux Namespaces**: a kernel feature that partitions system resources such that a group of processes sees a completely isolated view of the system.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                        The 7 Core Linux Namespaces                           │
├──────────────────────────────────────────────────────────────────────────────┤
│  CONTAINER PROCESS (Isolated view of the operating system)                   │
│  ┌────────────────────────────────────────────────────────────────────────┐  │
│  │ 1. PID Namespace   (`CLONE_NEWPID`): Sees itself as PID 1 (Init)       │  │
│  │ 2. Mount Namespace (`CLONE_NEWNS`):  Private `/` filesystem hierarchy │  │
│  │ 3. Net Namespace   (`CLONE_NEWNET`): Dedicated `veth` & 10.0.0.2 IP    │  │
│  │ 4. UTS Namespace   (`CLONE_NEWUTS`): Hostname = "isolated-sandbox"     │  │
│  │ 5. IPC Namespace   (`CLONE_NEWIPC`): Private shared memory & message Q │  │
│  │ 6. User Namespace  (`CLONE_NEWUSER`): UID 0 (root inside) = UID 1000   │  │
│  │ 7. cgroup Namespace(`CLONE_NEWCGROUP`): Isolated view of cgroups fs    │  │
│  └───────────────────┬────────────────────────────────────────────────────┘  │
│                      │ Root filesystem switched via                          │
│                      ▼                                                       │
│  `pivot_root()` ──► Container Rootfs (`/var/lib/containers/alpine_root/`)    │
└──────────────────────────────────────────────────────────────────────────────┘
```

---

### 1. The 7 Core Linux Namespaces Detailed

| Namespace | System Flag | What it Isolates |
| :--- | :--- | :--- |
| **PID** | `CLONE_NEWPID` | Process IDs (The process sees itself as PID 1, completely blind to host processes). |
| **Mount** | `CLONE_NEWNS` | Filesystem mount points (`pivot_root` switches `/` to container image). |
| **Network**| `CLONE_NEWNET` | IP addresses, routing tables, port bindings, firewall rules. |
| **UTS** | `CLONE_NEWUTS` | Hostname and NIS domain name. |
| **IPC** | `CLONE_NEWIPC` | System V IPC and POSIX shared memory message queues. |
| **User** | `CLONE_NEWUSER`| User & Group IDs (Root inside container is unprivileged user on host!). |
| **cgroup** | `CLONE_NEWCGROUP`| Isolated view of `/sys/fs/cgroup`. |

---

### 2. Filesystem Jail: `chroot` vs. `pivot_root`

- **`chroot` (Legacy / Insecure)**: Only changes the root directory of the current process. A root process can break out of a `chroot` jail by opening a file descriptor to the old root and calling `fchdir("..")`.
- **`pivot_root` (Production Standard)**: Atomically swaps the entire system root mount with a new directory and unmounts the old host filesystem, making breakout mathematically impossible.

---

### 3. Container Virtual Networking with `veth` Pairs

How does a container get internet access?
1. The host kernel creates a **Virtual Ethernet Pair** (`veth_host` $\leftrightarrow$ `veth_cont`).
2. Moves `veth_cont` into the container's private Network Namespace.
3. Assigns an IP address (`10.0.0.2/24`) to `veth_cont` and brings `lo` and `veth_cont` interfaces up.
4. Connects `veth_host` on the host side to a bridge interface (`docker0` / `br0`) with NAT masquerading (`iptables -t nat -A POSTROUTING`).

## Why It Matters in Systems & Backend Engineering

1. **Building Custom Cloud Runtimes**: Understanding namespaces allows you to build custom sandboxing engines (like AWS Firecracker, `runc`, or Cloudflare Worker isolators).
2. **Rootless Containers for Enterprise Security**: User Namespaces (`CLONE_NEWUSER`) allow developers to run Docker containers safely without `sudo` or root privileges on production nodes.
3. **Debug Container Networking**: Understanding `veth` and net namespaces lets you use `nsenter` to jump directly into a broken Kubernetes pod's network namespace to run packet captures.

## Complete, Compilable Code Example

The following program demonstrates the **Architecture of a Linux Container Runtime Engine in Pure Rust**:

```rust
use std::collections::HashMap;

/// Represents Container Isolation Configuration
#[derive(Debug, Clone)]
pub struct ContainerConfig {
    pub hostname: String,
    pub rootfs_path: String,
    pub ip_address: String,
    pub mapped_uid: u32, // Host UID mapped to Container UID 0 (root)
    pub command: Vec<String>,
}

/// Simulated Container Sandbox Engine
pub struct ContainerRuntime {
    active_containers: HashMap<String, ContainerConfig>,
}

impl ContainerRuntime {
    pub fn new() -> Self {
        Self { active_containers: HashMap::new() }
    }

    /// Simulates unshare() / clone() with 7 Linux Namespaces
    pub fn spawn_isolated_container(&mut self, id: &str, config: ContainerConfig) -> Result<(), &'static str> {
        println!("[RUNTIME] Initializing Linux Namespaces for Container '{}':", id);
        println!("  ✓ CLONE_NEWUTS: Setting isolated hostname to '{}'", config.hostname);
        println!("  ✓ CLONE_NEWPID: Virtualizing PID tree (Container child is PID 1)");
        println!("  ✓ CLONE_NEWNS:  Preparing pivot_root to '{}'", config.rootfs_path);
        println!("  ✓ CLONE_NEWNET: Allocating veth pair and assigning IP '{}'", config.ip_address);
        println!("  ✓ CLONE_NEWUSER: Mapping Host UID {} -> Container Root (UID 0)", config.mapped_uid);
        println!("  ✓ CLONE_NEWIPC: Isolating POSIX message queues and shared memory");
        println!("  ✓ CLONE_NEWCGROUP: Virtualizing /sys/fs/cgroup visibility");

        println!("[RUNTIME] Executing command inside jail: {:?}", config.command);
        self.active_containers.insert(id.to_string(), config);
        Ok(())
    }

    pub fn list_containers(&self) -> Vec<&String> {
        self.active_containers.keys().collect()
    }
}

fn main() {
    println!("=== Linux Container Engine & Namespaces from Scratch ===\n");

    let mut runtime = ContainerRuntime::new();

    let alpine_config = ContainerConfig {
        hostname: "alpine-microservice-01".to_string(),
        rootfs_path: "/var/lib/containers/alpine_root".to_string(),
        ip_address: "10.0.42.2".to_string(),
        mapped_uid: 1000, // Safe unprivileged rootless container!
        command: vec!["/bin/sh".to_string(), "-c".to_string(), "echo 'Inside container' && ps aux".to_string()],
    };

    runtime.spawn_isolated_container("c-9481a", alpine_config).unwrap();

    let containers = runtime.list_containers();
    println!("\nActive Running Sandboxes: {:?}", containers);
    assert_eq!(containers.len(), 1);
}
```

## Common Pitfalls & Server Mistakes

### 1. Forgetting to Mount Private `/proc` in New PID Namespace
- **Cause**: Spawning a process with `CLONE_NEWPID` without creating a new mount namespace and remounting `/proc`. Running `ps aux` inside the container will still show all host processes!
- **Fix**: Combine `CLONE_NEWPID` with `CLONE_NEWNS` and execute `mount -t proc proc /proc` inside the container.

### 2. UID/GID Mapping Permission Failures in User Namespaces
- **Cause**: Attempting to map host UIDs without configuring `/etc/subuid` and `/etc/subgid`.
- **Fix**: Ensure the parent process writes to `/proc/[pid]/uid_map` using authorized subuid ranges.

### Solution 2: Namespace Flags Bitmask Combiner
```rust
pub const CLONE_NEWNS: u64   = 0x00020000;
pub const CLONE_NEWUTS: u64  = 0x04000000;
pub const CLONE_NEWIPC: u64  = 0x08000000;
pub const CLONE_NEWUSER: u64 = 0x10000000;
pub const CLONE_NEWPID: u64  = 0x20000000;
pub const CLONE_NEWNET: u64  = 0x40000000;

pub fn build_clone_flags(isolate_net: bool, isolate_pid: bool, isolate_user: bool) -> u64 {
    let mut flags = CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC;
    if isolate_net { flags |= CLONE_NEWNET; }
    if isolate_pid { flags |= CLONE_NEWPID; }
    if isolate_user { flags |= CLONE_NEWUSER; }
    flags
}

#[test]
fn test_clone_flags() {
    let flags = build_clone_flags(true, true, false);
    assert_eq!(flags & CLONE_NEWNET, CLONE_NEWNET);
    assert_eq!(flags & CLONE_NEWPID, CLONE_NEWPID);
    assert_eq!(flags & CLONE_NEWUSER, 0);
}
```
