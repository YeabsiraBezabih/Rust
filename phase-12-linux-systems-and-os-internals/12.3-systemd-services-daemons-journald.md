## Concept

In modern Linux distributions, **Systemd** is the initial process spawned by the kernel (**PID 1**). It is responsible for:
1. Bootstrapping the operating system and mounting filesystems.
2. Managing the lifecycle of background daemons and microservices (starting, stopping, restarting on crash).
3. Collecting structured system logs via **`systemd-journald`**.
4. Managing cgroups, resource limits, and environment variables for all services.

```

│                    Systemd Service Lifecycle & Supervision                   │
├──────────────────────────────────────────────────────────────────────────────┤
```

### 1. Anatomy of a Production Rust Systemd Unit File

Place unit files at `/etc/systemd/system/rust-api.service`:

```ini
[Unit]
Description=High-Performance Rust Backend API Engine
Documentation=https://docs.mycompany.com/api
After=network.target postgresql.service redis.service
Requires=postgresql.service

[Service]
Type=notify
ExecStart=/usr/local/bin/rust-api-server
WorkingDirectory=/var/www/rust-api
User=backend
Group=backend

# Automatic Restart on Crash / Panic
Restart=always
RestartSec=5s

# Security Hardening Directives
ProtectSystem=strict
ProtectHome=true
NoNewPrivileges=true
PrivateTmp=true

# High-Concurrency Resource Quotas
LimitNOFILE=65536
LimitNPROC=4096

# Environment Injection
EnvironmentFile=/etc/rust-api/production.env

# Systemd Watchdog Heartbeat (Auto-restarts hung deadlocks!)
WatchdogSec=10s

[Install]
WantedBy=multi-user.target
```

### 3. Structured Logging with `journalctl` & Log Rotation

Systemd routes `stdout` and `stderr` directly to `systemd-journald`. Unlike flat text log files, journald logs include metadata (PID, UID, timestamp, unit name, syslog priority):

```bash
# Follow live logs in real time
journalctl -u rust-api -f

# Show logs since last boot with error priority only
journalctl -u rust-api -b -p err

# View logs from a specific timeframe
journalctl -u rust-api --since "2026-09-04 12:00:00" --until "2026-09-04 14:00:00"
```

For flat file logs written to `/var/log/rust-api/`, configure `/etc/logrotate.d/rust-api`:

```ini
/var/log/rust-api/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 backend backend
    sharedscripts
    postrotate
        /usr/bin/systemctl reload rust-api > /dev/null 2>&1 || true
    endscript
}
```

## Why It Matters in Systems & Backend Engineering

1. **Zero-Touch Crash Recovery**: If an uncaught panic or OOM event terminates your Rust service, Systemd automatically respawns it within seconds.
2. **Deadlock Detection via Watchdogs**: By enabling `WatchdogSec=10s`, Systemd will actively terminate and reboot your service if a thread deadlock stops your heartbeat thread.
3. **True Security Isolation**: Using `ProtectSystem=strict` and `NoNewPrivileges=true` ensures that even if an attacker achieves remote code execution in your web app, they cannot overwrite system binaries.

## Complete, Compilable Code Example

The following program implements a **Production-Ready Rust Service Daemon** that supports Systemd `Type=notify` readiness signaling, watchdog heartbeats, and graceful termination:

```rust
use std::env;
use std::os::unix::net::UnixDatagram;
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::Duration;

/// Helper to communicate with Systemd via the NOTIFY_SOCKET Unix datagram socket
pub struct SystemdNotifier {
    socket_path: Option<String>,
}

impl SystemdNotifier {
    pub fn from_env() -> Self {
        let socket_path = env::var("NOTIFY_SOCKET").ok();
        Self { socket_path }
    }

    /// Sends a raw notification state string to Systemd (e.g. "READY=1", "WATCHDOG=1")
    pub fn notify(&self, state: &str) -> bool {
        if let Some(ref path) = self.socket_path {
            if let Ok(socket) = UnixDatagram::unbound() {
                return socket.send_to(state.as_bytes(), path).is_ok();
            }
        }
        false
    }

    pub fn notify_ready(&self) {
        if self.notify("READY=1") {
            println!("[SYSTEMD] Successfully sent READY=1 notification to PID 1");
        } else {
            println!("[INFO] NOTIFY_SOCKET not set (Running standalone/locally)");
        }
    }

    pub fn notify_watchdog(&self) {
        let _ = self.notify("WATCHDOG=1");
    }
}

fn main() {
    println!("=== Rust Production Backend Service Daemon ===");

    let running = Arc::new(AtomicBool::new(true));
    let r_clone = Arc::clone(&running);

    // 1. Setup Signal Handler for Graceful Shutdown (SIGINT / SIGTERM)
    ctrlc::set_handler(move || {
        println!("\n[SHUTDOWN] Received termination signal. Initiating graceful teardown...");
        r_clone.store(false, Ordering::SeqCst);
    }).expect("Error setting signal handler");

    // 2. Perform Service Initialization (e.g. DB migrations, cache warm-up)
    println!("[INIT] Connecting to Database and initializing connection pools...");
    thread::sleep(Duration::from_millis(500)); // Simulate async startup

    // 3. Notify Systemd that we are READY to receive traffic!
    let notifier = SystemdNotifier::from_env();
    notifier.notify_ready();

    println!("[RUNNING] API Server listening on 0.0.0.0:8080");

    // 4. Main Service Loop with Watchdog Heartbeats
    let mut iteration = 0;
    while running.load(Ordering::SeqCst) {
        thread::sleep(Duration::from_millis(1000));
        iteration += 1;

        // Emit Watchdog heartbeat every 2 seconds
        if iteration % 2 == 0 {
            notifier.notify_watchdog();
            println!("[HEARTBEAT] Sent WATCHDOG=1 heartbeat (Health Check OK)");
        }

        if iteration >= 5 {
            println!("[SIMULATION] Work completed. Exiting daemon gracefully.");
            break;
        }
    }

    println!("[STOPPED] Service cleanly stopped.");
}
```

## Common Pitfalls & Server Mistakes

### 1. Using `Type=notify` without Sending `READY=1`
- **Cause**: Configuring `Type=notify` in the `.service` file while forgetting to implement the `NOTIFY_SOCKET` IPC message. Systemd will assume the service failed to initialize and terminate it after `TimeoutStartSec` (default 90s).
- **Fix**: Either call `sd_notify("READY=1")` after startup or change the service type to `Type=simple`.

### 2. High Open File Limit Exhaustion (`EMFILE`)
- **Cause**: High-throughput web servers hitting the default Linux per-process file descriptor limit (`1024`), causing `TcpListener::accept()` to fail.
- **Fix**: Always specify `LimitNOFILE=65536` in the `[Service]` section of your unit file.

## Complete Solutions to Exercises

### Solution 1: Systemd Service Health Check Validator
```rust
use std::env;

pub fn verify_service_environment() -> Result<bool, &'static str> {
    let has_invocation_id = env::var("INVOCATION_ID").is_ok();
    let has_notify_socket = env::var("NOTIFY_SOCKET").is_ok();

    if has_invocation_id || has_notify_socket {
        Ok(true)
    } else {
        Ok(false)
    }
}

#[test]
fn test_systemd_detection() {
    // In standard unit tests outside systemd, should return Ok(false)
    assert_eq!(verify_service_environment().unwrap(), false);
}
```

### Solution 2: Watchdog Failure Simulation
```rust
pub struct HealthMonitor {
    consecutive_failures: u32,
}

impl HealthMonitor {
    pub fn new() -> Self {
        Self { consecutive_failures: 0 }
    }

    pub fn record_check_result(&mut self, is_healthy: bool) -> bool {
        if is_healthy {
            self.consecutive_failures = 0;
            true // Can emit watchdog heartbeat
        } else {
            self.consecutive_failures += 1;
            // Stop sending heartbeat if 3 or more consecutive failures occur!
            self.consecutive_failures < 3
        }
    }
}

#[test]
fn test_watchdog_health_failure() {
    let mut monitor = HealthMonitor::new();
    assert!(monitor.record_check_result(true));
    assert!(monitor.record_check_result(false)); // 1 fail (still ok)
    assert!(monitor.record_check_result(false)); // 2 fails (still ok)
    assert!(!monitor.record_check_result(false)); // 3 fails (TRIGGER REBOOT)
}
```
