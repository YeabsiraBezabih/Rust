## Concept

Historically, Linux security was binary: a process was either **an unprivileged user (UID $\ge$ 1000)** or **the omnipotent `root` user (UID 0)**. If a web server running as root was compromised, the attacker gained unrestricted control of the entire server.

Modern Linux security decomposes root into granular **POSIX Capabilities**, restricts syscalls using **`seccomp-bpf`**, and enforces unprivileged access control using the **Landlock LSM**.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    Defense-in-Depth Linux Security Hierarchy                 │
├──────────────────────────────────────────────────────────────────────────────┤
│  1. POSIX CAPABILITIES (`cap_set_proc`)                                      │
│  Instead of full root: Grant ONLY `CAP_NET_BIND_SERVICE` to bind port 443!    │
│  Drop all other 40+ capabilities (`CAP_SYS_ADMIN`, `CAP_PTRACE`, etc.)      │
│                                                                              │
│  2. `prctl(PR_SET_NO_NEW_PRIVS, 1)`                                          │
│  Guarantees process and all children can NEVER gain privileges via SUID!     │
│                                                                              │
│  3. SECCOMP-BPF (System Call Firewall in Kernel)                             │
│  Process issues `syscall` ──► Intercepted by in-kernel BPF Filter            │
│  • Syscall in Allowlist? (`read`, `write`, `epoll_wait`)  ──► ALLOW          │
│  • Syscall in Blocklist? (`ptrace`, `mount`, `reboot`)    ──► KILL / EPERM   │
│                                                                              │
│  4. LANDLOCK LSM (Programmatic Unprivileged Filesystem & Net Sandboxing)     │
│  Restricts process to `/var/app/data` (Read/Write) and `/etc/ssl` (Read Only)│
└──────────────────────────────────────────────────────────────────────────────┘
```

---

### 1. Granular POSIX Capabilities

Instead of running backend daemons as root, grant only the specific capability required:

| Capability | What It Authorizes |
| :--- | :--- |
| **`CAP_NET_BIND_SERVICE`** | Bind to privileged ports below 1024 (e.g. 80, 443). |
| **`CAP_NET_RAW`** | Open raw sockets (`AF_PACKET`) for packet inspection. |
| **`CAP_SYS_PTRACE`** | Attach to and inspect memory of other processes via `ptrace`. |
| **`CAP_SYS_CHROOT`** | Call `chroot()`. |
| **`CAP_SYS_ADMIN`** | "The New Root": Mount filesystems, manage cgroups, load eBPF. |

Grant capability to a Rust binary without root:
```bash
sudo setcap 'cap_net_bind_service=+ep' ./my_api_server
```

---

### 2. `seccomp-bpf`: System Call Filtering

**Secure Computing Mode (`seccomp`)** lets a process define a strict allowlist of permitted syscalls using a Berkeley Packet Filter (BPF) bytecode program:

1. Process initializes: Loads config, connects to database, opens listening sockets.
2. Process locks itself down: Calls `prctl(PR_SET_NO_NEW_PRIVS)` and loads the `seccomp` filter.
3. If an attacker injects shellcode trying to invoke `execve("/bin/sh")` or `socket()`, the kernel instantly terminates the process (`SECCOMP_RET_KILL_PROCESS`) or returns an error (`SECCOMP_RET_ERRNO`).

---

### 3. Landlock LSM: Unprivileged Filesystem Sandboxing

Introduced in Linux 5.13, **Landlock** allows any unprivileged application to restrict its own filesystem access from within Rust:
- Explicitly allow read/write access to `/tmp/app/` and read-only access to `/usr/share/zoneinfo`.
- All other filesystem access attempts are rejected by the kernel with `EACCES`.

---

## Why It Matters in Systems & Backend Engineering

1. **Neutralizing Zero-Day RCE Exploits**: Even if an attacker finds a Remote Code Execution vulnerability in a JSON parser, an active `seccomp` filter prevents them from executing shell binaries or opening reverse shell sockets.
2. **Hardened Production Containers**: Docker and Kubernetes enforce default `seccomp` and capability profiles (dropping `CAP_SYS_ADMIN`, `CAP_NET_RAW`) on every container.
3. **Defense-in-Depth for Microservices**: Applying `seccomp` and capability dropping before entering the main request loop prevents lateral movement across a server fleet.

---

## Real-World Analogy

- **Running as Root** is like giving a hotel guest a master skeleton key that unlocks every hotel room, the cash safe, and the electrical circuit room.
- **POSIX Capabilities** is giving the guest an electronic keycard that only unlocks their specific room door (**`CAP_NET_BIND_SERVICE`**).
- **`seccomp-bpf`** is like a security guard stationed in the hallway with a clipboard list of approved actions: if the guest attempts an unapproved action (**Calling `execve`**), the guard immediately escorts them off the premises (**Process Killed**).

## Complete, Compilable Code Example

The following program demonstrates a **Syscall Security Policy Engine & Capability Validator in Pure Rust**:

```rust
use std::collections::HashSet;

/// Seccomp Action Verdicts
#[derive(Debug, PartialEq, Eq, Clone, Copy)]
pub enum SeccompAction {
    Allow,
    KillProcess,
    ReturnErrno(i32),
}

/// Simulated Seccomp-BPF Syscall Filter Engine
pub struct SeccompPolicyEngine {
    allowed_syscalls: HashSet<u32>,
    default_action: SeccompAction,
    is_locked: bool,
}

impl SeccompPolicyEngine {
    pub fn new(default_action: SeccompAction) -> Self {
        Self {
            allowed_syscalls: HashSet::new(),
            default_action,
            is_locked: false,
        }
    }

    /// Add permitted syscall number (e.g. read=0, write=1, epoll_wait=232)
    pub fn allow_syscall(&mut self, syscall_id: u32) -> Result<(), &'static str> {
        if self.is_locked {
            return Err("Cannot modify policy: Seccomp filter is locked!");
        }
        self.allowed_syscalls.insert(syscall_id);
        Ok(())
    }

    /// Irrevocably locks the filter (Simulating PR_SET_NO_NEW_PRIVS + seccomp load)
    pub fn lock_filter(&mut self) {
        self.is_locked = true;
        println!("[SECCOMP] Policy locked irrevocably. PR_SET_NO_NEW_PRIVS active.");
    }

    /// Evaluates a syscall against the active security profile
    pub fn evaluate_syscall(&self, syscall_id: u32) -> SeccompAction {
        if self.allowed_syscalls.contains(&syscall_id) {
            SeccompAction::Allow
        } else {
            self.default_action
        }
    }
}

fn main() {
    println!("=== Linux Security Architecture & Seccomp-BPF Filter Engine ===\n");

    let mut engine = SeccompPolicyEngine::new(SeccompAction::KillProcess);

    // 1. Configure strict allowlist for an HTTP API worker
    println!("Configuring Whitelisted Syscalls for Worker Process:");
    engine.allow_syscall(0).unwrap();   // sys_read
    engine.allow_syscall(1).unwrap();   // sys_write
    engine.allow_syscall(232).unwrap(); // sys_epoll_wait
    engine.allow_syscall(60).unwrap();  // sys_exit
    println!("  ✓ Whitelisted: read (0), write (1), epoll_wait (232), exit (60)");

    // 2. Lock security boundary
    engine.lock_filter();

    // 3. Test permitted operation (write)
    let verdict_write = engine.evaluate_syscall(1);
    println!("\nExecuting sys_write (Syscall 1) ──► Verdict: {:?}", verdict_write);
    assert_eq!(verdict_write, SeccompAction::Allow);

    // 4. Test blocked malicious operation (execve = syscall 59)
    let verdict_execve = engine.evaluate_syscall(59);
    println!("Attacker attempts sys_execve (Syscall 59) ──► Verdict: {:?}", verdict_execve);
    assert_eq!(verdict_execve, SeccompAction::KillProcess);

    // 5. Verify policy cannot be tampered with after lock
    let modify_attempt = engine.allow_syscall(59);
    println!("Attempting to tamper with locked policy: {:?}", modify_attempt);
    assert!(modify_attempt.is_err());
}
```

## Common Pitfalls & Server Mistakes

### 1. Blocking Required Startup Syscalls in Seccomp
- **Cause**: Locking down seccomp filters *before* initializing dynamic memory allocators or opening log files. Syscalls like `mmap`, `brk`, or `openat` get blocked, causing the application to terminate on startup.
- **Fix**: Perform all startup initializations first, and apply `seccomp` immediately before entering the main worker loop.

### 2. Forgetting `PR_SET_NO_NEW_PRIVS`
- **Cause**: Attempting to load a `seccomp` filter as an unprivileged user without calling `prctl(PR_SET_NO_NEW_PRIVS, 1)`. The kernel rejects the filter with `EPERM`.
- **Fix**: Always set `PR_SET_NO_NEW_PRIVS` before loading unprivileged BPF filters.

## Complete Solutions to Exercises

### Solution 1: Seccomp Profile Allowlist Builder
```rust
pub fn build_web_worker_seccomp_profile() -> SeccompPolicyEngine {
    let mut engine = SeccompPolicyEngine::new(SeccompAction::KillProcess);
    let essential_syscalls = [
        0,   // sys_read
        1,   // sys_write
        3,   // sys_close
        60,  // sys_exit
        202, // sys_futex
        232, // sys_epoll_wait
    ];

    for &id in &essential_syscalls {
        engine.allow_syscall(id).unwrap();
    }
    engine.lock_filter();
    engine
}

#[test]
fn test_worker_profile() {
    let profile = build_web_worker_seccomp_profile();
    assert_eq!(profile.evaluate_syscall(0), SeccompAction::Allow);
    assert_eq!(profile.evaluate_syscall(202), SeccompAction::Allow);
    assert_eq!(profile.evaluate_syscall(59), SeccompAction::KillProcess); // execve blocked
}
```

### Solution 2: POSIX Capability String Formatter
```rust
pub fn format_cap_flags(caps: &[&str]) -> String {
    format!("{}+ep", caps.join(","))
}

#[test]
fn test_cap_formatter() {
    let caps = ["cap_net_bind_service", "cap_net_raw"];
    assert_eq!(format_cap_flags(&caps), "cap_net_bind_service,cap_net_raw+ep");
}
```
