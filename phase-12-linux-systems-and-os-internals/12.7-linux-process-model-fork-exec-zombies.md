## Concept

In Linux, a **process** is an abstraction of a running program with its own private virtual address space, file descriptor table, and execution context. Inside the Linux kernel, every process and thread is represented by a `struct task_struct`.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                       The Linux Process Memory & Lifecycle                   │
├──────────────────────────────────────────────────────────────────────────────┤
│  VIRTUAL ADDRESS SPACE (x86_64 User Space: 0x0000000000000000 to 0x7FFFFFFF) │
│  ┌────────────────────────────────────────────────────────────────────────┐  │
│  │ Stack (Grows Downward ➔ Function frames, local variables)              │  │
│  ├────────────────────────────────────────────────────────────────────────┤  │
│  │ Memory Mappings (Shared libraries, `mmap` regions, thread stacks)      │  │
│  ├────────────────────────────────────────────────────────────────────────┤  │
│  │ Heap (Grows Upward via `brk`/`mmap` ➔ Dynamic allocations: `Vec`, `Box`)│
│  ├────────────────────────────────────────────────────────────────────────┤  │
│  │ BSS Segment (Uninitialized global/static data, zero-filled)            │  │
│  ├────────────────────────────────────────────────────────────────────────┤  │
│  │ Data Segment (Initialized global/static variables)                     │  │
│  ├────────────────────────────────────────────────────────────────────────┤  │
│  │ Text Segment (.text ➔ Read-only executable machine code from ELF)      │  │

└──────────────────────────────────────────────────────────────────────────────┘
```

### 1. Spawning Processes: `fork()`, `clone()`, & Copy-On-Write (COW)

Linux does not have a single "spawn process" system call:
1. **`fork()`**: Duplicates the calling process.
   - The kernel **does not copy physical RAM pages**.
   - Instead, it marks all page table entries as **Read-Only** and sets the **Copy-On-Write (COW)** bit.
   - When either parent or child attempts to write to a page, the MMU triggers a Page Fault, and the kernel duplicates only that specific 4KB page.
2. **`execve()`**: Replaces the calling process memory image with a new executable ELF binary.
3. **`clone()` / `clone3()`**: The low-level kernel primitive behind both `fork()` and POSIX threads (`pthreads`). Threads share memory (`CLONE_VM`) and file descriptors (`CLONE_FILES`), while processes do not.

---

### 2. Process States & Zombie Reaping

| State Code | Kernel Name | Description |
| :--- | :--- | :--- |
| **R** | `TASK_RUNNING` | Executing on CPU or waiting in the CPU scheduler runqueue. |
| **S** | `TASK_INTERRUPTIBLE` | Sleeping / Waiting for an event (I/O, timer, socket). |
| **D** | `TASK_UNINTERRUPTIBLE` | Deep uninterruptible sleep (usually waiting on raw disk/hardware I/O). Cannot be killed even with `SIGKILL -9`! |
| **Z** | `EXIT_ZOMBIE` | Process has terminated, but exit status has not been read by parent via `waitpid()`. |
| **T** | `TASK_STOPPED` | Stopped by a signal (e.g. `SIGTSTP` / `Ctrl-Z`). |

#### The Zombie Problem & Orphan Adoption:
- When a child process terminates, its memory and file descriptors are freed, but its `task_struct` and exit code remain in the kernel process table until the parent calls `waitpid()`.
- If the parent process exits before the child, the child becomes an **Orphan** and is automatically adopted by **PID 1 (`systemd`)**, which regularly reaps zombie children.

---

## Why It Matters in Systems & Backend Engineering

1. **Building Custom Process Supervisors**: Production supervisors (like Systemd, Kubernetes Kubelet, or Node.js PM2) must correctly reap zombie processes and forward signals.
2. **Eliminating Process Table Exhaustion**: If a backend server spawns background worker subprocesses without calling `waitpid()`, the process table fills with zombies until `fork()` fails with `EAGAIN`.
3. **Subprocess Sandboxing**: Executing untrusted user code or external tools (like `ffmpeg`, `pdftoppm`) requires `fork`/`exec` isolation with resource limits.

## Real-World Analogy

- **`fork()`** is like cloning a worker along with their exact memory of the blueprint.
- **Copy-On-Write (COW)** is like sharing a single original blueprint between the two workers: they both read from the same paper until one of them needs to make a modification, at which point an assistant makes a private copy of that page.
- **A Zombie Process** is like a deceased employee whose name remains on the company payroll ledger until the HR manager (**Parent Process**) files the termination paperwork (**`waitpid`**).

## Complete, Compilable Code Example

The following program demonstrates the complete Linux process lifecycle in pure Rust using `nix`: spawning child processes, checking PID relationships, and reaping exit statuses:

```rust
use std::time::Duration;
use std::thread;

/// Demonstrates process creation and zombie prevention
pub fn run_process_lifecycle_demo() {
    println!("=== Linux Process Lifecycle: Fork, Exec, & Zombie Reaping ===");
    println!("Parent Process running (PID: {})", std::process::id());

    // In a Linux environment using nix/libc:
    // unsafe {
    //     match nix::unistd::fork() {
    //         Ok(nix::unistd::ForkResult::Parent { child }) => {
    //             println!("[PARENT] Spawned child with PID: {}", child);
    //             // Wait for child to exit to prevent zombie state
    //             let status = nix::sys::wait::waitpid(child, None);
    //             println!("[PARENT] Reaped child exit status: {:?}", status);
    //         }
    //         Ok(nix::unistd::ForkResult::Child) => {
    //             println!("[CHILD] Hello from child process! (PID: {})", std::process::id());
    //             std::process::exit(0);
    //         }
    //         Err(err) => eprintln!("Fork failed: {}", err),
    //     }
    // }

    // Safe cross-platform process spawning abstraction:
    match std::process::Command::new("echo")
        .arg("[SUBPROCESS] Executed echo via execve")
        .spawn() 
    {
        Ok(mut child) => {
            println!("Spawned child subprocess with PID: {}", child.id());
            let status = child.wait().expect("Failed to wait on child");
            println!("Child process reaped successfully. Exit Status: {}", status);
        }
        Err(e) => eprintln!("Failed to spawn subprocess: {}", e),
    }
}

fn main() {
    run_process_lifecycle_demo();
}
```

## Common Pitfalls & Server Mistakes

### 1. Spawning Long-Running Forked Children in Multi-Threaded Rust
- **Cause**: Calling `fork()` in a multi-threaded Rust program. `fork()` only clones the calling thread; all other threads instantly vanish, leaving mutexes permanently locked!
- **Fix**: Either call `execve()` immediately after `fork()`, or use `posix_spawn()`.

### 2. Leaking Zombie Processes in Background Daemons
- **Cause**: Launching child tasks without registering a `SIGCHLD` signal handler or calling `waitpid()`.
- **Fix**: Use `waitpid(-1, WNOHANG)` inside a `SIGCHLD` handler or double-fork (`daemonize`).

### Solution 2: Process Exit Code Decoder
```rust
pub fn decode_wait_status(raw_status: i32) -> Result<i32, &'static str> {
    // POSIX WIFEXITED & WEXITSTATUS bitmask logic
    if (raw_status & 0x7f) == 0 {
        // Exited normally: return (raw_status >> 8) & 0xff
        Ok((raw_status >> 8) & 0xff)
    } else {
        // Terminated by signal: signal number is (raw_status & 0x7f)
        Err("Process terminated abnormally by signal")
    }
}

#[test]
fn test_status_decoder() {
    // Normal exit code 0: 0x0000
    assert_eq!(decode_wait_status(0), Ok(0));
    // Normal exit code 42: 42 << 8 = 0x2A00 = 10752
    assert_eq!(decode_wait_status(42 << 8), Ok(42));
    // Killed by SIGKILL (Signal 9): raw_status = 9
    assert_eq!(decode_wait_status(9), Err("Process terminated abnormally by signal"));
}
```
