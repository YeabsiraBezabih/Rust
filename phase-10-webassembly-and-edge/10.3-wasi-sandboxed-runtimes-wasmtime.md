## Concept

When Docker co-founder Solomon Hykes famously tweeted:
> *"If WASM+WASI existed in 2008, we wouldn't have needed to create Docker. That's how important it is. WebAssembly on the server is the future of computing."*

He was referring to **WASI (WebAssembly System Interface)**: a standard interface that allows WebAssembly modules to run **outside the browser** on bare metal, servers, and embedded devices with **Capability-Based Security** and sub-millisecond startup times.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Container vs WASM Sandbox                       │
├───────────────────────────────┬────────────────────────────────────────┤
│ Docker / OCI Container        │ WASI Sandboxed Engine (Wasmtime)       │
├───────────────────────────────┼────────────────────────────────────────┤
│ • Heavy image size (50MB–1GB) │ • Microscopic binary size (100KB–10MB) │
│ • Slow cold start (200ms–2s)  │ • Instant cold start (< 1ms / 50μs)    │
│ • Full Linux kernel syscalls  │ • Zero ambient authority / capabilities│
│ • High RAM overhead (~30MB)   │ • Ultra-low RAM overhead (~1MB)        │
└───────────────────────────────┴────────────────────────────────────────┘
```

### 1. Capability-Based Security in WASI

In traditional operating systems (POSIX), programs run with **Ambient Authority**: if your application runs as user `yeab`, any imported library can read `~/.ssh/id_rsa`, connect to a command-and-control server, or delete `/tmp`.

In **WASI**, a WebAssembly module has **ZERO ambient authority**:
- It cannot open any file unless the host runner explicitly passes a **pre-opened directory capability**.
- It cannot open any network socket unless explicitly granted by the host.
- It cannot read the system clock or random generator unless authorized.

```rust
// Wasmtime Host Configuration: Explicitly granting capabilities
let wasi = WasiCtxBuilder::new()
    .inherit_stdout()
    .preopened_dir(dir, "/sandbox_data")? // Can ONLY access /sandbox_data!
    .build();
```

### 2. Building a Safe Plugin Engine with Wasmtime

You can embed **Wasmtime** inside your Rust backend to allow users to upload custom untrusted `.wasm` scripts (like custom database triggers, smart contracts, or webhook filters) with two strict safety guarantees:

1. **Fuel Consumption Limits**: Every WASM instruction consumes "fuel". If a user writes `loop {}`, execution halts immediately after consuming allocated fuel, **preventing CPU denial-of-service**.
2. **Hard Memory Limits**: Enforces a strict upper bound on linear memory (e.g. max 32MB).

```rust
use wasmtime::*;

let mut config = Config::new();
config.consume_fuel(true); // Enables instruction counting

let engine = Engine::new(&config)?;
let mut store = Store::new(&engine, ());
store.set_fuel(10_000_000)?; // 10 Million instructions budget
```

## Why It Matters in Systems Programming

1. **Sub-Millisecond Cold Starts**: Wasmtime can instantiate a fresh WASM sandboxed module in **$30\text{ microseconds}$** ($10,000\times$ faster than a Linux container).
2. **Safe Multi-Tenant Plugin Architectures**: Run untrusted user code safely inside your database or web server without fear of server compromise.
3. **The Component Model (WASI Preview 2)**: Language-agnostic modular composition allowing Rust, Python, Go, and C++ WASM components to link together seamlessly.

## Complete, Compilable Code Example

Below is a complete, self-contained implementation demonstrating a **Sandboxed WASM Plugin Engine with Fuel Execution Limits** in pure Rust:

```rust
// ============================================================================
// 1. Sandboxed Plugin VM with Instruction Fuel Metering
// ============================================================================

pub struct SandboxedPluginVm {
    fuel_remaining: u64,
    memory: Vec<u8>,
    max_memory_bytes: usize,
}

impl SandboxedPluginVm {
    pub fn new(initial_fuel: u64, max_memory_bytes: usize) -> Self {
        Self {
            fuel_remaining: initial_fuel,
            memory: vec![0u8; 1024], // 1KB initial sandbox
            max_memory_bytes,
        }
    }

    /// Consume fuel per virtual instruction
    pub fn consume_fuel(&mut self, amount: u64) -> Result<(), &'static str> {
        if self.fuel_remaining < amount {
            return Err("ExecutionTrapped: Out of Fuel! (Infinite loop prevented)");
        }
        self.fuel_remaining -= amount;
        Ok(())
    }

    /// Execute a simulated plugin script calculating a discount code
    pub fn execute_discount_rule(&mut self, order_total_cents: u64) -> Result<u64, &'static str> {
        self.consume_fuel(100)?; // Setup cost

        // Simulate complex plugin logic
        let mut discount = 0u64;
        if order_total_cents > 10_000 {
            self.consume_fuel(50)?;
            discount = order_total_cents / 10; // 10% discount
        }

        self.consume_fuel(50)?;
        Ok(discount)
    }

    /// Simulate an untrusted malicious plugin attempting an infinite loop
    pub fn execute_malicious_script(&mut self) -> Result<(), &'static str> {
        println!("  Executing untrusted plugin with infinite loop...");
        loop {
            // Each loop iteration consumes fuel
            self.consume_fuel(1_000)?;
        }
    }
}

// ============================================================================
// 2. Verification & Sandboxed Execution
// ============================================================================

fn main() {
    println!("=== 1. Executing Safe User Plugin with WASI Fuel Metering ===");
    let mut vm = SandboxedPluginVm::new(100_000, 32 * 1024 * 1024);

    let order_amount = 25_000; // $250.00
    let discount = vm.execute_discount_rule(order_amount).unwrap();
    println!("Order Amount: ${:.2}", order_amount as f64 / 100.0);
    println!("Plugin Calculated Discount: ${:.2}", discount as f64 / 100.0);
    println!("Fuel Remaining: {} / 100,000 units\n", vm.fuel_remaining);

    println!("=== 2. Executing Malicious Plugin (Infinite Loop Trap) ===");
    let mut malicious_vm = SandboxedPluginVm::new(50_000, 1024);
    let trap_result = malicious_vm.execute_malicious_script();

    println!("Malicious Execution Result: {:?}", trap_result);
    assert!(trap_result.is_err());
    println!("✅ Host successfully trapped execution when fuel exhausted!");
}
```

## Common Pitfalls & Compiler Errors

### 1. Forgetting to Enable Fuel Metering on Untrusted Plugins
If you load untrusted third-party WASM modules in Wasmtime without configuring `consume_fuel(true)` or epoch interruption, a malicious plugin can execute `while true {}` and lock up a 100% CPU thread indefinitely.

### 2. Leaking Host File Descriptors
When configuring the WASI context (`WasiCtx`), passing standard input or root directories without restriction compromises the capability sandbox.

## Complete Solutions to Exercises

### Solution 1: Path Traversal Defense
In WASI, file operations take a directory file descriptor handle (e.g. `fd_read(dir_fd, path)`). The WASI runtime validates that every relative path resolves strictly inside the subtree of `dir_fd`, mathematically rejecting any `..` references that escape the pre-opened directory boundary.
