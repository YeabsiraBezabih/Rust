## Concept

In production backend engineering, writing SQL queries that work is only 20% of the job. The remaining 80% is ensuring queries run in sub-millisecond time under heavy database load.

To optimize queries, a systems engineer must read the database's internal **Query Execution Plan** using `EXPLAIN (ANALYZE, BUFFERS)` and choose the optimal **Indexing Strategy**.

```
                        EXPLAIN ANALYZE Execution Pipeline
┌────────────────────────────────────────────────────────────────────────┐
│  SQL Query ──► [ Planner / Cost Estimator ]                            │
│                 - Estimates Startup Cost & Total Cost                  │
│                 - Analyzes Table Statistics (pg_statistic / ANALYZE)   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  Plan Nodes (Evaluated Bottom-Up):                                     │
│                                                                        │
│  1. Seq Scan:           Reads all 8KB pages sequentially.              │
│  2. Index Scan:         Traverses B-Tree ➔ Fetches Row from Heap.      │
│  3. Index Only Scan:    Traverses B-Tree ➔ Data in Index (ZERO HEAP)!  │
│  4. Bitmap Index Scan:  Builds in-memory bitmask of matching pages.    │
└────────────────────────────────────────────────────────────────────────┘
```

---

### 1. Reading PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`

When profiling a slow query, prefix it with `EXPLAIN (ANALYZE, BUFFERS, COSTS, VERBOSE)`:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, email, balance_cents 
FROM accounts 
WHERE email = 'alice@example.com';
```

#### Output Analysis:
```text
Index Scan using idx_accounts_email on accounts  (cost=0.42..8.44 rows=1 width=48) (actual time=0.035..0.037 rows=1 loops=1)
  Index Cond: (email = 'alice@example.com'::text)
  Buffers: shared hit=4
Planning Time: 0.082 ms
Execution Time: 0.054 ms
```

- **`cost=0.42..8.44`**: Estimated startup cost (`0.42`) and total cost (`8.44`) in arbitrary disk page fetch units.
- **`actual time=0.035..0.037`**: Real elapsed wall-clock time in milliseconds.
- **`Buffers: shared hit=4`**: Number of 8KB buffer pool pages read from RAM. `hit` means cached in RAM; `read` means read from physical disk/NVMe.

### 2. Specialized Indexing Types in PostgreSQL

| Index Type | Best Used For | Example Query |
| :--- | :--- | :--- |
| **B-Tree** *(Default)* | Exact match, range checks, sorting | `WHERE age >= 21 ORDER BY created_at` |
| **GIN** *(Inverted)* | JSONB containment, full-text search, arrays | `WHERE metadata @> '{"role": "admin"}'` |
| **BRIN** *(Block Range)* | Massive append-only time-series tables (100GB+) | `WHERE created_at > '2026-01-01'` |
| **Partial Index** | Indexing only a subset of frequent rows | `CREATE INDEX idx ON orders (id) WHERE status = 'PENDING'` |
| **Covering Index** (`INCLUDE`) | Zero Heap reads (**Index Only Scan**) | `CREATE INDEX idx ON users (email) INCLUDE (balance)` |

---

### 3. The Leftmost Prefix Rule for Composite Indexes

If you create a composite index on 3 columns:
```sql
CREATE INDEX idx_user_search ON users (country, department, salary);
```

The database can use this index for:
- `WHERE country = 'US'` ✅
- `WHERE country = 'US' AND department = 'ENG'` ✅
- `WHERE country = 'US' AND department = 'ENG' AND salary > 100000` ✅

The database **CANNOT** use this index efficiently for:
- `WHERE department = 'ENG'` ❌ (Missing leftmost column `country`)
- `WHERE salary > 100000` ❌ (Missing leftmost columns)

### 4. Keyset (Cursor) Pagination vs `OFFSET` Bloat

#### The `OFFSET` Anti-Pattern ($O(N)$ Disk I/O):
```sql
-- Page 500: Database must read 50,000 rows from disk, sort them, and throw away 49,980!
SELECT id, title FROM posts ORDER BY id DESC LIMIT 20 OFFSET 50000;
```

#### The Keyset Pagination Solution ($O(1)$ B-Tree Direct Seek):
```sql
-- Direct O(log N) jump straight to next 20 rows using last seen ID
SELECT id, title FROM posts WHERE id < 14920 ORDER BY id DESC LIMIT 20;
```

---

## Why It Matters in Systems Programming

1. **Eliminate Full Table Scans**: Converting a `Seq Scan` on a 10M row table to an `Index Only Scan` drops query latency from $850\text{ms}$ to $0.05\text{ms}$ ($17,000\times$ speedup).
2. **Reduce Buffer Pool Thrashing**: Sequential scans on huge tables flush active cached pages out of PostgreSQL's buffer pool, degrading performance across the entire database.
3. **Optimized Pagination for High-Traffic APIs**: Keyset pagination maintains constant sub-millisecond response times regardless of whether the user requests Page 1 or Page 100,000.

---

## Real-World Analogy

- **Sequential Scan (`Seq Scan`)** is searching for a specific book by walking through every aisle of a 10-story library and inspecting every single shelf one by one.
- **Index Scan** is checking the librarian catalog computer to get the aisle and shelf number, then walking to that shelf to pick up the book.
- **Index-Only Scan (Covering Index)** is looking at the catalog computer, and seeing that the catalog screen already displays the exact answer you wanted (e.g. the publication year and title) so you don't even have to walk to the physical shelf at all!

## Complete, Compilable Code Example

Below is a complete Rust simulation of a **B-Tree Index Scan vs Table Heap Scan Engine** demonstrating cost estimation, buffer page counting, and keyset pagination:

```rust
use std::collections::BTreeMap;
use std::time::Instant;

// ============================================================================
// 1. Storage & Index Simulation
// ============================================================================

#[derive(Debug, Clone)]
pub struct TableRow {
    pub id: u64,
    pub username: String,
    pub status: String,
    pub score: u32,
}

pub struct DatabaseTable {
    pub rows: Vec<TableRow>,                       // Table Heap File
    pub primary_index: BTreeMap<u64, usize>,       // B-Tree on ID (Primary Key)
    pub score_index: BTreeMap<u32, Vec<usize>>,    // Secondary B-Tree on Score
}

impl DatabaseTable {
    pub fn new() -> Self {
        Self {
            rows: Vec::new(),
            primary_index: BTreeMap::new(),
            score_index: BTreeMap::new(),
        }
    }

    pub fn insert(&mut self, id: u64, username: &str, status: &str, score: u32) {
        let row_idx = self.rows.len();
        let row = TableRow {
            id,
            username: username.to_string(),
            status: status.to_string(),
            score,
        };

        self.rows.push(row);
        self.primary_index.insert(id, row_idx);
        self.score_index.entry(score).or_default().push(row_idx);
    }

    /// 1. Sequential Scan: O(N) heap scan
    pub fn seq_scan_by_score(&self, min_score: u32) -> (Vec<&TableRow>, usize) {
        let mut pages_inspected = 0;
        let mut results = Vec::new();

        for row in &self.rows {
            pages_inspected += 1;
            if row.score >= min_score {
                results.push(row);
            }
        }
        (results, pages_inspected)
    }

    /// 2. B-Tree Index Scan: O(log N + K) index range seek
    pub fn index_scan_by_score(&self, min_score: u32) -> (Vec<&TableRow>, usize) {
        let mut pages_inspected = 0;
        let mut results = Vec::new();

        // Direct B-Tree range traversal
        for (_score, row_indices) in self.score_index.range(min_score..) {
            pages_inspected += 1; // Index node read
            for &idx in row_indices {
                pages_inspected += 1; // Heap page read
                results.push(&self.rows[idx]);
            }
        }
        (results, pages_inspected)
    }

    /// 3. Keyset (Cursor) Pagination: O(Limit)
    pub fn paginate_keyset(&self, last_seen_id: u64, limit: usize) -> Vec<&TableRow> {
        let mut results = Vec::new();
        // Traverse primary B-Tree starting strictly after last_seen_id
        for (&id, &row_idx) in self.primary_index.range(last_seen_id + 1..) {
            results.push(&self.rows[row_idx]);
            if results.len() == limit {
                break;
            }
        }
        results
    }
}

// ============================================================================
// 2. Benchmarking & Verification
// ============================================================================

fn main() {
    println!("=== 1. Populating Simulated Table with 100,000 Records ===");
    let mut table = DatabaseTable::new();
    for i in 1..=100_000 {
        let score = (i % 1000) as u32; // Scores 0 to 999
        let status = if i % 2 == 0 { "ACTIVE" } else { "INACTIVE" };
        table.insert(i, &format!("user_{}", i), status, score);
    }
    println!("Table populated successfully with 100,000 rows.\n");

    println!("=== 2. Comparing Seq Scan vs B-Tree Index Scan (Score >= 995) ===");
    
    // Test Seq Scan
    let start = Instant::now();
    let (seq_results, seq_pages) = table.seq_scan_by_score(995);
    let seq_time = start.elapsed();
    println!("Seq Scan:        Found {} rows | Inspected {} pages | Time: {:?}", seq_results.len(), seq_pages, seq_time);

    // Test Index Scan
    let start = Instant::now();
    let (idx_results, idx_pages) = table.index_scan_by_score(995);
    let idx_time = start.elapsed();
    println!("Index Scan:      Found {} rows | Inspected {} pages | Time: {:?}", idx_results.len(), idx_pages, idx_time);

    let speedup = seq_pages as f64 / idx_pages as f64;
    println!("Page I/O Reduction: {:.1}x fewer buffer reads using Index Scan!\n", speedup);

    println!("=== 3. Testing Keyset Cursor Pagination (Page Size: 5) ===");
    let page_1 = table.paginate_keyset(0, 5);
    println!("Page 1 IDs: {:?}", page_1.iter().map(|r| r.id).collect::<Vec<_>>());

    let last_id = page_1.last().unwrap().id;
    let page_2 = table.paginate_keyset(last_id, 5);
    println!("Page 2 IDs: {:?}", page_2.iter().map(|r| r.id).collect::<Vec<_>>());
}
```

## Common Pitfalls & Compiler Errors

### 1. Wrapping Indexed Columns in Functions
Writing:
```sql
SELECT * FROM users WHERE LOWER(email) = 'satoshi@bitcoin.org';
```
PostgreSQL cannot use a standard index on `email` because it indexes the raw bytes, not the result of `LOWER()`.
**Fix**: Create a functional expression index: `CREATE INDEX idx_users_lower_email ON users (LOWER(email));`.

### 2. High `OFFSET` Memory Exhaustion
Using `OFFSET 1000000` requires PostgreSQL to allocate memory, execute query sorting, and discard 1 million rows before returning 10. Always use **Keyset (Cursor) pagination** with `(created_at, id) < ($1, $2)` in high-scale systems.

## Complete Solutions to Exercises

### Solution 1: Index-Only Scan Simulation

```rust
impl DatabaseTable {
    /// Pure Index-Only Scan: Counts matching rows with 0 table heap reads
    pub fn index_only_count(&self, min_score: u32) -> usize {
        self.score_index
            .range(min_score..)
            .map(|(_score, indices)| indices.len())
            .sum()
    }
}
```

### Solution 2: Two-Column Keyset Pagination SQL

```sql
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```
