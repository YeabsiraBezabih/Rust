## Concept

To write high-performance backend systems in Rust that interact with relational databases (PostgreSQL, MySQL, SQLite), a systems programmer cannot treat the database as a "black box". You must understand the physical storage layer, memory caching (buffer pool), write-ahead logging (WAL), indexing mechanisms, and relational algebra.

### 1. The Physical Storage Unit: Slotted Pages (8KB Blocks)

Relational database engines store rows inside fixed-size disk blocks called **Pages** (default 8KB in PostgreSQL).

A Page contains:
1. **Page Header**: 24 bytes containing LSN (Log Sequence Number), checksums, and free space pointers.
2. **Item Pointers (Line Pointers)**: An array of `(offset, length)` tuples growing from top to bottom.
3. **Free Space**: Unallocated byte area in the middle.
4. **Tuple (Row) Data**: Physical row records growing from bottom to top.

```
┌────────────────────────────────────────────────────────┐
│ Page Header (24B: LSN, flags, lower/upper pointers)    │
├────────────────────────────────────────────────────────┤
│ Line Pointer 1 [offset=8120, len=76] ───┐              │
│ Line Pointer 2 [offset=8040, len=80] ───┼─┐            │
│ Line Pointer 3 [offset=7950, len=90] ───┼─┼─┐          │
├─────────────────────────────────────────┼─┼─┼──────────┤
│                  ◄── FREE SPACE ──►     │ │ │          │
├─────────────────────────────────────────┼─┼─┼──────────┤
│ Tuple 3 Data (90 bytes)  ◄──────────────┼─┼─┘          │
├─────────────────────────────────────────┼─┼────────────┤
│ Tuple 2 Data (80 bytes)  ◄──────────────┼─┘            │
├─────────────────────────────────────────┼──────────────┤
│ Tuple 1 Data (76 bytes)  ◄──────────────┘              │
└────────────────────────────────────────────────────────┘
```

**Why Slotted Pages Matter**:
When a row is updated or deleted, the database only adjusts the 4-byte line pointer. The tuple ID (`ctid` in Postgres) is `(page_number, line_pointer_index)`, providing stable row addresses without needing full page defragmentation on every write.

---

### 2. Write-Ahead Logging (WAL) & Durability

Disk writes to arbitrary 8KB table pages are **random I/O** (slow).
To guarantee ACID durability without crippling write throughput:
1. Every insert/update/delete operation writes an append-only delta record to the **Write-Ahead Log (WAL)**.
2. The WAL record is immediately flushed to disk via `fsync()`. (Fast **sequential I/O**).
3. The in-memory 8KB page in the **Buffer Pool** is marked *dirty*.
4. A background process (Checkpointer) lazily flushes dirty pages from RAM to disk table files later.
5. If the server loses power, crash recovery replays the WAL from the last checkpoint to restore corrupted/unflushed pages.

---

### 3. B-Tree Indexes & Point Lookups

Without an index, finding a row requires a **Sequential Scan** ($O(N)$ disk page reads).
A **B-Tree Index** maintains a balanced multi-way search tree of $8\text{KB}$ index pages:

```
                          [ Root Node Page ]
                          [ 100 | 500 | 900 ]
                         /      |      \     \
       ┌────────────────┘       │       \     └────────────────┐
       ▼                        ▼        ▼                     ▼
 [ Leaf Page 1 ]        [ Leaf Page 2 ] [ Leaf Page 3 ]  [ Leaf Page 4 ]
 [ Keys 1..99  ]        [ Keys 100..499] [ Keys 500..899] [ Keys 900..1200 ]
       │                        │               │               │
       └────────────────────────┴───────────────┴───────────────┴──► Points to (Page#, Offset)
```

- High fan-out: A 3-level B-Tree index can index billions of rows with only **3 to 4 disk page lookups** ($O(\log N)$).
- Range Scans: Leaf pages form a doubly-linked list, allowing fast range scans (`WHERE age BETWEEN 20 AND 30`) by traversing leaf pointers sequentially.

---

## Why It Matters in Systems Programming

1. **Avoid Unnecessary I/O Bottlenecks**: Understanding that databases read in 8KB chunks prevents anti-patterns like selecting 50 columns when only 2 are needed (`SELECT *` bloat).
2. **Prevent Write Amplification**: Updating an indexed column requires updating both the heap table page and the B-Tree leaf page, creating multi-page write amplification and WAL traffic.
3. **Designing Cache-Friendly Schemas**: Normalization vs Denormalization tradeoffs directly affect the number of random disk pages your backend must read from the buffer pool.

## Real-World Analogy

- The **Disk Table** is an 800-page encyclopedia.
- A **Sequential Scan** is reading every word on all 800 pages to find references to "Rust".
- A **B-Tree Index** is the alphabetically sorted index at the back of the encyclopedia: in 3 page flips, it tells you: `"Rust is on Page 412, Paragraph 3"`.
- The **Buffer Pool** is your desk surface: you keep the 5 most recently used encyclopedia volumes open on your desk so you don't have to walk to the bookshelf every time.
- The **Write-Ahead Log (WAL)** is a scratchpad where you instantly jot down any notes before making formal edits to the encyclopedia pages.

## Complete, Compilable Code Example

Below is a simplified in-memory Rust implementation of a **Slotted Page (8KB Block Storage)** and a **WAL Append Engine** demonstrating how relational storage engines operate internally.

```rust
use std::io::{self, Write};

pub const PAGE_SIZE: usize = 8192; // 8 KB Standard Postgres/MySQL Page
pub const PAGE_HEADER_SIZE: usize = 24;

// ============================================================================
// 1. Slotted Page Physical Layout
// ============================================================================

#[derive(Debug, Clone, Copy)]
pub struct LinePointer {
    pub offset: u16,
    pub length: u16,
}

pub struct SlottedPage {
    pub data: [u8; PAGE_SIZE],
    pub line_pointers: Vec<LinePointer>,
    pub lower_free_offset: usize, // Grows downward
    pub upper_free_offset: usize, // Grows upward
}

impl SlottedPage {
    pub fn new() -> Self {
        Self {
            data: [0u8; PAGE_SIZE],
            line_pointers: Vec::new(),
            lower_free_offset: PAGE_HEADER_SIZE,
            upper_free_offset: PAGE_SIZE,
        }
    }

    /// Insert a raw tuple (row) into the 8KB slotted page
    pub fn insert_tuple(&mut self, tuple_data: &[u8]) -> Option<usize> {
        let tuple_len = tuple_data.len();
        let pointer_size = std::mem::size_of::<LinePointer>();

        // Check if there is enough free space between lower and upper offsets
        if self.lower_free_offset + pointer_size + tuple_len > self.upper_free_offset {
            return None; // Page full
        }

        // 1. Allocate tuple data from the bottom (upper_free_offset down)
        self.upper_free_offset -= tuple_len;
        let tuple_offset = self.upper_free_offset;
        self.data[tuple_offset..tuple_offset + tuple_len].copy_from_slice(tuple_data);

        // 2. Add Line Pointer at the top (lower_free_offset up)
        let lp = LinePointer {
            offset: tuple_offset as u16,
            length: tuple_len as u16,
        };
        self.line_pointers.push(lp);
        self.lower_free_offset += pointer_size;

        // Return Tuple Slot Index
        Some(self.line_pointers.len() - 1)
    }

    /// Read tuple by slot index
    pub fn get_tuple(&self, slot_idx: usize) -> Option<&[u8]> {
        let lp = self.line_pointers.get(slot_idx)?;
        let start = lp.offset as usize;
        let end = start + lp.length as usize;
        Some(&self.data[start..end])
    }

    pub fn free_space_bytes(&self) -> usize {
        self.upper_free_offset.saturating_sub(self.lower_free_offset)
    }
}

// ============================================================================
// 2. Minimal Write-Ahead Log (WAL) Record
// ============================================================================

#[derive(Debug)]
pub struct WalRecord {
    pub lsn: u64,
    pub page_id: u32,
    pub slot_idx: u16,
    pub payload: Vec<u8>,
}

pub struct WalEngine {
    current_lsn: u64,
    log_buffer: Vec<u8>,
}

impl WalEngine {
    pub fn new() -> Self {
        Self {
            current_lsn: 1,
            log_buffer: Vec::new(),
        }
    }

    /// Append record to WAL buffer and simulate synchronous fsync
    pub fn append(&mut self, page_id: u32, slot_idx: u16, payload: &[u8]) -> io::Result<u64> {
        let lsn = self.current_lsn;
        self.current_lsn += 1;

        // Encode WAL record: LSN (8B) + PageID (4B) + SlotID (2B) + PayloadLen (2B) + Payload
        self.log_buffer.extend_from_slice(&lsn.to_be_bytes());
        self.log_buffer.extend_from_slice(&page_id.to_be_bytes());
        self.log_buffer.extend_from_slice(&slot_idx.to_be_bytes());
        self.log_buffer.extend_from_slice(&(payload.len() as u16).to_be_bytes());
        self.log_buffer.extend_from_slice(payload);

        // In real systems: writer.flush() + file.sync_all() (fsync)
        Ok(lsn)
    }

    pub fn buffered_bytes(&self) -> usize {
        self.log_buffer.len()
    }
}

fn main() {
    println!("=== 1. Simulating 8KB Slotted Page Storage ===");
    let mut page = SlottedPage::new();
    println!("Initial Free Space: {} bytes", page.free_space_bytes());

    let user_1 = b"USER_ID=1001;NAME=Alice;BALANCE=5420.50";
    let user_2 = b"USER_ID=1002;NAME=Bob;BALANCE=120.00";
    let user_3 = b"USER_ID=1003;NAME=Charlie;BALANCE=98000.00";

    let slot_0 = page.insert_tuple(user_1).expect("Insert user 1");
    let slot_1 = page.insert_tuple(user_2).expect("Insert user 2");
    let slot_2 = page.insert_tuple(user_3).expect("Insert user 3");

    println!("Inserted 3 records into Slotted Page:");
    println!("  Slot 0 (User 1): {}", String::from_utf8_lossy(page.get_tuple(slot_0).unwrap()));
    println!("  Slot 1 (User 2): {}", String::from_utf8_lossy(page.get_tuple(slot_1).unwrap()));
    println!("  Slot 2 (User 3): {}", String::from_utf8_lossy(page.get_tuple(slot_2).unwrap()));
    println!("Remaining Free Space in Page: {} bytes", page.free_space_bytes());

    println!("\n=== 2. Simulating Write-Ahead Log (WAL) Flush ===");
    let mut wal = WalEngine::new();
    let lsn_1 = wal.append(1, slot_0 as u16, user_1).unwrap();
    let lsn_2 = wal.append(1, slot_1 as u16, user_2).unwrap();
    let lsn_3 = wal.append(1, slot_2 as u16, user_3).unwrap();

    println!("WAL Appended: LSN {}, LSN {}, LSN {}", lsn_1, lsn_2, lsn_3);
    println!("WAL Buffer Flushed: {} bytes written to sequential log", wal.buffered_bytes());
}
```

## Common Pitfalls & Compiler Errors

### 1. In-Place Update Fallacy
Engineers coming from application-level programming often assume updating a SQL column simply overwrites bytes in place on disk. In reality, modern MVCC databases (like PostgreSQL) **never update in place**: they insert a new tuple version and update the line pointer, leaving the old version for concurrent transactions until `VACUUM` cleans it up.

### 2. Assuming Unindexed Queries Scale Linearly
Without an index, querying `SELECT * FROM users WHERE email = 'test@example.com'` forces the database to read every single 8KB page from disk into the buffer pool. On a 100GB table, this requires reading 13 million 8KB pages!

## Complete Solutions to Exercises

### Solution 1 & 2: Tombstone Deletion and Page Compaction

```rust
impl SlottedPage {
    /// Mark a tuple as deleted by zeroing out its length (Tombstone)
    pub fn delete_tuple(&mut self, slot_idx: usize) -> bool {
        if let Some(lp) = self.line_pointers.get_mut(slot_idx) {
            lp.length = 0;
            true
        } else {
            false
        }
    }

    /// Compacts active tuples, eliminating dead space from deleted records
    pub fn compact(&mut self) {
        let mut new_data = [0u8; PAGE_SIZE];
        let mut new_upper = PAGE_SIZE;

        for lp in self.line_pointers.iter_mut() {
            if lp.length > 0 {
                let old_start = lp.offset as usize;
                let old_end = old_start + lp.length as usize;
                let len = lp.length as usize;

                new_upper -= len;
                new_data[new_upper..new_upper + len].copy_from_slice(&self.data[old_start..old_end]);
                lp.offset = new_upper as u16;
            }
        }

        self.data = new_data;
        self.upper_free_offset = new_upper;
    }
}
```
