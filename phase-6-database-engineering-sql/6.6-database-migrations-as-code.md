## Concept

In modern DevOps and systems engineering, the database schema is not managed manually via interactive SQL consoles. Instead, the schema is treated as **immutable, version-controlled code**.

Every schema modification (adding a table, altering a column, creating an index) is recorded in a numbered migration script (e.g., `202609040001_create_accounts.sql`).

```
                              Application Startup Sequence
                              ────────────────────────────
┌──────────────────────────────────────┐
│  Compiled Rust Binary                │
│  Includes embedded migrations        │
│  via `sqlx::migrate!("./migrations")`│
└──────────────────┬───────────────────┘
                   │ 1. Acquire Migration Lock (`pg_advisory_lock`)
                   ▼
┌──────────────────────────────────────┐
│  PostgreSQL Instance                 │
│  Checks `_sqlx_migrations` Table:    │
│  - 202609010001 (Applied)            │
│  - 202609020002 (Applied)            │
│  - 202609040003 (PENDING ➔ APPLIES)  │
└──────────────────┬───────────────────┘
                   │ 2. Execute within SQL Transaction
                   │ 3. Record Checksum & Timestamp
                   │ 4. Release Advisory Lock
                   ▼
┌──────────────────────────────────────┐
│  Service Ready to Accept HTTP Traffic│
└──────────────────────────────────────┘
```

---

### 1. Embedded Migrations (`sqlx::migrate!`)

Rather than requiring an external tool (like Flyway, Liquibase, or `sqlx-cli`) in production containers, Rust can compile raw `.sql` migration files directly into the compiled ELF binary:

```rust
use sqlx::PgPool;

pub async fn run_database_migrations(pool: &PgPool) -> Result<(), sqlx::migrate::MigrateError> {
    // Embeds all files in `./migrations` directory directly into binary at compile time
    sqlx::migrate!("./migrations")
        .run(pool)
        .await?;

    println!("All database migrations applied successfully!");
    Ok(())
}
```

---

### 2. The Migration Ledger Table (`_sqlx_migrations`)

When SQLx runs migrations, it maintains an internal tracking table in PostgreSQL:

```sql
CREATE TABLE _sqlx_migrations (
    version BIGINT PRIMARY KEY,
    description TEXT NOT NULL,
    installed_on TIMESTAMPTZ NOT NULL DEFAULT now(),
    success BOOLEAN NOT NULL,
    checksum BYTEA NOT NULL,
    execution_time BIGINT NOT NULL
);
```

#### Migration Checksums
Every migration file's content is SHA-384 hashed into `checksum`. If a developer modifies an already applied migration file in git, SQLx halts startup immediately with a **Checksum Mismatch Error** to prevent silent schema drift.

---

### 3. Zero-Downtime Migration Pattern: "Expand and Contract"

In production systems handling thousands of requests per second, you cannot run destructive migrations (like renaming a column) in a single deployment without breaking running web servers.

To perform zero-downtime schema evolution, use the **Expand and Contract** pattern across 3 phases:

```
Phase 1: EXPAND (Deploy DB Migration)
- Add NEW column `full_name` (NULLABLE) alongside old columns `first_name`, `last_name`.

Phase 2: DUAL-WRITE & BACKFILL (Deploy App Version N+1)
- App writes to both `first_name/last_name` AND `full_name`.
- Background worker backfills historical rows: `UPDATE users SET full_name = first_name || ' ' || last_name WHERE full_name IS NULL`.

Phase 3: CONTRACT (Deploy App Version N+2 & Final DB Migration)
- App reads and writes exclusively from `full_name`.
- DB migration drops old columns `first_name` and `last_name`.
```

---

## Why It Matters in Systems Programming

1. **Atomic Deployment & Self-Bootstrapping**: When your microservice container starts in Kubernetes or on bare metal, it automatically checks and applies pending migrations before binding its HTTP listener, guaranteeing that database tables exist before incoming requests arrive.
2. **Advisory Locks Prevent Race Conditions**: If 50 Kubernetes pods boot simultaneously, `sqlx::migrate!` acquires a PostgreSQL session-level advisory lock (`pg_advisory_lock`), ensuring only one pod executes the migration while the other 49 wait safely.
3. **Immutable History**: Once a migration is merged and deployed, it is never edited. Any correction must be a new migration file.

---

## Real-World Analogy

- **Manual SQL schema edits** are like building a skyscraper and knocking down walls on a whim without updating the architectural blueprint.
- **Database Migrations as Code** are like an append-only construction log: Page 1 documents the foundation, Page 2 documents the steel beams, Page 3 documents the electrical wiring. Any contractor arriving on site can follow the sequential log from scratch and reproduce the exact building structure.

## Complete, Compilable Code Example

Below is a self-contained in-memory **Migration Runner Engine** demonstrating advisory locking, checksum verification, and atomic version tracking in pure Rust:

```rust
use std::collections::BTreeMap;
use std::time::Instant;

// ============================================================================
// 1. Migration Record & Definition
// ============================================================================

#[derive(Debug, Clone)]
pub struct MigrationScript {
    pub version: i64,
    pub description: &'static str,
    pub sql_up: &'static str,
    pub checksum: u64, // Simplified numeric hash for demonstration
}

#[derive(Debug, Clone)]
pub struct AppliedMigration {
    pub version: i64,
    pub description: String,
    pub checksum: u64,
    pub execution_time_ms: u64,
}

// ============================================================================
// 2. Migration Runner Engine
// ============================================================================

pub struct MigrationEngine {
    applied_ledger: BTreeMap<i64, AppliedMigration>,
    advisory_lock_held: bool,
}

impl MigrationEngine {
    pub fn new() -> Self {
        Self {
            applied_ledger: BTreeMap::new(),
            advisory_lock_held: false,
        }
    }

    /// Calculate simple deterministic checksum of SQL string
    pub fn compute_checksum(sql: &str) -> u64 {
        use std::collections::hash_map::DefaultHasher;
        use std::hash::{Hash, Hasher};
        let mut hasher = DefaultHasher::new();
        sql.hash(&mut hasher);
        hasher.finish()
    }

    /// Simulate acquiring Postgres advisory lock
    pub fn acquire_lock(&mut self) -> Result<(), &'static str> {
        if self.advisory_lock_held {
            return Err("Advisory lock already acquired by another worker");
        }
        self.advisory_lock_held = true;
        Ok(())
    }

    pub fn release_lock(&mut self) {
        self.advisory_lock_held = false;
    }

    /// Execute pending migrations
    pub fn run_migrations(&mut self, scripts: &[MigrationScript]) -> Result<usize, String> {
        self.acquire_lock().map_err(|e| e.to_string())?;

        let mut newly_applied = 0;

        for script in scripts {
            if let Some(applied) = self.applied_ledger.get(&script.version) {
                // Verify Checksum Integrity
                if applied.checksum != script.checksum {
                    self.release_lock();
                    return Err(format!(
                        "FATAL: Migration {} ('{}') checksum mismatch! Disk: {}, Database: {}. File modified after apply!",
                        script.version, script.description, script.checksum, applied.checksum
                    ));
                }
                // Already applied and verified, skip
                continue;
            }

            // Apply new migration inside simulated atomic transaction
            println!("  [APPLYING] Migration {}: {} ...", script.version, script.description);
            let start = Instant::now();

            // Simulate executing raw SQL DDL
            println!("    Executing DDL: {}", script.sql_up.trim());

            let elapsed = start.elapsed().as_millis() as u64;

            self.applied_ledger.insert(
                script.version,
                AppliedMigration {
                    version: script.version,
                    description: script.description.to_string(),
                    checksum: script.checksum,
                    execution_time_ms: elapsed,
                },
            );
            newly_applied += 1;
        }

        self.release_lock();
        Ok(newly_applied)
    }

    pub fn print_status(&self) {
        println!("\n=== Database Schema Migration Ledger (_sqlx_migrations) ===");
        for (version, record) in &self.applied_ledger {
            println!(
                "  Version: {} | Description: {:<25} | Checksum: {:016X} | Took: {}ms",
                version, record.description, record.checksum, record.execution_time_ms
            );
        }
    }
}

// ============================================================================
// 3. Execution & Verification
// ============================================================================

fn main() {
    let mut engine = MigrationEngine::new();

    let migration_1_sql = "CREATE TABLE accounts (id BIGSERIAL PRIMARY KEY, email TEXT NOT NULL UNIQUE);";
    let migration_2_sql = "ALTER TABLE accounts ADD COLUMN balance_cents BIGINT NOT NULL DEFAULT 0;";

    let script_1 = MigrationScript {
        version: 202609010001,
        description: "create_accounts_table",
        sql_up: migration_1_sql,
        checksum: MigrationEngine::compute_checksum(migration_1_sql),
    };

    let script_2 = MigrationScript {
        version: 202609020002,
        description: "add_balance_column",
        sql_up: migration_2_sql,
        checksum: MigrationEngine::compute_checksum(migration_2_sql),
    };

    println!("=== 1. First Boot: Applying Initial Migrations ===");
    let migrations_v1 = vec![script_1.clone(), script_2.clone()];
    let applied = engine.run_migrations(&migrations_v1).unwrap();
    println!("Successfully applied {} migrations.\n", applied);
    engine.print_status();

    println!("\n=== 2. Second Boot: Zero Pending Migrations ===");
    let applied_second_boot = engine.run_migrations(&migrations_v1).unwrap();
    println!("Applied {} migrations (Database is up-to-date).\n", applied_second_boot);

    println!("=== 3. Simulating Illegal File Mutation After Deployment ===");
    let tampered_script_1 = MigrationScript {
        version: 202609010001,
        description: "create_accounts_table",
        sql_up: "CREATE TABLE accounts (id BIGSERIAL PRIMARY KEY, email TEXT NOT NULL, username TEXT);", // Tampered!
        checksum: MigrationEngine::compute_checksum("CREATE TABLE accounts (id BIGSERIAL PRIMARY KEY, email TEXT NOT NULL, username TEXT);"),
    };

    let tampered_batch = vec![tampered_script_1, script_2];
    match engine.run_migrations(&tampered_batch) {
        Ok(_) => println!("Error: Failed to catch tampered migration!"),
        Err(err) => println!("Caught Schema Drift Error as expected:\n{}", err),
    }
}
```

## Common Pitfalls & Compiler Errors

### 1. Modifying Past Migrations
Never alter an existing migration file that has already been deployed to production or shared branches. If you need to fix a column type or add an index, create a brand-new migration file (`202609040002_fix_column.sql`).

### 2. Non-Transactional DDL in MySQL / CockroachDB
While PostgreSQL supports transactional DDL (if a migration fails halfway through, the entire `ALTER TABLE` is rolled back), MySQL and older databases do not support transactional DDL. If an error occurs midway through a migration in MySQL, the database is left in a dirty, half-applied state.

### Solution 1: Migration Rollback

```rust
impl MigrationEngine {
    pub fn revert_last(&mut self, scripts: &[MigrationScript]) -> Result<i64, String> {
        let last_version = match self.applied_ledger.keys().last().cloned() {
            Some(v) => v,
            None => return Err("No migrations to revert".to_string()),
        };

        println!("Reverting migration {} ...", last_version);
        self.applied_ledger.remove(&last_version);
        Ok(last_version)
    }
}
```
