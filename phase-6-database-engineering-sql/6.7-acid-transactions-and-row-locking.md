## Concept

In financial systems, inventory control, and multi-threaded backends, multiple concurrent requests attempt to read and mutate the same data simultaneously. Without strict concurrency control, race conditions cause **double spending**, **negative inventory balances**, and **corrupted financial ledgers**.

```
Transaction A (Withdraw $50)                    Transaction B (Withdraw $50)
────────────────────────────                    ────────────────────────────
1. Read Balance ($60)                           1. Read Balance ($60)
   (Both see $60 > $50 ➔ OK)                       (Both see $60 > $50 ➔ OK)
2. New Balance = $60 - $50 = $10                2. New Balance = $60 - $50 = $10
3. UPDATE balance = $10                         3. UPDATE balance = $10
────────────────────────────────────────────────────────────────────────────
Result: $100 withdrawn from a $60 account! Double-Spend Disaster!
```

---

### 1. The ANSI SQL Isolation Levels

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly |
| :--- | :---: | :---: | :---: | :---: |
| **Read Uncommitted** | Possible | Possible | Possible | Possible |
| **Read Committed** *(Postgres Default)* | **Prevented** | Possible | Possible | Possible |
| **Repeatable Read** *(Snapshot Isolation)* | **Prevented** | **Prevented** | **Prevented** *(in PG)* | Possible |
| **Serializable** *(SSI)* | **Prevented** | **Prevented** | **Prevented** | **Prevented** |

In PostgreSQL **Read Committed**, each SQL statement sees a new snapshot of committed data. In **Repeatable Read**, the entire transaction sees an immutable snapshot frozen at the exact moment the transaction began.

---

### 2. Pessimistic Locking: `SELECT FOR UPDATE`

To prevent concurrent race conditions in **Read Committed** mode, we explicitly lock rows before mutating them:

```sql
BEGIN;

-- Acquires an exclusive row-level lock on account #42
-- Any other transaction trying to SELECT FOR UPDATE or UPDATE this row BLOCKS until this commits.
SELECT id, balance_cents 
FROM accounts 
WHERE id = 42 
FOR UPDATE;

-- Safely deduct balance knowing no other thread can touch row #42
UPDATE accounts 
SET balance_cents = balance_cents - 5000 
WHERE id = 42;

COMMIT;
```

#### Non-Blocking Lock Variants
1. **`FOR UPDATE NOWAIT`**: Fails immediately with error `55P03 (lock_not_available)` instead of blocking if another transaction holds the lock.
2. **`FOR UPDATE SKIP LOCKED`**: Skips locked rows and grabs the next unlocked row. This is the foundation of **high-throughput distributed job queues in PostgreSQL**.

```sql
-- High-throughput, zero-contention background job consumer:
SELECT id, task_payload 
FROM job_queue 
WHERE status = 'PENDING' 
ORDER BY priority DESC 
LIMIT 1 
FOR UPDATE SKIP LOCKED;
```

### 3. Optimistic Concurrency Control (OCC)

Instead of acquiring database locks, **Optimistic Concurrency Control (OCC)** uses a monotonic version number or timestamp:

```sql
-- Step 1: Read row (e.g. version is currently 4)
SELECT id, balance_cents, version FROM accounts WHERE id = 42;

-- Step 2: In application code, calculate new balance
-- Step 3: Conditional Update checking version
UPDATE accounts 
SET balance_cents = 1000, version = version + 1 
WHERE id = 42 AND version = 4;
```
If another transaction updated the row first, `version` is already `5`. The `UPDATE` modifies **0 rows**. The application detects `rows_affected == 0` and retries the operation.

---

### 4. Deadlock Prevention: Deterministic Lock Ordering

A **Deadlock** occurs when:
- Tx 1 locks Account A, then attempts to lock Account B.
- Tx 2 locks Account B, then attempts to lock Account A.
- Both transactions freeze forever waiting on each other until PostgreSQL's `deadlock_timeout` triggers and aborts one.

```
       Tx 1                   Tx 2
        │                      │
        ▼                      ▼
  [ Lock Acc A ]        [ Lock Acc B ]
        │                      │
        ▼                      ▼
[ Wait for Acc B ] ◄══► [ Wait for Acc A ]   ◄── DEADLOCK!
```

#### The Golden Rule of Deadlock Prevention:
**Always acquire locks in strictly sorted order by Primary Key (e.g., `min(id1, id2)` first, then `max(id1, id2)`).**

---

## Why It Matters in Systems Programming

1. **High-Throughput Task Queues**: Using `FOR UPDATE SKIP LOCKED` enables 100 concurrent Rust worker threads to poll a single PostgreSQL table without lock contention or duplicate work.
2. **Preventing Balance Inconsistencies**: Financial ledgers require double-entry bookkeeping wrapped in atomic transactions with pessimistic row locks.
3. **Deadlock-Free Wire Protocol Handling**: Enforcing sorted lock ordering in Rust services guarantees zero deadlock rollbacks.

---

## Real-World Analogy

- **Pessimistic Locking (`SELECT FOR UPDATE`)** is like putting a physical padlock on a fitting room door before trying on clothes. Nobody else can enter until you unlock the door and leave.
- **`SKIP LOCKED`** is like walking into a large airport restroom with 20 stalls: you don't stand waiting at the first locked stall; you walk down the hall and immediately enter the first open stall.
- **Optimistic Concurrency Control (OCC)** is like collaborating on a shared Google Doc: both people edit their copy, and when saving, the system checks if someone made a revision while you were typing.

## Complete, Compilable Code Example

Below is a complete, thread-safe financial transfer engine in pure Rust demonstrating pessimistic locking, sorted lock ordering, and deadlock-free transfers:

```rust
use std::collections::HashMap;
use std::sync::{Arc, Mutex};
use std::thread;

// ============================================================================
// 1. Account Entity & Thread-Safe In-Memory Ledger
// ============================================================================

#[derive(Debug, Clone)]
pub struct Account {
    pub id: u64,
    pub owner: String,
    pub balance_cents: i64,
    pub version: u64,
}

pub struct BankLedger {
    // Each account has its own Mutex (Row-Level Lock)
    accounts: HashMap<u64, Arc<Mutex<Account>>>,
}

impl BankLedger {
    pub fn new() -> Self {
        Self {
            accounts: HashMap::new(),
        }
    }

    pub fn insert_account(&mut self, id: u64, owner: &str, initial_balance: i64) {
        let account = Account {
            id,
            owner: owner.to_string>,
            balance_cents: initial_balance,
            version: 1,
        };
        self.accounts.insert(id, Arc::new(Mutex::new(account)));
    }

    pub fn get_account_lock(&self, id: u64) -> Option<Arc<Mutex<Account>>> {
        self.accounts.get(&id).cloned()
    }

    /// Deadlock-Free Atomic Money Transfer using Deterministic Lock Ordering
    pub fn transfer(
        &self,
        from_id: u64,
        to_id: u64,
        amount_cents: i64,
    ) -> Result<(), &'static str> {
        if from_id == to_id {
            return Err("Cannot transfer to the same account");
        }
        if amount_cents <= 0 {
            return Err("Transfer amount must be positive");
        }

        let from_lock = self.get_account_lock(from_id).ok_or("Source account not found")?;
        let to_lock = self.get_account_lock(to_id).ok_or("Destination account not found")?;

        // CRITICAL: Deterministic Lock Ordering (Always lock lower ID first)
        // Prevents circular wait deadlocks between concurrent transfers
        let (first_lock, second_lock) = if from_id < to_id {
            (&from_lock, &to_lock)
        } else {
            (&to_lock, &from_lock)
        };

        // Acquire row locks in sorted order
        let mut _guard_1 = first_lock.lock().unwrap();
        let mut _guard_2 = second_lock.lock().unwrap();

        // Mutate accounts (Both row locks held!)
        let mut from_acc = from_lock.lock().unwrap_or(_guard_1);
        let mut to_acc = to_lock.lock().unwrap_or(_guard_2);

        if from_acc.balance_cents < amount_cents {
            return Err("Insufficient funds");
        }

        from_acc.balance_cents -= amount_cents;
        from_acc.version += 1;

        to_acc.balance_cents += amount_cents;
        to_acc.version += 1;

        println!(
            "  [TRANSFER OK] ${:.2} from {} (#{}) to {} (#{}), New Balances: [From: ${:.2}, To: ${:.2}]",
            amount_cents as f64 / 100.0,
            from_acc.owner,
            from_id,
            to_acc.owner,
            to_id,
            from_acc.balance_cents as f64 / 100.0,
            to_acc.balance_cents as f64 / 100.0
        );

        Ok(())
    }
}

// ============================================================================
// 2. High-Concurrency Stress Test
// ============================================================================

fn main() {
    println!("=== 1. Initializing Bank Ledger ===");
    let mut ledger = BankLedger::new();
    ledger.insert_account(101, "Alice", 100_000);  // $1,000.00
    ledger.insert_account(102, "Bob", 100_000);    // $1,000.00

    let ledger = Arc::new(ledger);

    println!("Initial State: Alice ($1,000.00), Bob ($1,000.00)");
    println!("Spawning bidirectional concurrent transfers (Tx 1: 101->102 vs Tx 2: 102->101)...");

    let mut handles = Vec::new();

    // 10 Threads transferring Alice -> Bob ($10)
    for _ in 0..10 {
        let l = Arc::clone(&ledger);
        handles.push(thread::spawn(move || {
            let _ = l.transfer(101, 102, 1000);
        }));
    }

    // 10 Threads transferring Bob -> Alice ($10) simultaneously
    for _ in 0..10 {
        let l = Arc::clone(&ledger);
        handles.push(thread::spawn(move || {
            let _ = l.transfer(102, 101, 1000);
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("\n=== Final Verification ===");
    let alice_acc = ledger.get_account_lock(101).unwrap().lock().unwrap().clone();
    let bob_acc = ledger.get_account_lock(102).unwrap().lock().unwrap().clone();
    println!("Alice Final Balance: ${:.2} (Version: {})", alice_acc.balance_cents as f64 / 100.0, alice_acc.version);
    println!("Bob Final Balance:   ${:.2} (Version: {})", bob_acc.balance_cents as f64 / 100.0, bob_acc.version);
    println!("Total System Wealth: ${:.2} (Conserved!)", (alice_acc.balance_cents + bob_acc.balance_cents) as f64 / 100.0);
}
```

## Common Pitfalls & Compiler Errors

### 1. Forgetting `FOR UPDATE` During Multi-Step Transactions
In `Read Committed` mode, running `SELECT balance FROM accounts WHERE id = 1` does NOT lock the row. A concurrent transaction can update the balance before your subsequent `UPDATE` runs.
**Fix**: Always use `SELECT ... FOR UPDATE` when reading data that determines the mutation logic.

### 2. Lock Escalation & Long-Running Transactions
Holding a transaction open while performing long external operations (e.g. image encoding or sending an email) keeps row locks active for seconds, causing dozens of other transactions to queue up and fail with `LockTimeout`.

## Complete Solutions to Exercises

### Solution 1: OCC Balance Update

```rust
impl BankLedger {
    pub fn optimistic_update_balance(
        &self,
        account_id: u64,
        expected_version: u64,
        delta_cents: i64,
    ) -> Result<u64, &'static str> {
        let lock = self.get_account_lock(account_id).ok_or("Account not found")?;
        let mut acc = lock.lock().unwrap();

        if acc.version != expected_version {
            return Err("OCC Conflict: Account was modified by another transaction! Retry.");
        }

        if acc.balance_cents + delta_cents < 0 {
            return Err("Insufficient funds");
        }

        acc.balance_cents += delta_cents;
        acc.version += 1;

        Ok(acc.version)
    }
}
```

### Solution 2: PostgreSQL Worker Queue Query

```sql
WITH claim_batch AS (
    SELECT id 
    FROM job_tasks 
    WHERE status = 'PENDING' 
    ORDER BY created_at ASC 
    LIMIT 5 
    FOR UPDATE SKIP LOCKED
)
UPDATE job_tasks 
SET status = 'PROCESSING', updated_at = now() 
FROM claim_batch 
WHERE job_tasks.id = claim_batch.id 
RETURNING job_tasks.id, job_tasks.payload;
```
