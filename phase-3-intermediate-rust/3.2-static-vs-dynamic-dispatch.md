## Concept

Polymorphism allows a single function or data structure to operate on multiple different types. In Rust, you choose between two execution models:

1. **Static Dispatch (Compile-Time Polymorphism)** via Generics and `impl Trait`.
2. **Dynamic Dispatch (Runtime Polymorphism)** via Trait Objects (`dyn Trait`).

---

### 1. Static Dispatch via Monomorphization

When you use generic type parameters (`fn send<T: Transport>(t: T)` or `fn send(t: impl Transport)`), the Rust compiler performs **Monomorphization**:
- It inspects every concrete type passed to the function across the entire codebase.
- It generates a separate, specialized copy of the machine code for each type.

```
Source Code:
fn send<T: Transport>(t: T)

Compiled Binary (Monomorphized):
fn send_tcp(t: TcpTransport) { ... inlined assembly ... }
fn send_udp(t: UdpTransport) { ... inlined assembly ... }
```

- **Pros**: Zero runtime overhead, enables CPU instruction caching and aggressive compiler inlining.
- **Cons**: Increases binary size ("code bloat"), and all items in a collection must be of the **same single concrete type** (homogeneous).

---

### 2. Dynamic Dispatch via Trait Objects (`dyn Trait`)

When you need a heterogeneous collection (e.g., storing `TcpTransport`, `UdpTransport`, and `TlsTransport` in the same `Vec`), the concrete types cannot be known at compile time.

You use a **Trait Object** behind a pointer: `Box<dyn Transport>` or `&dyn Transport`.

#### The 16-Byte Fat Pointer (Vtable Layout)
Because `dyn Trait` is dynamically sized (**DST** / `!Sized`), a trait object is stored as a **Fat Pointer** consisting of two 64-bit words:
1. **Data Pointer**: Points to the instance data on the heap or stack.
2. **Vtable Pointer**: Points to the **Virtual Method Table** containing function pointers and drop glue.

```
Trait Object: Box<dyn Transport> (16 bytes on Stack)
┌────────────────────────┬────────────────────────┐
│   Data Pointer (8B)    │   Vtable Pointer (8B)  │
└───────────┬────────────┴───────────┬────────────┘
            │                        │
            ▼ (Heap)                 ▼ (Read-Only Data Segment)
      ┌───────────┐            ┌──────────────────────┐
      │ TcpStream │            │ drop_in_place() ptr  │
      │ { fd: 4 } │            │ size: 24, align: 8   │
      └───────────┘            │ send() fn pointer    │
                               └──────────────────────┘
```

- **Pros**: Supports heterogeneous collections and runtime plugin systems.
- **Cons**: Minor runtime cost from vtable pointer indirection; prevents function inlining.

---

### 3. Object Safety Rules

A trait can be turned into a trait object `dyn Trait` only if it is **Object-Safe**:
1. The trait does **not** require `Self: Sized`.
2. None of its methods return `Self`.
3. None of its methods have generic type parameters.

---

### 4. Comparison Summary

| Feature | Static Dispatch (`impl Trait`, `<T: Trait>`) | Dynamic Dispatch (`Box<dyn Trait>`) |
| :--- | :--- | :--- |
| **Resolution Time** | Compile time | Runtime |
| **Mechanism** | Monomorphization | Vtable fat pointer |
| **Performance** | Maximum (Inlined machine code) | Slight indirection penalty |
| **Memory** | Larger executable binary size | Smaller binary, 16-byte fat pointers |
| **Collections** | Homogeneous (`Vec<T>`) | Heterogeneous (`Vec<Box<dyn Trait>>`) |

---

## Why it matters

- **HTTP Middleware Pipelines**: Web frameworks like Axum and Actix allow users to chain arbitrary middleware handlers using `Box<dyn Middleware>` to execute request transformations.
- **Driver Abstractions**: Operating systems and embedded systems write hardware driver registries where serial, I2C, and SPI peripherals are registered as trait objects.

---

## Analogy

- **Static Dispatch**: A custom tailored suit built specifically for one exact person. Perfect fit and maximum speed, but unusable by anyone else.
- **Dynamic Dispatch**: A one-size-fits-all adjustable strap with velcro. Slightly bulkier and requires adjusting at runtime, but works for anyone.

## Code Example

Save this to `src/main.rs` and run `cargo run`:

```rust
// Shared trait for metrics reporting
pub trait MetricsSink {
    fn record_metric(&self, name: &str, value: f64);
    fn flush(&self);
}

// Concrete Implementation 1: Console Logger
pub struct ConsoleSink;
impl MetricsSink for ConsoleSink {
    fn record_metric(&self, name: &str, value: f64) {
        println!("[CONSOLE METRIC] {} = {:.2}", name, value);
    }
    fn flush(&self) {
        println!("[CONSOLE METRIC] Flushed to stdout.");
    }
}

// Concrete Implementation 2: In-Memory Aggregator
pub struct MemorySink {
    buffer: std::sync::Mutex<Vec<(String, f64)>>,
}

impl MemorySink {
    pub fn new() -> Self {
        MemorySink {
            buffer: std::sync::Mutex::new(Vec::new()),
        }
    }
}

impl MetricsSink for MemorySink {
    fn record_metric(&self, name: &str, value: f64) {
        let mut buf = self.buffer.lock().unwrap();
        buf.push((name.to_string(), value));
        println!("[MEMORY SINK] Buffered metric '{}', total count: {}", name, buf.len());
    }
    fn flush(&self) {
        let mut buf = self.buffer.lock().unwrap();
        buf.clear();
        println!("[MEMORY SINK] Buffer cleared.");
    }
}

// -------------------------------------------------------------
// 1. Static Dispatch: Generics (High throughput, single sink type)
// -------------------------------------------------------------
pub fn record_batch_static<S: MetricsSink>(sink: &S, batch: &[(&str, f64)]) {
    for (name, val) in batch {
        sink.record_metric(name, *val);
    }
    sink.flush();
}

// --------------------------------------------------------------------
// 2. Dynamic Dispatch: Trait Objects (Heterogeneous fan-out dispatcher)
// --------------------------------------------------------------------
pub struct MultiSinkDispatcher {
    sinks: Vec<Box<dyn MetricsSink>>, // Stores different types together!
}

impl MultiSinkDispatcher {
    pub fn new() -> Self {
        MultiSinkDispatcher { sinks: Vec::new() }
    }

    pub fn register_sink(&mut self, sink: Box<dyn MetricsSink>) {
        self.sinks.push(sink);
    }

    pub fn broadcast_metric(&self, name: &str, value: f64) {
        for sink in &self.sinks {
            sink.record_metric(name, value);
        }
    }
}

fn main() {
    let console = ConsoleSink;
    let memory = MemorySink::new();

    // 1. Static Dispatch Example
    let batch = [("cpu_usage", 78.4), ("memory_mb", 1024.0)];
    println!("--- Static Dispatch Call ---");
    record_batch_static(&console, &batch);

    // 2. Dynamic Dispatch Example (Fan-Out)
    println!("\n--- Dynamic Dispatch Multi-Sink ---");
    let mut dispatcher = MultiSinkDispatcher::new();
    dispatcher.register_sink(Box::new(console));
    dispatcher.register_sink(Box::new(memory));

    dispatcher.broadcast_metric("network_rx_kbps", 450.2);
}
```

## Common Mistakes

### 1. Declaring `Vec<dyn Trait>` Without Pointer Indirection
Attempting to create a collection of bare `dyn Trait`:
```rust
// ❌ COMPILE ERROR: the size for values of type `(dyn MetricsSink + 'static)` cannot be known at compilation time
let sinks: Vec<dyn MetricsSink> = Vec::new();

// ✅ CORRECT: Box or reference the dynamically sized trait
let sinks: Vec<Box<dyn MetricsSink>> = Vec::new();
```

---

### 2. Attempting Trait Objects on Traits with Generic Methods
```rust
trait Serializer {
    fn serialize<T>(&self, value: &T) -> String; // Generic method!
}

// ❌ COMPILE ERROR: Trait `Serializer` cannot be made into an object because method `serialize` has generic type parameters
fn handle(s: Box<dyn Serializer>) { ... }
```
*Why it fails*: A vtable needs a fixed number of function pointers. A generic method could produce infinite machine code functions, which cannot fit into a static vtable.

---

### 3. Defaulting to `Box<dyn Trait>` When Generics Are Sufficient
Wrapping everything in `Box<dyn Trait>` adds unnecessary heap allocations and removes compiler optimization opportunities. Default to static dispatch with `impl Trait` or generics unless runtime flexibility or heterogeneous collections are required.

## Solutions

### Solution to Exercise 1
```rust
pub trait Plugin {
    fn name(&self) -> &'static str;
    fn execute(&self, payload: &str) -> String;
}

pub struct UpperPlugin;
impl Plugin for UpperPlugin {
    fn name(&self) -> &'static str { "UpperCase" }
    fn execute(&self, payload: &str) -> String { payload.to_uppercase() }
}

pub struct TrimPlugin;
impl Plugin for TrimPlugin {
    fn name(&self) -> &'static str { "Trimmer" }
    fn execute(&self, payload: &str) -> String { payload.trim().to_string() }
}

pub struct PluginManager {
    plugins: Vec<Box<dyn Plugin>>,
}

impl PluginManager {
    pub fn new() -> Self {
        PluginManager { plugins: Vec::new() }
    }
    pub fn add(&mut self, plugin: Box<dyn Plugin>) {
        self.plugins.push(plugin);
    }
    pub fn execute_all(&self, payload: &str) -> Vec<String> {
        self.plugins.iter().map(|p| p.execute(payload)).collect()
    }
}
```

---

### Solution to Exercise 2
**Explanation**: With static dispatch, the compiler knows the exact machine code instructions of the callee at compile time, allowing it to inline the body of the function directly into the loop, unroll loops, and combine adjacent calculations into 128-bit or 256-bit SIMD vector registers. With dynamic dispatch, the function address must be loaded from memory (vtable) at runtime, inserting an indirect jump instruction that prevents inlining and compiler SIMD loop vectorization.

---

### Solution to Exercise 3
```rust
pub trait Task {
    fn duplicate(&self) -> Box<dyn Task>;
    fn run(&self);
}

pub struct WorkerTask {
    pub id: u64,
}

impl Task for WorkerTask {
    fn duplicate(&self) -> Box<dyn Task> {
        Box::new(WorkerTask { id: self.id })
    }
    fn run(&self) {
        println!("Running worker task {}", self.id);
    }
}

fn main() {
    let mut manager = PluginManager::new();
    manager.add(Box::new(UpperPlugin));
    manager.add(Box::new(TrimPlugin));

    let results = manager.execute_all("  hello systems  ");
    assert_eq!(results, vec!["  HELLO SYSTEMS  ", "hello systems"]);

    let task: Box<dyn Task> = Box::new(WorkerTask { id: 42 });
    let cloned_task = task.duplicate();
    cloned_task.run();
    println!("All dispatch exercises passed!");
}
```
